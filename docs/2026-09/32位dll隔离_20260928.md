# 32 位 dll 隔离处置（2026-09-28）

## 一句话

`op_c_api_x86.dll`（2026-09-14 上游预编译件）会让 32 位目标进程崩溃，已全部移出活动路径，隔离到
`D:\AutoPro\op-master\backup\isolated\x86_dll_20260928\`。**当前工具链只走 64 位。**

## 为什么隔离

| 项 | 事实 |
|---|---|
| 文件 | `op_c_api_x86.dll`，**7 859 200 字节**，sha1 `febb1cfd9f3620ebf520a658f04571c7fc3d739a` |
| 来源 | **上游预编译件**，时间戳 2026-09-14（对比：本仓库 x64 构建 2026-09-28 / 27.8 MB / 256 导出） |
| 接口 | **214 个导出**，比 x64 少 42 个（缺 `OpRequestCaptureForTest`、全部 A\* 族、`AutoOcr*`、`DxAttr`、`GetFps`、锁窗口…） |
| 致命点 | 早于本仓库**全部** hook 加固（`c4420ae` 09-16「DX 注入致 0xC0000005·延迟加载失败钩子兜底」、H2b「`setup` 先发布 trampoline 再 `MH_EnableHook`」） |

**触发链路（已实证）**：

1. 宿主侧导出名解析修复（`ad6e460`）后，32 位目标从「**干净失败**」（解析不到 `_SetDisplayHook@8` → 不注入不调用）
   变成「**真的调用**这份旧 dll 的 hook 代码」。
2. 旧 dll 的 `DisplayHook setup locate failed`（`target=00000000 detour=00000000`）→ 返回 0。
3. 目标进程随即 `0xC0000005`（ACCESS_VIOLATION，WER 类型 **BEX**，故障模块 **unknown**、偏移 **0** = 调用空函数指针）。
4. 转储：`%LOCALAPPDATA%\CrashDumps\client.exe.8944.dmp`（52.9 MB）。
5. 目标：蜀门 `client.exe`（i386 + D3D9）。

> ⚠️ 关键认知：**修好导出名解析 ≠ 32 位可用**。解析修好只是让宿主能真正调到那份危险 dll。

## 隔离了什么

全盘 17 份副本、全部同源（sha1 一致）：

- **13 份活动副本 → 已移入隔离目录**（保留原路径结构，便于反向恢复）
  - `OPTool/Common/Dll/`（主副本，csproj 从这里分发）
  - `OPTool/{Common,OPTestTool,WordDictTool}/bin/Release/**/Dll/`
  - 工作区探针目录：`optool_verify/`、`op_audit/WordDictLayoutProbe/`、`portable_probe/`、`wordcut_verify/{comma,ocr,wordcut}_probe/`
- **4 份历史快照 → 有意保留不清**（`backup/2026-09-23_stable/`、`backup/2026-09-28_stable/` 下的发布件快照）
  —— 快照的语义是"冻结的历史发布件"，其完整性优先；它们不会被自动加载。

清单（含逐条 `原路径 -> 隔离路径` 映射，可直接反向恢复）：
`backup/isolated/x86_dll_20260928/_MANIFEST.txt`

## 隔离后的能力边界

| 功能 | 32 位目标（如蜀门） | 说明 |
|---|---|---|
| `normal` / `gdi` 绑定、截图 | ✅ 可用 | 不注入，走桌面 DC / GDI |
| 图色（FindColor/FindPic/GetColor…） | ✅ 可用 | 基于截图 |
| OCR（字库 / AI） | ✅ 可用 | 基于截图 |
| OpenCV（`Cv*` 36 个） | ✅ 可用 | 基于截图 |
| 窗口查询 / 枚举 / 进程 | ✅ 可用 | Win32 |
| **前台**键鼠 | ✅ 可用 | 走 `SendInput` 类，不注入 |
| **`dx` / `dx.d3d9` / `opengl` 显示捕获** | ❌ **不可用** | 需注入 x86 dll |
| **后台键鼠**（dx 输入通道） | ❌ **不可用** | 需注入 x86 dll |
| 内存读写 | ❌ 不可用 | 需跨进程注入/驱动 |

> 对 32 位目标做注入类调用现在会**干净失败**（"file not exists"），不再崩目标进程 —— 这正是隔离的目的。

## 想恢复 32 位怎么走

唯一正确路径是**自建 x86**（拿到含全部加固的 `op_c_api_x86.dll`）：

```bash
cd D:/AutoPro/op-master/op
python build.py -a x86 --deps-arch both
```

前置成本：**OpenCV 不是可选项**（`libop/CMakeLists.txt` 无 `OP_ENABLE_OPENCV` 开关，硬要求
`install/<generator>-<arch>` 目录），而 `_deps/opencv/install/` 与 `_deps/BlackBone/build/`
**都只有 x64** ⇒ 首次需源码构建 OpenCV x86。产出后再用 `_MANIFEST.txt` 反向恢复或直接替换。

> ⚠️ 在拿到自建 x86 之前，**不要**从隔离目录手工恢复这份 dll —— 恢复到活动路径就等于恢复崩溃风险。
