# C API / 注入侧导出 异常覆盖普查（H14 结案）

日期：2026-09-28　｜　对象：`build/nmake-x64-Release/libop/op_c_api_x64.dll`　｜　方法：静态扫描 + DLL 导出表交叉核对

## 零、结论速览

| 项 | 结果 |
|---|---|
| 台账原描述（H14） | 「199 个 C 导出中仅 **5 个**公开函数有 try/catch → 异常穿越 `extern "C"` 边界 = 宿主崩溃」 |
| 普查结论 | **前提不成立，无需加统一包裹**。导出总数 **268**，其中 **264 个已有护栏**（98.5%） |
| 真正零护栏的 | `op_c_api.cpp` 4 条（其中 2 条实际无风险、1 条纯转发），以及**台账完全没有提到的** `HookExport.cpp` 12 个注入侧导出 |
| 实际处置 | 只补了注入侧那 12 个（它们的爆炸半径更大：崩的是**游戏进程**，不是宿主），并加了可测的护栏纯函数用例 |
| 同类误判次数 | 这是本项目第 4 次「先按台账描述改，读代码发现描述本身错」——**先读调用链再判定** |

## 二、宿主侧 C API：264/268 已有护栏

`op_c_api.cpp` 的护栏不是"每个函数各写一遍 try"，而是**统一模板 + 函数体走模板**：

| 入口 | try 位置 | 说明 |
|---|---|---|
| `call_int` / `call_ret` | `op_c_api.cpp:51` | 绝大多数返回 int/long 的导出走这里 |
| `call_intptr` | `:76` | 返回句柄/指针的导出 |
| `call_string` | `:94` | 返回 `const wchar_t*` 的导出（结果写进 `op_c_context::string_result`） |
| `call_json_string` | `:112` | 返回 JSON 字符串的导出（带 fallback 常量） |
| `call_memory` | `:163` | 内存读写类导出 |
| `OpCreate` | `:181` | 生命周期，自带 try |
| `OpFindPic` | `:881` | 多出参，自带 try |
| `OpGetScreenData` / `OpGetScreenDataBmp` / `OpGetScreenFrameInfo` | `:995/:1018/:1045` | 需要写出参，自带 try |

统计口径（`scripts/c_api_throw_survey.py`，已计入 `OP_MOUSE_RET` / `OP_CV_FILE_RET` 两个宏批量生成的导出）：

```
导出总数 257（静态扫源，比 DLL 少 1 —— 见第四节）
  guarded_helper   248   走 call_* 模板
  guarded_own        5   自带 try（上表后 5 个）
  UNGUARDED          4   ↓
```

### 4 条 UNGUARDED 逐条判定

| 行 | 函数 | 判定 |
|---|---|---|
| L192 | `OpDestroy` | `delete handle` → `~op_c_context` 是 `= default`，隐式 `noexcept`。析构真抛的话在进入 `catch` 之前就 `std::terminate` 了，**包 try 无效**。非缺陷 |
| L198 | `OpVer` | `return OP_WIDE_TEXT(OP_VERSION);` 宏字面量，零可抛点 |
| L669 | `OpUnbindWindow` | 函数体只有 `return OpUnBindWindow(handle);` —— **纯转发**，被转发者走 `call_ret` 已护栏。扫描器的假阳性 |
| L947 | `OpRequestCaptureForTest` | 唯一真正裸露的：直接 `BindingSession::set_display_method` / `Image` 分配（`bad_alloc` 可达）。但它名字里就带 `ForTest`，只由测试与诊断脚本调用，不是宿主 API 面 |

⇒ **宿主侧不需要"统一包裹"改造**。台账 H14 建议的"评估真实可抛点，或在导出层加统一包裹"——真实可抛点已被 264/268 的既有护栏覆盖，改造收益 ≈ 0，风险（动 1683 行里 250+ 函数）远大于收益。

## 三、真正的零护栏：注入侧 12 个导出（台账未提）

`HookExport.cpp` 的 12 个 `__stdcall` 导出**一个 try 都没有**。它们与宿主侧 C API 的关键差别：

- 宿主侧 C API 跑在**宿主进程**，异常穿出 = 宿主的用户程序崩（用户还能看到错误）。
- 注入侧导出随 hook DLL 被 blackbone 注入到**目标进程**后由宿主 `MakeRemoteFunction` 远程调用，跑在**游戏进程**里。异常穿出 = `std::terminate` = **游戏直接消失**，宿主侧只看到一个 RPC 返回失败，完全对不上因果。

爆炸半径更大，而且和 `75d64bb` 那批「静默失败」是同一个反面：这次不是静默，是"炸得莫名其妙"。

### 处置

1. 新增 `libop/hook/ExportGuard.h`（header-only）：
   ```cpp
   template <typename Ret, typename Func>
   Ret guarded(const char *name, Ret fallback, Func &&func);
   ```
   双 catch（`std::exception` + `...`）+ `setlog` 留证 + 返回调用方指定的 fallback。口径与宿主侧的 `call_int` 一致。
2. 12 个导出逐个包上，fallback 取各函数"未生效"时的既有语义值（如 `SetInputLock` 未 Hook 时 `lock==0 ? 1 : 0`），**不改变原有返回语义**。
3. `tests/hook_export_guard_test.cpp`：4 条用例（正常透传 / std 异常 / 非 std 异常 / 非 long 返回类型）。
   - **判别力设计**：fallback 取 `7` 而不是 `0`。若断言用 `0`，"return fallback" 与 "return Ret{}" 两种实现结果相同 —— 假通过。
   - **反向验证**：把两处 `return fallback` 改成 `return Ret{}` → 3/4 FAIL，而"正常透传"仍 PASS（说明用例定位精确，不是整体崩）。

## 四、两个已知的统计口径差（留证）

| 差异 | 原因 | 影响 |
|---|---|---|
| 静态扫源 257 vs DLL 导出 256 | `OpRequestCaptureForTest` 等测试专用符号可能未进导出表，或某个 `OP_CALL` 函数被 `#if` 排除 | 不影响结论（两个方向都指向"护栏覆盖 ≥ 98%"） |
| 台账写"199 个导出" | 未计入 `OP_MOUSE_RET` / `OP_CV_FILE_RET` 两个宏批量生成的 29 个导出，且数字来源未注明 | 台账该行数字作废 |

## 五、判据与边界

- ✅ 覆盖判据：静态扫描（含宏展开）+ `dumpbin -exports` 交叉核对，两侧独立。
- ✅ 行为判据：`HookExportGuardTest.*` 4 条纯函数用例 + 反向验证成立（3/4 FAIL / 恢复 4/4 PASS）。
- ⚠️ **无真机判据**：注入侧导出的 `guarded` 包装在真实游戏进程内触发异常路径的端到端验证做不到 —— 现有 `dx_carrier` 载体不会抛异常。因此本项的保证是"护栏语义正确 + 已挂在全部 12 个导出上"，靠代码审查确认挂载完整性（`dumpbin` 12 个导出名 ↔ `HookExport.cpp` 12 个函数名逐一对齐）。
