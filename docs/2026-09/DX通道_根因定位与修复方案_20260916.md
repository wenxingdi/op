## 一、结论（三句话）

1. **DX 输入通道的代码本身是正确的** —— 修好依赖问题后，`dx` / `dx.win` 的输入**确实送达目标**（实测标题计数 move/down 递增）。
2. **它有两个独立的阻塞项**，任一不满足都无法使用：
   - **门槛 A（P0 缺陷）**：注入的 `op_c_api_x64.dll` 在目标进程里需要 `onnxruntime.dll`，否则**目标进程直接崩溃**。
   - **门槛 B（设计约束）**：目标进程必须已加载 `dinput8.dll`，否则整个输入绑定被拒绝。
3. **汽水音乐两条都不满足**（Chromium 应用，不加载 dinput8；目标目录也无 onnxruntime），所以它**不能**作为 dx 验证目标。验证请用 `dx_target.exe`（已交付）。

## 二、v1 的正确部分（保留）

注入的宿主模块是 `op_c_api_x64.dll`（`HookModule.h:10` `ResolveHookModuleName` 返回宿主自身名字）。

`dumpbin /dependents` 显示其**唯一非系统依赖是 `onnxruntime.dll`**（`libop/CMakeLists.txt:470-477` 隐式共享链接）。

修复前实测（BlueStacks 5，hwnd 656988 / pid 14988，管理员权限）：

```
input hook inject failed. pid=14988 hwnd=... status=0xC0000135
  dll=D:\AutoPro\op-master\op\bin\x64\op_c_api_x64.dll
```

`0xC0000135` = `STATUS_DLL_NOT_FOUND` → 注入阶段就失败 → 10/10 绑定全灭。
→ 据此已实施 **方案 A：`/DELAYLOAD:onnxruntime.dll`**（`libop/CMakeLists.txt`），PE 层已验证生效
（`onnxruntime` 从静态导入表移入延迟导入表，两个导出 DLL 均确认）。

## 三、v2 新发现：DELAYLOAD 只解决一半，故障转移成"目标进程崩溃"

### 3.1 症状

`/DELAYLOAD` 后重新绑定，**目标进程以 `0xC0000005`（ACCESS_VIOLATION）崩溃**：

```
场景 A: 首次即 dx
   绑定前      IsWindow=True   proc=ALIVE
   bind(normal, dx, dx) = 0
   绑定后      IsWindow=True   proc=EXITED(0xC0000005)   ← 目标进程死了
```

三个场景稳定复现，且 **`windows` 模式完全正常**（证明注入基础设施本身没问题）：

| display | mouse | keypad | bind | 目标进程 |
|---|---|---|---|---|
| normal | **dx** | normal | 0 | **CRASHED(0xC0000005)** |
| normal | normal | **dx** | 0 | **CRASHED(0xC0000005)** |
| normal | **dx** | **dx** | 0 | **CRASHED(0xC0000005)** |
| normal | **dx.dinput** | normal | 0 | **CRASHED(0xC0000005)** |
| normal | **windows** | windows | **1** | **ALIVE** |

### 3.2 唯一变量对照实验（决定性）

只改**目标 exe 所在目录里有没有 `onnxruntime.dll`**：

| 目标目录 | bind(normal, dx, dx) | 目标进程 |
|---|---|---|
| **无** onnxruntime.dll | 0 | **CRASHED(0xC0000005)** |
| **有** onnxruntime.dll | **1** | **ALIVE** ✅ |

**唯一变量，结果翻转 —— 根因闭环。**

### 3.3 完整故障链

```
bind(mouse="dx") → DxMouse::Bind → input_hook_client::Bind
  → blackbone 注入 op_c_api_x64.dll 到目标进程        (InputHookClient.cpp:40)
  → DLL 静态加载成功（DELAYLOAD 让 onnxruntime 不再阻塞加载）
  → 远程调用 SetInputHook → InputHook::setup        (HookExport.cpp:72 / InputHook.cpp:865)
  → setup 执行路径触碰 ONNX 相关符号
  → 延迟加载尝试从【目标进程】搜索 onnxruntime.dll → 找不到
  → 延迟加载失败 → 目标进程 0xC0000005 崩溃
```

**注**：v1 的失败模式（`0xC0000135`、目标不崩）与 v2 的失败模式（`0xC0000005`、目标崩）是同一根因的两个阶段 ——
DELAYLOAD 把"加载期失败"变成了"运行期失败"。

### 3.4 门槛 B 的代码依据（v1 已定位，保留）

`libop/hook/InputHook.cpp:883-890`：

```cpp
if (!hook_dinput()) {
    // P1-9: 不再谎报成功——DirectInput 通道完全装不上（目标进程无 dinput 设备可挂）
    // 时中止本次输入绑定，让宿主 Bind 显性失败，避免"绑定成功但 GetDeviceState 静默全失效"。
    setlog("input hook dinput setup failed, abort input bind");
    release();
    return 0;
}
```

`load_dinput_vtables()`（`:366-372`）在 `ResolveApi("dinput8.dll", "DirectInput8Create")` 为空时返回 false。
→ **目标不加载 dinput8.dll 就整体拒绝**，连不依赖 DirectInput 的 `dx.raw` / `dx.win` 一起被牵连。

## 四、端到端可用性验证（修复依赖后）

目标目录放入 onnxruntime.dll，绑定后实际发送 `MoveTo(客户区中心)` + `LeftClick`，
读 `dx_target.exe` 窗口标题上的输入计数：

| mouse / keypad | bind | 发送前 | 发送后 | 送达 | 进程 |
|---|---|---|---|---|---|
| `dx` / `dx` | 1 | move=0 down=0 | **move=2 down=1 up=1** | **YES** | ALIVE |
| `dx.win` / `dx.win` | 1 | move=0 down=0 | **move=1 down=1 up=1** | **YES** | ALIVE |
| `dx.raw` / `dx.raw` | 1 | move=0 down=0 | move=0 down=0 | NO（**预期**） | ALIVE |
| `dx.dinput` / `dx.dinput` | 1 | move=0 down=0 | move=0 down=0 | NO（**预期**） | ALIVE |

- `dx` / `dx.win` = **通道真实可用** ✅
- `dx.raw` / `dx.dinput` 显示 NO 是**正确行为**：`dx_target` 既不读 DirectInput 设备也不调 `GetRawInputData`，
  而 dx 通道的语义是"hook 目标的读取 API"，目标不读就收不到。**这不是缺陷。**

> **结论：DX 输入通道不是"没实现"也不是"坏的"，而是被依赖问题与 dinput8 门槛挡在门外。**

## 五、修复方案

### 5.1 门槛 A（P0）—— ✅ 已按 A1 修复并验证（提交 `c4420ae`）

| 方案 | 做法 | 改动量 | 结论 |
|---|---|---|---|
| **✅ A1 延迟加载失败钩子（已采用）** | 在 hook DLL 内实现 `__pfnDliFailureHook2`；`dliFailLoadLib` 时用**本模块所在目录（op 安装目录）**的绝对路径 + `LOAD_WITH_ALTERED_SEARCH_PATH` 兜底 | 新增 1 文件（~110 行）+ CMake 2 行 | **采用**：不污染目标进程；标准做法；当日可验 |
| A2 注入时带依赖 | 注入前把 onnxruntime.dll 写进目标进程 / 远程 `SetDllDirectory` 指向 op 目录 | 中等 | **弃**：会改动目标进程搜索路径；且**对延迟加载无效**（搜索目录在注入后立即恢复，而延迟加载发生在运行期，见 §二/§三） |
| A3 拆轻量 hook DLL | 把 hook 能力单独编成不含 ONNX 的 DLL | 新增构建目标 | **弃**（按「够用」总原则）：架构最正解但工作量最大，收益不抵成本 |

**实施要点**（`libop/hook/DliFailureHook.cpp`）：

1. `delayimp.h` 默认把 `__pfnDliFailureHook2` 声明为 **`const`**（只读段），覆写必须**先** `#define DELAYIMP_INSECURE_WRITABLE_HOOKS`；
2. 实测**无 LNK2005** —— delayimp.lib 内的默认钩子是弱符号，可被用户强定义覆盖；
3. 只处理 `dliFailLoadLib` 且只认 `onnxruntime.dll`，**其余一切不干预**（保持默认行为）；
4. 两个 `/DELAYLOAD` 目标（`op_x64` / `op_c_api_x64`）**各编入一份**，故显式列入 `OP_COM_SOURCES` / `OP_C_API_SOURCES` —— 静态库成员若无符号引用不会被拉入，会导致钩子静默失效；
5. 钩子内**不调 `setlog`**（崩溃路径上的最后兜底不能再依赖任何运行时设施），仅 `OutputDebugStringW` 留痕。

**验证结果（真机，自控目标 `dx_target.exe` 置于不含 onnxruntime 的目录 —— 正是门槛 A 场景）**：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 绑定矩阵（10 组 dx 后缀组合） | bind=0 **且目标进程崩溃** `0xC0000005` | **10/10 bind=1，进程存活** ✅ |
| 端到端 `MoveTo` + `LeftClick` | 无法进行（进程已崩） | **move=1 down=1 up=1** ✅ |
| 端到端 `KeyPress(F1)` | 无法进行 | **key=1** ✅ |
| 目标进程 | CRASHED | ALIVE，全程存活 ✅ |

**回归**：`op_test` 197 用例 → **155 PASS / 35 SKIP / 7 FAILED**。其中 WGC 6 项经 **A/B 判别**（换回修复前 DLL 跑同一 `--gtest_filter=WgcTest.*` → 同样 6 FAILED + 同样 `WgcCapture::Init SEH fault 0xC0000005`）确认为**本机既有 WGC 环境问题**（首例 SEH 后熔断连带），与本次改动无因果；另 1 项为已知 `MouseKeyTest.WaitKey` 环境失败。**零回归。**

### 5.2 门槛 B（⏸ 按「够用」总原则降级为文档化，暂不实施）

现状"dinput 装不上就整体失败"是 P1-9 为消除"静默失效"而引入的，逻辑正当，但误伤面过大。
建议改为**按需判定**：仅当期望启用的通道包含 DirectInput 时才要求 `hook_dinput()` 成功；
`dx.win` / `dx.raw` 单独使用时不应被 dinput8 门槛拦截。

**注意**：`InputHook::setup` 在 `:878` 把 `m_dxAttrs = DX_ATTR_ALL` 重置，
而通道掩码是**绑定之后**才由 `SetDxAttr` 下发的 —— 即 **setup 时并不知道用户想要哪些通道**。
若要按需判定，需要把期望掩码一路传进 `SetInputHook`（`HookExport.cpp:72` 目前第二个参数 `int` 被忽略）。

**结论（2026-09-16 拍板）**：这是**增强**而非**必需** —— 目标不加载 `dinput8.dll` 时 dx 通道本就无设备可 hook，属**设计约束**而非缺陷。按「以满足够用为主」总原则**降级为文档化，不实施**。若后续出现真实使用场景（例如某目标只支持 `dx.win`），再单独排期。
