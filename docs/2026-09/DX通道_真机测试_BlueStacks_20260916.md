## 四、第二轮：送达验证 —— 判据的三次迭代（本轮最有价值的部分）

送达判据在真实目标上没有"窗口标题计数"这种现成读数，只能靠**截图差分**。整个过程暴露了三个坑，前两轮数据**全部作废**，记录如下以避坑。

### 4.1 第一轮判据（作废）：屏幕 DC BitBlt

- 做法：`BitBlt(屏幕DC → 客户区矩形)` + 逐像素 diff
- 结果：噪声 479–527，dx 与 windows 两组差异 45–944，**无法区分**
- **作废原因**：`SetForegroundWindow` 对蓝叠**无效**（无法抢占前台），抓到的实际是**遮挡窗口**（汽水音乐 PC 版）的画面 —— 所谓"噪声"是遮挡窗口自己的动画。抓图第一张就是证据：内容是汽水音乐 + 领星ERP，根本没有蓝叠。

### 4.2 第二轮修正：PrintWindow

- 改用 `PrintWindow(hwnd, hdc, 2 /*PW_RENDERFULLCONTENT*/)` —— 直接向窗口索取绘制内容，**不受遮挡影响**
- 结果：抓图完美（采样非黑像素 144/145），画面 = 蓝叠内运行的"汽水音乐 Android 版"
- **本底噪声 = 0**（连续 3 帧逐像素完全一致）→ 判据瞬间变得极干净

### 4.3 第三轮校正：分离 hover 与 click

- 零噪声下点击即得 359–1196 像素差异，初判"点击送达"
- **但 `move_to` 的悬停高亮同样会造成差异** —— 必须分离：

| 组 | 点击目标 | 仅 move（悬停） | move 后 click 增量 |
|---|---|---|---|
| **DX** | 听书 tab | 483 | **703** |
| **DX** | 推荐 tab | 808 | **715** |
| WINDOWS | 听书 tab | 483 | 491 |
| WINDOWS | 推荐 tab | 917 | 830 |

**解读**：在噪声恒为 0 的前提下，任何非零差异**只能**来自我方输入。因此
- 悬停 483–917 → **`move_to` 送达**（触发 Android 端 hover/高亮）
- 点击后再次变化 491–830 → **`left_click` 送达**（此前画面无任何其他变化源）
- DX 与 WINDOWS 数值同量级 → 两条通道在真实目标上行为一致

对照组提供关键排除：WINDOWS 组**首次**点击曾得到差异 **0**（零响应），证明"0 差异"确实会如实出现，非零即送达。

### 4.4 未达成项（如实记录）

试图取得"页面级切换"的大信号（数万像素）**全部失败**：点击 tab / 搜索框 / 蓝叠侧边栏按钮，增量始终停留在 0.2–0.6%。可能原因（未定论）：
1. 该 app 的三个 tab 可能是**同页内容筛选**而非页面跳转，视觉差异天然很小；
2. 150% DPI 下坐标定位误差（见 §五.1）导致点击未精确落在控件中心；
3. Android 的 tab 切换可能需要**触摸事件**语义，而非鼠标按下/抬起。

> 结论强度因此封顶为"输入确已送达被消费"，未能升级为"驱动了完整业务流程"。

## 五、副产品发现（对后续工作有直接影响）

### 5.1 🔴 DPI 缩放：OP 坐标是物理像素，Win32 默认是逻辑像素

| 取法 | 结果 |
|---|---|
| `op.get_client_rect()` | **(450,120,890,861) → 440×741** |
| `GetClientRect()`（进程非 DPI-aware） | **293×494** |

两者之比恰为 **1.500** = 屏幕 150% DPI。OP 是 DPI-aware 的（物理像素），而普通 Python/Win32 进程默认被 DPI 虚拟化（逻辑像素）。

**影响**：跨这两套坐标传值时若不换算，落点会偏移 1.5 倍（本轮前期的坐标偏差即源于此）。**修正办法**：脚本开头调用 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2 /* -4 */)`，两套坐标即统一。
**注意**：非 DPI-aware 时连 `PrintWindow` 抓到的图都是虚拟化尺寸，内容与物理图不一致，会导致元素定位错误。

### 5.2 ~~🔴 OP Capture 对蓝叠全线失败~~ → **❌ 已推翻（2026-09-16 晚复核）**

> **更正**：本条**作废**。当轮 8 组全 `False` 是**调用错误（输出路径无扩展名）+ 窗口被最小化**两个因素叠加的假象，
> **不是**蓝叠渲染方式导致抓屏不可用。复核后真实结果：除 `dx` 显示模式外，`normal/gdi/gdi2/dx2/opengl/normal.dxgi/normal.auto`
> 在蓝叠上 `capture=True` 且文件内容正确（含 BlueStacks 5 标题栏与 Android 画面）。
> 完整复核与真实矩阵见《`Capture_排查与更正_20260916.md`》。

**当轮数据与复核后真因对照**

| display | mouse | 当轮 bind/capture | 复核后 bind/capture | 当轮归因 | 复核后真因 |
|---|---|---|---|---|---|
| normal | normal / dx | True / **False** | True / **True** | 目标硬件加速导致抓屏不可用 | 输出路径无扩展名（`CImage::Save` 靠扩展名查 GDI+ 编码器） |
| gdi / gdi2 / dx2 | dx | True / **False** | True / **True** | 同上 | 同上 |
| **dx** | dx | True / **False** | True / **False** | 同上 | **真因**：蓝叠是 Qt/OpenGL 渲染，DX Present 无帧 → HookCapture 取不到帧（`dx` 显示模式独有） |
| dxgi | dx | **False** / — | True / **True** | 归因不明 | **时序敏感**：窗口刚移动/最小化后立即绑定会偶发失败，多轮实测可稳定成功 |

**新增的真实约束**（原"能力缺口"不成立，但以下三条成立）：

1. **`dx` **显示模式**在蓝叠上恒不可用** → 该绑定下 `capture`/`find_color`/`find_color_ex`/`get_color` 全部静默失效
   （`find_color` 返回 `(0,-1,-1)`、`get_color` 返回 `000000`）。蓝叠应选 `normal`/`dx2`/`opengl`。
   —— 注意与 **dx 输入通道**（mouse/keypad 传 `dx`）无关，后者在蓝叠上工作正常。
2. **`capture` 失败是静默的**（无日志、无异常）：三个触发条件已验证 —— ①路径无扩展名 ②窗口最小化 ③`dx` 显示模式。
3. **未绑定时 `check_bind()` 会自动回退绑定桌面窗口**（`BindingSession.cpp:590-604`）→ 绑定失败后 `capture` 仍返回 `True`，
   但截到的是**整个桌面**而非目标窗口，会掩盖"忘绑定/绑定失败"。

### 5.3 dx 模式不驱动系统光标（设计语义，非缺陷）

把系统光标停到 (1400,900) 后 `move_to(80,140)`：

| mouse/keypad | 光标变化 | 命中目标点 |
|---|---|---|
| normal/normal | (1400,900) → **(680,320)** | ✅ 是 |
| dx/dx | (1400,900) → **(1400,900)** | — 纹丝不动 |
| windows/windows | → (1957,1465) | 否（坐标系不同） |
| dx.win/windows | → (966,411) | 否 |

⇒ **`dx` 是真后台输入**：设备级注入、不碰系统光标，适合多开/挂机；`normal` 走真实光标。

### 5.4 windows 模式在无焦点窗口上首击可能丢失

WINDOWS 组第一次点击差异为 **0**（未送达），第二次起正常。而蓝叠窗口当时**始终不是前台窗口**（`SetForegroundWindow` 被系统拒绝）。dx 组在同样条件下点击**每次都有响应** ⇒ 无焦点场景下 dx 通道更可靠。
