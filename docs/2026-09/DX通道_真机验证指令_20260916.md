# DX 输入通道 · 真机验证指令

> 交付日期：2026-09-16 ｜ 对应总纲：`OP_Master_功能分类与优化路线_20260916.md` 批 2（鼠标输入域）
> 配套工具：`op/scripts/dx_probe.py`（新）

> **⚠️ 2026-09-16 状态更新：验证目前被阻塞，请先读这条。**
> 真机实测（BlueStacks 5，管理员权限）显示 DX 三通道 **10/10 绑定失败**，根因已闭环定位并经 A/B 对照实验确认：
> 注入的 `op_c_api_x64.dll` 隐式依赖 `onnxruntime.dll`，目标进程解析不到该依赖 →
> `STATUS_DLL_NOT_FOUND (0xC0000135)`，在**注入阶段**就失败。
> 完整证据链与修复方案见 **`DX通道_根因定位与修复方案_20260916.md`**。
> **依赖问题修复前，第三、四节不会产出有效数据。** 应急验证可临时把
> `onnxruntime.dll` + `onnxruntime_providers_shared.dll` 拷进目标 exe 目录（实验已证有效，
> 但会污染目标目录，用完务必删除）。
>
> 另有一个**设计约束**需提前知道：目标进程必须已加载 `dinput8.dll`，dx 通道才可能建立
> （hook 的对象就是 `dinput8` 的导出）。纯 GDI/Qt 程序通常不加载它。

## 一、先说为什么必须真机（这步不能省）

DX 三通道（DirectInput / RawInput / 窗口消息）的绑定本质是 **`input_hook_client::Bind()` 跨进程注入 hook**：

```
BindWindow(hwnd, "normal", "dx", ...)
   └─ DxMouse::Bind            (libop/input/mouse/DxMouse.cpp:20)
        └─ input_hook_client::Bind(hwnd, mode)     ← 注入失败则返回 0
```

而单元测试用的是**自建窗口**（`tests/mouse_keyboard_test.cpp:723` `MouseEventWindow`），它**从不创建 DirectInput/RawInput 设备**：

```cpp
op.BindWindow((long)(intptr_t)window.hwnd, L"normal", L"dx", L"windows", 0, &ret);
if (ret != 1) { GTEST_SKIP() << "DX mouse bind unavailable on current environment"; }
```

→ **绑定阶段就返回 0，测试根本没走到发送环节。** 这就是 13 条 DX 用例长期 SKIP 的根因，不是"偶发环境问题"。

**结论：gtest 只能证明"契约/参数校验正确"，三通道是否真的送达目标，只能拿真实目标（游戏/模拟器）验。**

**不要**拿微信、文档、浏览器当目标——它们不走 DirectInput，必然验不出东西。

### B2. 跑绑定矩阵（不点击，最安全）

### B3. 跑完整验证（会真实操作窗口）

```powershell
& "D:\Program Files\Python312\python.exe" scripts\dx_probe.py --hwnd 656988
```

> 交互提问看不到时（个别终端会吞提示），Ctrl+C 退出，改跑 B2；或先执行 `$OutputEncoding=[Console]::OutputEncoding=[Text.Encoding]::UTF8` 再重跑。

两段：
- **第一段 bind-matrix**：10 组绑定组合的返回值，以及成功组合下的 `MoveTo / LeftClick / KeyPress(F1)` 返回值；
- **第二段 channel-matrix**：对首个绑定成功的组合，依次执行

  | 步骤 | 操作 | 你要看的 |
  |---|---|---|
  | 1 | 默认全开（7） | 目标响应吗 |
  | 2 | `SetDxAttr(4,0)` 仅关窗口消息 | 关掉后是否**立刻**失去响应 |
  | 3 | `SetDxAttr(0,7)` 恢复全开 | 响应是否恢复 |
  | 4 | `SetDxAttr(2,0)` 仅关 RawInput | 同上 |
  | 5 | 恢复全开 | |
  | 6 | `SetDxAttr(1,0)` 仅关 DirectInput | 同上 |
  | 7 | 恢复全开 | |

  每步脚本会发一次 `MoveTo(客户区中心)` + `LeftClick`，然后**在控制台问你 `目标有反应吗? (y/n/s)`**，照实回答即可。

结果自动写入 `op/dx_probe_<时间戳>.md`。

**安全提示**：`--no-click` 可跳过所有点击/按键；脚本点击点固定为**客户区中心 + F1**，请用能接受偶然误操作的窗口（模拟器/游戏），不要对着重要文档跑。

| 现象 | 指向 | 下一步 |
|---|---|---|
| 10 组 Bind 全 ret=0 | 注入失败：权限 / 目标位数 / 反作弊 | 查 setlog 三元组，确认是 mouse 还是 keypad ret=0 |

| `dx.dinput` 失败、`dx.win` 成功 | 目标未用 DirectInput（正常，非缺陷） | 换真有 DInput 的目标 |
| 关某通道后目标立即失效 | 该通道是主驱动通路 ✓ 设计成立 | 记入 `DX_INPUT_CHANNEL_REPORT.md` |
| 关掉全部三通道后**仍**响应 | 输入的其实不是 dx 通道（走了普通 SendMessage） | 高优先缺陷，回查 DxMouse 发送路径 |
| `SetDxAttr` 返回 1 但 `GetDxAttr` 不变 | 掩码未生效，且 `BindingSession.cpp:322` 只写日志不报错 | 属"静默降级"缺陷，记入绑定域报告 |

## 七、已知会被这轮验证顺带覆盖的项

`SetDxAttr` 参数校验（已有专测 `DxAttrDefaultsToAllChannelsAndValidatesArguments`）之外，
本轮还会实测 **多实例边界** 的疑点：`hook/InputHook.h:53` 的通道掩码是**进程内全局** `static std::atomic<LONG>`，
而 `_dx_attr` 是 per-Op。若你要顺带验这个，加一步：

```powershell
# 同进程内创建两个 op 实例，绑同一目标但设不同通道，看是否互踩
python -c "from op import Op; ..."
```

这个需要单独脚本，等主线验完再决定要不要做。
