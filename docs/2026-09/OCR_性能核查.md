# OCR 耗时核查报告（2026-09-09，doc2 不入库）

> 背景：B 组真机 `ocr_from_file` 42.6ms（det+rec 全链）高于 9-13ms 纯 rec 目标。
> 目的：量化耗时构成，判断瓶颈归属与目标可达性。**纯核查，未改任何引擎代码。**

## 1. 复现与方法

- 载体：`doc2/smoke_ocr_region.bmp`（620×160 32bpp，单行文本 "许愿树[320,-778]12345"，B 组同图）
- 通道：Python ctypes → `op_c_api_x64.dll`（build/nmake-x64-Release/libop，含内置 PP-OCRv4 det+rec）→ `ocr_from_file`（读文件→颜色二值化→det→按框 rec）
- 剖析脚本：`doc2/ocr_profile.py`（复现+行数）、`ocr_profile2.py`（多分辨率 det 占比 + threads）、`ocr_profile3.py`（组间漂移验证）

## 2. 实测数据

| 测量 | 结果 | 说明 |
|---|---|---|
| ocr_from_file 全链（冷净进程） | min 44.5 / avg 49.3ms | 与真机 42.6 同量级 ✓ |
| 返回行数 | 1 行 | 全链仅 1 次 rec（320×48） |
| rec 免 det 对照（autoocr_line 桌面 620×160） | avg 32.6ms | 含桌面截图+投影切行+rec；**桌面无字也整块 rec** |
| threads=4 vs =1（det+rec 全链） | 133 vs 179ms | 4 线程省 ~46ms（25%），多线程有效 |
| det 缩放扫描（x1→x0.25，det 张量 160×608→32×160） | 全链 130→104ms | 相对趋势：det 缩小省 ~26ms（20%），**恒有 ~100ms+ 底价** |

## 3. 关键发现

1. **本机性能对运行环境极敏感（3 倍波动）**：同二进制同配置跨进程 49ms（冷净）vs 130-150ms（后续）。系统画像：i5-13400（10C16T，P/E 核）+ **雷电模拟器 HD-Player 常驻** + SearchIndexer 高占用。49 vs 130 差异经冷却 60s 复测排除降频假说，归因于共存负载与 P/E 核调度波动。→ **9-13ms 目标在本机日常负载下不可达也不可复现**，标定须在低负载环境。
2. **单行场景 1 次 rec，全链 49ms 的构成 ≠ "rec 达标 det 拖后腿"**：det 缩放实验显示 det 段仅贡献 ~1/5-1/4；autoocr_line 免 det 路径（纯 rec 语义）实测仍 33ms（含截图）。**rec 单行本机实际成本可能就 ≥20ms**（若截图/切行 5ms、rec 剩 ~25ms），注释中"4 线程 320×48 ≈ 10-15ms"在 i5-13400 上未复现。
3. **引擎内部分段无法外部定论**：C-API 无 rec-only 文件入口（autoocr_line 是窗口接口），det/rec/二值化/后处理各自耗时只能代码级 QPC 计时才能精确归属。

## 4. 结论

- **9-13ms 目标需重新审视**：它是 rec 单行推理的理论目标，本机实测（含前置）明显高于此；且受共存进程影响波动 3 倍。性能验收应定"低负载环境冷测基线"而非绝对值。
- **优化前必须先做引擎内分段计时**（det_run / db_postprocess / 每行 crop+pca+rec_image 各自 QPC），否则 49ms 归属不明，盲改 det 或 rec 都可能无效。
- 可选优化方向（待分段计时确认热点后再评估）：① rec 量化(INT8)/动态宽减少 320 固定 pad 浪费（短行如本例实际内容 ~600×35 → 行宽比超 320 cap，pad 收益有限，须按真实行宽分布评估）② det 限宽 960 对 <960 宽输入不缩放→单行场景可考虑跳过 det 的 API 级快路径（已有 autoocr_line 但它是窗口接口）③ 纯 rec 文件 API（`ocr_line_from_file` 类）既服务标定也服务场景。
