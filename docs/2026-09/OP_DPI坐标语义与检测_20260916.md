# OP 坐标语义与 DPI 检测（2026-09-16）

- 触发：BlueStacks 真机测试中发现"逻辑坐标 ×1.5 偏移"，需给出可复现的机制解释与落地检测
- 结论：**OP 一直会主动把宿主进程提升为 DPI 感知**（`OpContext.cpp`），这是**有意设计**（与类大漠一致：坐标统一为物理像素），
  但它**改变宿主进程的坐标语义**，且此前**无任何日志**——现已加检测日志（本轮落地）
- 证据等级：子进程隔离 A/B 实测 + 源码路径 + 日志实证
- 代码改动：**4 处纯日志（不改任何返回值/行为）**，详见 §5

---

## 1. 一句话结论

**加载 OP 会让宿主进程从 DPI-unaware 变成 DPI-aware，此后所有窗口/客户区坐标从"被系统虚拟化的缩放后值"变成"物理像素值"。**
若脚本混用了提升前取到的坐标，就会整体偏移一个缩放比（150% 缩放 → 偏 1.5 倍），现场表现是**"点了但没点中"**。

---

## 2. 铁证：子进程隔离 A/B

同一个 HWND（BlueStacks 5，屏幕 150% 缩放），只改变"是否加载 OP"：

| 阶段 | 线程 DPI 语境 | `GetWindowRect` | `GetClientRect` |
|---|---|---|---|
| 未加载 OP | `UNAWARE` | `(53, 40, 346, 534)` | `293 × 494` |
| 加载 OP 之后 | **`SYSTEM_AWARE`** | **`(80, 60, 520, 801)`** | **`440 × 741`** |

`53×1.5 = 79.5 → 80`、`40×1.5 = 60`、`346×1.5 = 519 → 520`、`534×1.5 = 801` —— **逐项精确 ×1.5**。

> 该实验用独立子进程分别运行（探针脚本同一份，仅环境变量区分是否 import op），
> 排除了"同进程内多次测量互相污染"的可能。

**关键推论**：同一进程内，OP 的 `get_client_rect` 与系统 `GetClientRect` **是一致的**（都是物理像素）。
偏移只发生在**跨语境比较**时 —— 例如脚本在 `import op` 之前就缓存了 Win32 坐标、或同一套坐标要同时喂给 OP 和一个未加载 OP 的进程。

## 3. 机制：谁改的

```cpp
// libop/op/OpContext.cpp:32-34（原始代码）
op::internal::OpContext::OpContext(int client_id) : id(client_id) {
    // 将进程默认 DPI 感知设置为系统 DPI 感知
    ::SetProcessDPIAware();
```

| 项 | 说明 |
|---|---|
| 触发时机 | **每次构造 `OpContext`**（即用户每次 `new Op()` / `Op()`） |
| 实际生效 | 仅**首次**（`SetProcessDPIAware` 是进程级一次性 API；已感知时调用失败且不改变现状） |
| 覆盖范围 | 进程级。若宿主 EXE 清单已声明 DPI 感知（如 PerMonitorV2），该调用**无效**，OP 将沿用宿主声明 |
| 等价级别 | 老 API，等价 `SYSTEM_AWARE`（区别于 PerMonitorV2：多屏不同 DPI 时行为不同） |

**设计意图**（保留原样，未改）：与类大漠一致，让坐标统一为物理像素，避免缩放环境下的虚拟化抖动。
**问题只在于它无声** —— 使用者看到"坐标整体偏 1.5 倍"时，无从判断是绑定错、找色错还是 DPI 语义变了。

## 4. 检测方式（本轮新加）

`OpContext` 构造时记录一行，内容是**提升前后状态 + 系统 DPI + 缩放比**：

实测输出（150% 缩放本机）：

```
[2026/09/16 18:18:07.886]x64info: dpi: process is DPI-aware, system dpi=144 (scale 150%); window/client rects are physical pixels
```

首次提升（进程原本 unaware）时输出的是另一条：

```
dpi: process elevated from DPI-unaware to DPI-aware, system dpi=144 (scale 150%); window/client rects are physical pixels now
```

| 设计取舍 | 说明 |
|---|---|
| 为什么两条都打 | 提升只发生在**首个实例**上，而那时用户的日志通常还没打开（`set_show_error_msg` 需先有实例）。故后续实例继续记录**当前状态**，保证这条信息随时可取 |
| 为什么用老 API `IsProcessDPIAware` | 不需要 `_WIN32_WINNT` 版本宏、无编译期依赖；本用例只需 unaware/aware 二态 |
| 是否会刷日志 | 每次 `new Op()` 一行，正常用法下量极小；且 `setlog` 默认静默（`m_showErrorMsg = 0`），只有主动开日志才可见 |

**使用方式**：`op.set_show_error_msg(2)` → 日志落 `cwd/__op.log`（详见 `Capture_排查与更正_20260916.md` §8.5）。

## 6. 使用侧的正确姿势

| 场景 | 做法 |
|---|---|
| 脚本只在 OP 坐标系内工作 | **无需理会** —— OP 内部自洽（客户端物理像素） |
| 脚本同时用 Win32 取坐标喂给 OP | **同一进程内两者一致**（OP 加载后都返回物理像素）；不要跨进程/跨语境比较 |
| 需要与其它工具（未加载 OP）对齐坐标 | 显式统一：在脚本开头 `SetProcessDpiAwarenessContext(-4)`，或按检测日志里的缩放比手工换算 |
| 排查"点了没中" | ①先开日志 ②看有没有 `dpi:` 行记下缩放比 ③确认取坐标与用坐标在同一 DPI 语境 |
