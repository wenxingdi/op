# UWP 窗口（系统计算器）截图全黑根因分析

- 日期：2026-09-19
- 触发：真机验收中"系统自带计算器绑定截图异常"，用户追问根因
- 结论：**不是绑定失败，是捕获通道对 UWP（DirectComposition）窗口整体无效**——5 条通道 4 死 1 错
- 环境：Windows 10 build 18363（1909）/ i5-13400 / 4 个虚拟显示驱动
- 复现工具：`workbench/probes/uwp_capture_probe.py`、`workbench/probes/win32_control_probe.py`

> **后续复查（同日）**：本问题**不止 UWP**。对 7 个已打开 App 做矩阵体检后发现，
> **全部 GPU 合成窗口**（Chromium / Electron：WorkBuddy、紫鸟、汽水音乐）的 `gdi`/`dx2`
> 同样全黑，根因相同（画面不进 GDI 表面）；而 `normal` 依赖 Z 序、被遮挡即截到遮挡物。
> 完整矩阵与优化建议见 `多目标绑定截图能力矩阵_20260919.md`。
> 该文件中的 §5 修复方案已被后续实测**扩展到覆盖全部 4 类目标**。

---

## 1. 一句话结论

系统计算器是 **UWP 应用**（窗口类名 `ApplicationFrameWindow`，内容由 `dcomp.dll` DirectComposition 合成），
它的画面**从不写入窗口的 GDI 表面**。而 op 的 `gdi` / `dx2` 两个模式取画面用的是
`PrintWindow(hwnd, hdc, 0)`（flags=0，走 `WM_PRINTCLIENT` 老路），对这类窗口**恒定返回全黑**。
唯一官方可行的 WGC 通道在本机因虚拟显示器驱动崩溃。**`normal` 模式看似可用，实则截到的是遮挡物。**

---

## 2. 实测证据

### 2.1 同机对照实验（决定性）

同一台机器、同一段代码、只换目标窗口：

| 捕获方式 | 计算器（UWP） | 记事本（Win32） |
|---|---|---|
| `GetDC(NULL)` + BitBlt（= op `normal`） | 有内容<sup>注</sup> | 有内容 ✓ |
| `GetDC(hwnd)` + BitBlt | **全黑 ✗**（唯一色 1 / 亮度 0） | 有内容 ✓ |
| `PrintWindow(hwnd, hdc, 0)`（= op `gdi`/`dx2`） | **全黑 ✗**（唯一色 1 / 亮度 0） | 有内容 ✓（亮度 213.8 / 44 色） |
| `PrintWindow(hwnd, hdc, 0x2)`<br>`PW_RENDERFULLCONTENT` | **有内容 ✓**（亮度 211.1 / 27 色） | 有内容 ✓ |

> 注：计算器那一格"有内容"是**假阳性**——截到的是覆盖在它上面的 Edge / WorkBuddy 窗口。

**关键**：`PrintWindow(hwnd, hdc, 0)` 对记事本**有效**、对计算器**全黑**。
同一 API、同一机器，唯一变量是目标窗口类型 → 问题在**目标窗口的渲染机制**，不在 op 的调用姿势。

### 2.2 遮挡验证（解释 `normal` 为什么也是错的）

对计算器窗口矩形内 4 个点做 `WindowFromPoint`：

| 采样点 | 屏幕坐标 | 实际归属窗口 |
|---|---|---|
| 中心 | (516, 707) | Edge — `数据看板 - 领星ERP广告` |
| 左上+20 | (366, 453) | Edge — 同上 |
| 上边缘+5 | (516, 438) | Edge — 同上 |
| 右下-40 | (647, 942) | WorkBuddy |
| 计算器是否前台 | — | **否** |

**4/4 个点都不属于计算器**。桌面 DC 取的是"屏幕上看着是什么"，被遮挡就取到遮挡物。
落盘图 `workbench/real_machine/uwp_probe/uwp_ApplicationFrameWind_desktop.png` 显示的是
领星ERP广告看板的"广告花费"圆环，而非计算器界面——**`normal` 模式对该窗口输出的是错图**。

### 2.3 计算器进程加载的图形模块

| 进程 | 相关模块 | opengl32.dll |
|---|---|---|
| `ApplicationFrameHost.exe` (pid 21348) | `dxgi` `d3d11` `dwmapi` **`dcomp`** `D3D10Warp` | ❌ 无 |
| `Calculator.exe` (pid 33236) | **`dcomp`** `dxgi` `d3d11` | ❌ 无 |

- 有 `dcomp.dll` → 走 **DirectComposition** 提交视觉树给 DWM，**不经 `IDXGISwapChain::Present`**
- 无 `opengl32.dll` → opengl 模式的 hook（`wglSwapBuffers`/`SwapBuffers`）**无目标可挂**

## 3. 逐通道根因

| op 模式 | 实现位置 | 实测 | 根因 |
|---|---|---|---|
| `normal` | `GdiCapture.cpp:86` `GetDC(NULL)` + `:223` `BitBlt` | **错图**（截到遮挡物） | 桌面 DC 只能拿"屏幕可见像素"；窗口非前台/被遮挡即失效 |
| `gdi` | `GdiCapture.cpp:298` `PrintWindow(hwnd, hdc, **0**)` | **全黑** | UWP 不响应 `WM_PRINTCLIENT`；画面在 DWM 合成层，不在窗口 GDI 表面 |
| `dx2` | `GdiCapture.cpp:304` `UpdateWindow`+`PrintWindow(hwnd, hdc, **0**)` | **全黑**<br>（与 `gdi` 逐像素相同） | 与 `gdi` 同函数同调用，仅多一次 `UpdateWindow`；**"dx2" 在窗口捕获路径上是空头衔**，并未走 `DxgiCapture::DuplicateOutput` |
| `opengl` | `HookCapture.cpp:149/286` 注入 hook `SwapBuffers` | **无产物** | 计算器不加载 opengl32.dll，无 Present 调用可 hook（`HookCapture.cpp:362` 注释已述该机制） |
| `normal.wgc` | `WgcCapture.cpp` `Windows.Graphics.Capture` | **崩溃**<br>`Init SEH 0xC0000005` | 本机 4 个虚拟显示驱动（向日葵 OrayIddDriver / GameViewer / USB Mobile Monitor ×2）；WGC 是微软**唯一官方支持 UWP 截图**的 API，本机恰好不可用 |

补充：`RDT_GDI2`（`gdi2`）经代码确认走**同一个 else 分支**（`GdiCapture.cpp:300`），同样是 `PrintWindow(hwnd,hdc,0)`。
`PW_RENDERFULLCONTENT` 在 op 全仓库 **零使用**（已 grep 确认），即从未尝试过该 flags。

## 4. 为什么之前的验收没发现

`PrintWindow` 对 UWP 返回 **1（成功）**，`Capture` 也返回 **1**，落盘 BMP 尺寸正确、字节数正常。
但内容是**纯黑**。上一次验收以 `ret=1` 为判据，因此误判"三模式全通过"。

> **教训**：截图类接口的 `ret=1` 只表示"调用没报错"，**不等于截到了内容**。
> 判据必须包含像素级校验（非黑占比 / 唯一色数 / 与已知底纹比对）。

本次已用像素统计补齐，产物矩阵见 §2.1。

## 5. 修复方案

### 方案 A（推荐，风险低）：为 GDI 系模式补 `PW_RENDERFULLCONTENT` —— ✅ 已落地（2026-09-19）

在 `GdiCapture.cpp` 的 `PrintWindow` 调用处改为先带 flags、内容为空则退回原调用：

```cpp
// 伪代码
if (!::PrintWindow(_hwnd, _hmdc, PW_RENDERFULLCONTENT))   // 0x2
    ::PrintWindow(_hwnd, _hmdc, 0);                        // 兼容旧行为
```

实测该 flags 对计算器有效（§2.1 第 4 行），且能**穿透遮挡**取到窗口真实内容。

**实际落地形态**（与本文最初建议不同，见 `多目标绑定截图能力矩阵_20260919.md` §7）：
- 采纳**直接改现有 `gdi` / `gdi2` / `dx2`**（不新增 `gdi.fc` 模式）——`normal` 系已经承担"屏幕所见"语义，两者互补而非冲突
- 空判定按**整幅全黑**触发（`PrintWindow` 失败或全黑均回退），非"返回值为假"
- `dx2` 实际走 `BitBlt(窗口 DC)` 而非 `PrintWindow`，故额外为它加了「BitBlt 全黑 → 回退到 PrintWindow 分支」链路

**风险**（落地后复核）：
- 语义变化——`gdi` 从"仅客户区 GDI 表面"变成"窗口真实内容"（穿透遮挡、不依赖 Z 序）：
  已用真机 7 目标 × 4 模式矩阵复跑确认零劣化，且**裁剪偏移语义未变**（位图仍是整窗坐标系）；
- Win 8.1 以下无此 flags —— 已确认本项目最低支持 **Win10**
- 端到端成功用例 —— 已补 `tests/capture_mode_test.cpp`（2 例，含非黑与颜色断言、遮挡穿透断言）


### 方案 B（治本，风险中）：修复 WGC 通道

WGC 是微软官方为 UWP / DirectComposition 设计的截图 API，是唯一能覆盖
"UWP + 遮挡 + 最小化 + 硬件加速视频"全部场景的通道。
当前阻塞点是 `WgcCapture::Init` 的 `0xC0000005`——需定位是虚拟显示器驱动的
`IDXGIOutput` 枚举问题，还是在多适配器环境下选错输出。修好后 UWP 由 `normal.wgc` 覆盖。

### 方案 C（兜底，风险低）：文档化能力矩阵

若短期不动代码，至少在文档中明确：

| 目标类型 | 推荐模式 |
|---|---|
| 经典 Win32（GDI 绘制） | `normal` / `gdi` / `dx2` 均可 |
| UWP / DirectComposition | **当前无可用模式**；`normal` 需保证窗口前台且无遮挡 |
| DX 全屏 / 独占游戏 | `dx.d3d11` / `dx.d3d12`（本机 BlueStacks 已验证） |
| OpenGL 应用 | `opengl` |

## 6. 复现工具

```bash
# UWP 目标探针（4 种方式对照 + 可选落盘）
python workbench/probes/uwp_capture_probe.py 计算器 --save workbench/real_machine/uwp_probe

# Win32 对照组（内置启停记事本）
python workbench/probes/win32_control_probe.py
```

输出含义：`PrintWindow`/`BitBlt` 的返回值 + 非黑像素占比 + 平均亮度 + 唯一色数。
**唯一色 ≤ 1 且亮度 = 0 判为全黑**（注意：唯一色 ≤ 1 但亮度正常是纯色窗口，属正常）。

---

## 7. 决策结果（2026-09-19）

1. `PW_RENDERFULLCONTENT` —— **直接改进现有 `gdi`/`gdi2`/`dx2`**，不新增模式；已落地并通过真机矩阵 + 全量回归验证。
2. WGC 崩溃（方案 B）—— **不立项**；`normal` 系"屏幕所见"、非最前窗口截到遮挡物属预期行为，只要每种目标有可用模式即可。
3. 最低支持 Windows 版本 —— **Win10 起**，无需运行时判断该 flags 可用性。

> 本机 4 个虚拟显示驱动（向日葵 OrayIddDriver / GameViewer / USB Mobile Monitor ×2）导致 WGC 不可用，属**环境性**限制；
> 若后续要在干净机器上验收 WGC，可复用 `workbench/probes/run_wgc_isolated.bat` 与 `WgcTest` 套件。
