# dx 靶子体系：双架构受控载体 + DirectInput 闭环 + 屏保路线（2026-09-29）

## 1. 要解决的问题

hook 注入有一条硬约束：**注入的 dll 位数必须匹配目标进程位数**（32 位进程只能加载 32 位 dll）。
在此之前的靶子状况是：

| 通道 | 靶子 | 问题 |
|---|---|---|
| x64 + D3D9 | `dx_carrier.exe --backend d3d9` | 可用 |
| x64 + DXGI | `dx_carrier.exe --backend d3d11` | 可用 |
| **x86 + D3D9** | 只有蜀门 `client.exe`（真实游戏） | 状态不可控：绑定时游戏停在哪个界面、模块加载到哪一步全看运气 |
| **x86 + DXGI** | 无 | 同上 |

于是「32 位 dx 通道是否可用」这个问题的答案被游戏可用性绑架——而这恰恰是 x86 注入修复后
最需要独立验证的一环。本轮把它解掉。

## 2. 结论（先看这个）

1. **x86 现在有了完全可控的 D3D9 / D3D11 靶子**，`dx/windows/windows`、`dx/dx/dx`、
   `dx.d3d11/windows/windows` 三条通道全部 bind=1 且像素四象限精确匹配。
2. **`dx/dx/dx` 返回 0 的根因被闭环定性**：目标进程未加载 `dinput8.dll`。同一载体加不加
   `--dinput` 即可让 bind 从 0 变 1——单一变量实验，蜀门上的旧结论得到独立确认。
3. **屏保 `Bubbles.scr /p <hwnd>` 可当免安装的第三方 D3D9 靶子**（实测 bind=1、uniq=2015）。
4. **第三方程序不等于好靶子**：`AJ绑定测试工具Ex.exe` 导入 d3d11 但窗口是 GDI、
   不产生 Present 帧 → 绑定成功也取不到画面。判据必须是**运行时行为**，不是导入表。

## 3. 新增能力

### 3.1 `build_dx_carrier.py --arch x86`

```bash
python scripts/build_dx_carrier.py                 # -> workbench/probes/dx_carrier.exe      (x64)
python scripts/build_dx_carrier.py --arch x86      # -> workbench/probes/dx_carrier_x86.exe    (x86)
```

实现要点：

- `build_dx_target.py:find_cl(arch="x64")` 支持 `bin/Hostx64/{x64,x86}/cl.exe`。
  两者都在 `Hostx64` 下，**同目录自带 link.exe**，所以不需要 `vcvars32.bat`，直接拼
  `INCLUDE`/`LIB`/`PATH` 即可交叉编译。
- x86 用 **`/MT` 静态 CRT**：载体是探针，自包含（不依赖目标机上是否有 x86 vcruntime）
  比省体积重要；x64 保持 `/MD` 与既有产物一致。
- 产物校验：PE `Machine` = `0x14C`（i386），导入表含 `d3d9.dll`。

### 3.2 载体 `--dinput`

```bash
dx_carrier_x86.exe --backend d3d9 --dinput --seconds 60 --report r.txt
```

加载 `dinput8.dll`，创建 `SysMouse`/`SysKeyboard` 设备（`DISCL_BACKGROUND | DISCL_NONEXCLUSIVE`），
并在每帧真的调用 `GetDeviceState`/`Poll`——**hook 只有被调用过才算可用，装上不算**。

默认**关闭**：不改变既有用例「可绑定/不可绑定」的预期。`--report` 文件新增 `dinput=` 字段，
测试侧可据此判断"该轮靶子是否具备 DirectInput 环境"。`tests/CMakeLists.txt` 同步补
`dinput8.lib dxguid.lib`。

## 4. 验证记录

探针：`workbench/_t_dx32_carrier.py`（起载体 → 读 report 拿 hwnd → 64 位宿主 bind → 采样四象限）。

| 靶子 | 模式 | bind | is_bind | 像素 |
|---|---|---|---|---|
| `dx_carrier_x86 --backend d3d9` | `dx/windows/windows` | 1 | 1 | TL=FF0000 TR=00FF00 BL=0000FF BR=FFFFFF ✅ |
| `dx_carrier_x86 --backend d3d9` | `dx/dx/dx` | **0** | 0 | —（无 dinput8，input 侧如实失败） |
| `dx_carrier_x86 --backend d3d9 --dinput` | `dx/dx/dx` | **1** | 1 | 四象限精确 ✅ |
| `dx_carrier_x86 --backend d3d11` | `dx.d3d11/windows/windows` | 1 | 1 | 四象限精确 ✅ |
| `dx_carrier.exe --backend d3d11`（x64 对照） | `dx.d3d11/windows/windows` | 1 | 1 | 四象限精确 ✅ |
| `dx_carrier.exe --backend d3d9 --dinput`（x64 对照） | `dx/dx/dx` | 1 | 1 | 四象限精确 ✅ |

四象限纯色的意义：能同时暴露**全黑 / 红蓝互换 / 原点偏移 / 尺寸错**四类取帧缺陷；
单色靶子只能测出"有没有画面"。

## 5. `dx/dx/dx` 返回 0：闭环定性

调用链：`BindWindowEx` → `InputHook::setup`（`libop/hook/InputHook.cpp:883`）→
`hook_dinput()` → `load_dinput_vtables()` → `ResolveApi("dinput8.dll", "DirectInput8Create")`。

`ResolveApi`（`libop/hook/ApiResolver.cpp`）**只做 `GetModuleHandleA`，不 LoadLibrary**。
目标进程没加载 `dinput8.dll` ⇒ 拿不到 `DirectInput8Create` ⇒ `hook_dinput()` 返回 false ⇒
按 P1-9「不再谎报成功」中止本次输入绑定并返回 0（RPC `status=0x0`，**不是崩溃**）。

单一变量实验（同一 x86 d3d9 载体、同一模式 `dx/dx/dx`）：

| 目标侧 `dinput8.dll` | bind |
|---|---|
| 未加载 | 0 |
| 已加载（`--dinput`） | 1 + 像素精确 |

⇒ 蜀门「版本检查」界面 `SetInputHook` 返回 0 的原因确认成立，**不是缺陷**。

## 6. 第三方程序怎么判（含反例）

判定顺序（贴 `workbench/_t_bind_any.py` 一条命令即出）：

1. **PE 位数** —— 决定走 32 位还是 64 位注入。
2. **静态导入表** —— 只说明「可能会用」，不能作为靶子资格。
3. **运行时模块**（`workbench/_t_mods.py`）—— `dx` 分支要求 `d3d9.dll` 已在；
   `dx.d3d11` 要求 `dxgi.dll`/`d3d11.dll` 已在；**input 侧 `dx` 还要求 `dinput8.dll`**。
4. **实际取帧** —— 绑定成功后连续多次 `OpGetScreenData`，全 ret=0 就是"不产生 Present 帧"。

反例（本轮实测）：`D:\GMPLUG\AJPlug\AJ绑定测试工具Ex.exe`

- x86，导入 `d3d11.dll` + `dxgi.dll`；运行时模块 91 个，确实加载了 `d3d11.dll`/`dxgi.dll`；
- `dx.d3d11/windows/windows` **bind=1**、进程存活；
- 但连接 4 次 capture 全部 ret=0；`dx/windows/windows` bind=0（它没有 `d3d9.dll`，
  注入侧日志 `DisplayHook locate D3D9 failed render_type=131072`）。
- 结论：它把 d3d11 当**显卡探测**用，主窗口类 `VolWinForm` 是纯 GDI，
  **不产生 swapchain Present 帧** → 不是合格 DXGI 靶子。

## 7. 屏保路线（可行，已验证）

```bash
# 起宿主窗口（载体本身就是个窗口）
dx_carrier.exe --backend d3d9 --seconds 45 --w 500 --h 400 --report r.txt
# 屏保以预览模式渲染进该窗口，不抢全屏
Bubbles.scr /p <r.txt 里的 hwnd>
```

实测（`workbench/_t_scr_probe.py`）：

- 屏保进程（pid 独立）创建子窗口 `class='D3DSaverWndClass'`、标题「气泡」、尺寸 500x400，
  父窗口正是宿主 hwnd；
- 屏保进程模块里出现 `d3d9.dll` + `D3DREF9.DLL` + `nvd3dumx.dll`；
- op 绑**该子窗口** `dx/windows/windows` → **bind=1，capture ret=1，uniq=2015**（真实气泡画面）。

注意两点：① 要绑**子窗口**而不是宿主窗口（画面画在子窗口上，绑宿主只会拿到黑帧）；
② 本机 `SysWOW64` 下只有 `PhotoScreensaver.scr` / `scrnsave.scr`，**都不导入 d3d9**，
所以屏保路线只能覆盖 x64；32 位仍以自建 `dx_carrier_x86` 为准。

## 8. 遗留与风险

- **`ResolveApi` 不 LoadLibrary**：目标进程尚未加载 `dinput8.dll` 时 op 直接放弃 input 绑定。
  理论上 op 可自行加载 dinput8 补齐（游戏随后加载会复用同一模块、vtable 一致，hook 仍有效），
  属于**行为变更**，本轮未改，待决议。
- `dx_carrier_x86.exe` 与 `_t_*.py` 探针都在 `workbench/` 下，按项目约定**不入库**；
  入库的是 `scripts/build_dx_carrier.py`、`scripts/build_dx_target.py`、`scripts/dx_carrier.cpp`、
  `tests/CMakeLists.txt`。
- gtest 用的载体副本是 `build/nmake-x64-Release/tests/dx_carrier.exe`（CMake 目标 `dx_carrier`），
  改了 `dx_carrier.cpp` 后要 `python build/_wb_build.py dx_carrier` 重建，否则测试跑的是旧载体。

## 9. 复现命令汇总

```bash
# 1) 双架构载体
python scripts/build_dx_carrier.py
python scripts/build_dx_carrier.py --arch x86
python build/_wb_build.py dx_carrier            # 刷新 gtest 用的 x64 副本

# 2) 32 位 dx 端到端（受控，不依赖游戏）
python workbench/_t_dx32_carrier.py --arch x86 --backend d3d9 --dinput --modes "dx|dx|dx,dx|windows|windows"
python workbench/_t_dx32_carrier.py --arch x86 --backend d3d11 --modes "dx.d3d11|windows|windows"

# 3) 任意第三方程序能不能绑
python workbench/_t_bind_any.py "<exe路径>" --wait 7 --modes "dx.d3d11|windows|windows"
python workbench/_t_mods.py <进程名>             # 运行时模块（d3d9/dinput8/op_c_api_x86）

# 4) 屏保路线
python workbench/_t_scr_probe.py

# 5) 回归
python workbench/run_optest.py --filter "HookCapture*"
```
