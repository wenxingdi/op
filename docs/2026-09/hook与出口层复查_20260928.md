## 一、P1（有实际故障风险）

### H1 未知 DXGI 格式被当作 RGBA8 —— HDR 目标静默颜色错乱
- **位置**：`libop/hook/DxCaptureCommon.cpp:86-93`（`GetImageBufferFormat`）
- **现象**：只识别 BGRA 家族（`B8G8R8A8` / `B8G8R8X8` 及其 `TYPELESS`/`SRGB` 变体），**其余一律返回 `IBF_R8G8B8A8`**。
- **后果**：`DXGI_FORMAT_R10G10B10A2_UNORM`（HDR 常见）/ `R16G16B16A16_FLOAT`（ScRGB HDR）等被按 4 字节/像素的 RGBA 逐通道重排 → 颜色完全错乱。**全程静默**（`Capture ret=1`、尺寸与字节数正常），只能靠目视发现。
- **放大因素**：Windows 11「自动 HDR」会改变交换链格式；`R10G10B10A2` 也是不少引擎的默认后备缓冲格式。
- **建议**：显式枚举支持集，未识别格式**记日志 + 关捕获**（而不是猜 RGBA8）。是否加 10bit 转换另议（成本高，可先只做"不静默"）。

### H2 解绑与在途 detour 竞态 —— `old_address` 可能被置空后被读取
- **位置**：`libop/hook/DisplayHook.cpp:164-176`（`release`）配合各 `*_hkPresent`（如 `D3D11Capture.cpp:170`）
- **时序**：
  1. 渲染线程 T 进入 detour，尚未执行 `((Present_t)DisplayHook::old_address)(...)`
  2. RPC 线程 R 调 `release()` → `MH_DisableHook` / `MH_RemoveHook`
  3. MinHook 会冻结/解冻其他线程，**但解冻发生在 `MH_RemoveHook` 返回时**，而 `old_address = nullptr` 在其**之后**执行（`DisplayHook.cpp:171`）
  4. T 解冻后读 `old_address` → 可能读到 `nullptr` → **调用空函数指针 → 目标进程崩溃**
- **备注**：MinHook 自带线程冻结，所以窗口很窄、非必现；但 `bb98e92`（dx Hook 生命周期）修的正是同类"解绑顺序"问题，显示侧尚未对齐。
- **建议**：`release` 不置空 `old_address`（或改 `std::atomic<void*>` + 延迟回收）；更稳的是"先停捕获 → 等一个重试计数确认 detour 退出 → 再拆 hook"。

### H3 D3D9 不支持 MSAA 后备缓冲 —— 每帧静默失败
- **位置**：`libop/hook/D3D9Capture.cpp:70`（`GetRenderTargetData`）
- **现象**：D3D10/11 都有 `SampleDesc.Count > 1` → 先 resolve 的分支；**D3D9 没有**。`IDirect3DDevice9::GetRenderTargetData` 对 MSAA 后备缓冲返回 `D3DERR_INVALIDCALL`。
- **后果**：目标开了 MSAA（D3D9 时代非常常见）→ `dx`/`dx.d3d9` 显示模式**永远截不到图，且无日志**（`D3D9Capture.cpp:71-72` 直接 `return hr`）。
- **建议**：按 D3D10/11 的模式补 `StretchRect` 到非 MSAA surface 再 `GetRenderTargetData`；短期至少补日志。

### H4 `resolve_hook_dll` 未判空 —— 宿主崩溃
- **位置**：`libop/hook/InputHookClient.cpp:32`
- **现象**：`proc.modules().GetMainModule()->type` 直接解引用，**无 null 检查**。
- **后果**：受保护进程 / 模块枚举受限时（Attach 成功但枚举失败）→ 宿主进程空指针崩溃。
- **建议**：判空后回退（按宿主位数猜）/ 记日志返回失败。

### H5 4 个远端 RPC 函数缺异常护栏 —— RPC 异常直穿宿主
- **位置**：`libop/hook/InputHookClient.cpp` 的 `call_set_input_hook:36` / `call_release_input_hook:81` / `call_set_input_lock:107` / `call_set_input_attr:135` / `call_cursor_shape:192`
- **对比**：`call_ping_hook:165` **有** try/catch，注释明确写"BlackBone RPC 可能抛异常（目标进程状态异常时）"，说明作者已知该风险，但只补了这一处。
- **后果**：`MakeRemoteFunction` / `remote()` 抛异常 → 传播到宿主 → 宿主崩溃（而非返回失败码）。
- **建议**：与 `call_ping_hook` 对齐，统一包 try/catch。

### H6 D3D12 硬编码 `IBF_R8G8B8A8` —— BGRA 交换链红蓝互换
- **位置**：`libop/hook/D3D12Capture.cpp:132`（`int fmt = IBF_R8G8B8A8;`）
- **现象**：完全**不读**交换链格式（`desc.Format` 在 `D3D12_RESOURCE_DESC` 里可用），而 D3D10/11 走的是 `GetImageBufferFormat(...)`。
- **后果**：交换链为 `B8G8R8A8_UNORM` 时（D3D12 常见），`CopyImageData` 的 RGBA 分支会交换 B/R → **红蓝互换**，且静默。
- **建议**：改用 `GetImageBufferFormat(desc.Format)`，与 D3D10/11 统一。

## 四、已验证无问题（避免后续重复排查）

| 项 | 证据 |
|---|---|
| **COM 出口异常防护** | 251 个 `STDMETHODIMP` 表面上只有 1 个 try，但那个 try 在 `OpAutomation::Invoke:92-107`——**IDispatch 唯一入口**，覆盖全部晚绑定调用（VBScript/易语言/按键精灵均走晚绑定）。`catch (const std::exception&)` + `catch(...)` 双兜，返回 `E_FAIL` + `pExcepInfo`。**不是缺陷** |
| InputHook 并发 | `g_stateMutex` / `g_eventMutex` + `std::atomic<LONG> m_inputLock / m_dxAttrs` 齐备（P1-8 修复已落地） |
| DliFailureHook | `self_directory` 对 `GetModuleFileNameW` 的 `len >= MAX_PATH` 有校验；非 onnxruntime 失败不干预；钩子内不调 setlog（崩溃路径自身不依赖运行时时序）——设计完整 |
| SharedFrame 容量计算 | `RequiredSharedFrameBytes` 对 `width > max/height`、`pixels > (max-header)/4` 双溢出保护 |
| MinHook 引用计数配对 | `AcquireMinHook`/`ReleaseMinHook` 在 setup 的各失败路径与 release 均有配对（靠 `hook_target` 非空隐式判定，虽然隐晦但正确） |
| IPC 多开隔离 | 共享内存/互斥体名按 hwnd 派生（`op_mutex_<hwnd>` / `op_shared_mem_<hwnd>`）→ 不同窗口天然隔离 |
| MinHook 线程冻结 | `MH_DisableHook` / `MH_RemoveHook` 内部冻结其他线程，所以 H2 是**窄窗口**而非必现 |

**已知设计限制（非缺陷，记录）**：

- `DisplayHook::is_hooked` / `InputHook::is_hooked` 是**进程级静态单例** + `HookExport` 的 `g_display_ref_count > 0` 时拒绝换 hwnd（`HookExport.cpp:39-43`）→ **同进程多窗口不支持**（与 `InputHook.h:53` 通道掩码进程级是同一根因）。
- 延迟加载钩子只处理 `dliFailLoadLib` 不处理 `dliFailGetProc` → 目标进程若已加载**版本不匹配**的 onnxruntime.dll，符号解析失败仍会崩（注释 §「约束/注意」已明示取舍）。
- `libop/network/` 自 09-18 `196df8c` 已整体移出构建（HTTP 后端隐藏），非活跃域。

### 7.2 判定为"不是问题"（差点误判，记录以免下次重复怀疑）

**`DisplayHook.cpp:179-186` 的绑定态发布顺序**：先 `MH_EnableHook` 启用钩子，再写 `shared_res_name`（`std::wstring`）等绑定态，最后 `set_capture_enabled(true)`；detour 侧是"先 `capture_enabled()`，再读名字"。初看是**并发读写 `std::wstring`**（UB）。

**读了调用链后推翻**：`is_capture` 是 `std::atomic<int>` 默认 **seq_cst**，`set_capture_enabled(true)` 写在赋名之后、detour 读名字在 `capture_enabled()` 之后 —— seq_cst 天然构成 release/acquire 配对，happens-before 成立，**有序、安全**。

但这是**碰巧成立**的：`is_capture` 只是用了默认内存序，代码里零说明。谁把它"优化"成 `relaxed` 就是真 UB（并发读写 `std::wstring`，表现为无规律崩溃/花屏，极难复现）。已在 `DisplayHook.cpp` 加注释固化该约束。

> 这是本项目**第 5 次**「按直觉判定问题 → 读调用链发现前提不成立」（前 4 次：`HookExport` COM 护栏、H14 的"仅 5 个有 try"、H1/H6 的格式静默降级范围、批 1 的 `UnBindEx`）。**先读调用链，再判定缺陷。**

### 7.6 真机补课：32 位目标 hook 导出名解析（2026-09-28 夜）

用真实游戏（蜀门 `client.exe`，PID 8944，**i386 + D3D9**，句柄 `0x03941210`，无任何反外挂特征模块）做真机验证时，暴露出**台账里没有的一类问题：不是 hook 逻辑错，而是 32 位目标上远端函数根本解析不到**。

- **现象**：`dx` / `dx.d3d9` / `dx.d3d11` / `opengl` **全部绑定失败**（`remote function 'SetDisplayHook' not found in op_c_api_x86.dll`），而 `normal` / `gdi` 正常。日志**没有** `Inject false`/`attach false` → 注入成功，断的只是名字解析。
- **根因**：`DLL_API` = `extern "C" __declspec(dllexport)`，`extern "C"` 只消 C++ 修饰，**不消 `__stdcall` 的 `_Name@N`**（x64 无此问题）。blackbone 的 `GetExport` 只做精确名匹配。`/DEF` 只挂给了 COM 目标，C API / hook 目标没有 `.def`。
- **修**（`HookExportName.h` + `HookRemoteCall.h`，14 处调用点）：读本地 dll 导出表把未修饰名映射成实际名字；未修饰名优先、找不到原样返回、失败不落终值、按 dll 缓存整张表。新增 12 条用例（含真实 PE 产物端到端）+ 两轮反向验证。
- **反向验证的收获**：第一轮「去掉 `@` 位置检查」竟然没被测出 —— 因为同前缀兄弟导出 `_SetInputHookEx@8` 会被后续「后缀纯数字」检查拦住，而用例缺了**「无 `@` 但 plain 后是纯数字」**（`_Foo12`）这一形状。补上后第二轮精确命中。**多条件防护的用例必须覆盖每条检查各自独有的输入形状。**
- **真机结果分两半**：✅ 解析链**已生效**（宿主日志 `SetDisplayHook -> _SetDisplayHook@8`，且游戏进程内 `__op.log` 出现 `DisplayHook setup ...`，证明远程调用真的进了目标进程）；⚠️ 但现有 `op_c_api_x86.dll`（**2026-09-14 上游预编译件**，7.8MB/214 导出 vs 本仓库 x64 的 27.8MB/256 导出）**挂不住蜀门**：游戏内日志 `DisplayHook setup locate failed ... target=00000000 detour=00000000`，随后目标进程以 `0xc0000005`（BEX、故障模块 unknown、偏移 0 = **调空函数指针**）崩溃，转储 `client.exe.8944.dmp`。
- **定性**：该 x86 dll 早于本仓库**全部** hook 加固（最近的同类修复是 `c4420ae`(09-16)「DX 注入致 0xC0000005 崩溃·延迟加载失败钩子兜底」与 H2b「`setup` 先发布 trampoline 再 `MH_EnableHook`」），崩溃形态与这些已修缺陷一致 → **非本轮引入**。
- **⚠️ 安全影响必须记住**：本修复把 32 位目标的行为从「**干净失败**（解析不到 → 不注入不调用）」变成「**真的调用那份旧 dll 的 hook 代码**」。所以在自建含全部加固的 x86 之前，**旧 x86 dll 不应再被用于任何真实 32 位游戏**。
- **挂账（独立批次）**：x86 自建。`build.py -a x86` 与 `--deps-arch both` 都可用，但 OpenCV 不是可选项（无开关，CMake 硬要求 `install/<gen>-<arch>`），而 `_deps/{BlackBone,build}` 与 `_deps/opencv/install` 目前都只有 x64 → 首次需源码构建 OpenCV x86。

**顺带确认的事实**（供后续真机复用）：蜀门是 **i386**，必须走 `op_c_api_x86.dll` 注入模块（`ResolveHookModuleName` 在宿主为 `op_c_api_*` 时返回它，而非 `op_x86.dll`）；`m_opPath` 由 `RuntimeEnvironment::getBasePath()` 自动取**已加载 dll 所在目录** → 从哪加载决定注入能否找到 x86 模块（`op/bin/x64` 下没有它，`OPTool/Common/Dll` 下有）。蜀门在 150% 缩放下 op 报 client 1360×768（物理）、Win32 报 906×512（逻辑），恰好 ×1.5。窗口被完全遮挡时 `gdi` 仍能截到真实画面，`normal`（桌面 DC）只会截到覆盖层。
