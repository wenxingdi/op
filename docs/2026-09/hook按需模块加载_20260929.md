# hook 按需模块加载（on-demand module load）

日期：2026-09-29
涉及：`libop/hook/ApiResolver.{h,cpp}`、`libop/hook/DisplayHook.cpp`、`libop/hook/InputHook.cpp`、
`scripts/plain_carrier.cpp`（新增）、`tests/hook_capture_test.cpp`、`tests/CMakeLists.txt`

---

## 1. 要解决的问题

`ResolveApi` 与 kiero 的 `locate<Implementation_*>` 全程只用 `GetModuleHandleA`，**不主动加载**。
于是两种完全不同的情况被混为一谈：

| 真实情况 | 应有的行为 |
|---|---|
| 目标进程**此刻还没**加载 `d3d9.dll`（游戏启动早期 / DirectInput 要等进场景才创建） | 加载它，再挂钩 |
| 目标进程**永远不用**这条 API（例如只用 Raw Input 的游戏） | 如实失败 |

后果最重的是 input 侧。`InputHook::setup` 里：

```cpp
if (!hook_dinput()) {
    // P1-9: 不再谎报成功——DirectInput 通道完全装不上时中止本次输入绑定
    release();
    return 0;
}
```

也就是说 **dinput8 一条通道没就绪，会让整个输入绑定失败**。而 op 实际还有三条通道可用：
win32 键状态（`GetKeyState`/`GetAsyncKeyState`/`GetKeyboardState`）、Raw Input、
窗口过程 `opWndProc`。为一条通道整体失败是更差的结果。

实测触发场景：蜀门 `client.exe` 停在「版本检查」界面时没有加载 `dinput8.dll`
（`workbench/_t_mods.py` Toolhelp32 枚举），于是 `dx/dx/dx` 绑定返回 0。

## 2. 设计

### 2.1 `LoadApiModule` / `ResolveApiLazy`

```cpp
void *LoadApiModule(const char *mod_name);                              // 加载（或复用）系统模块
void *ResolveApiLazy(const char *mod_name, const char *func_name);      // 先原语义解析，失败再加载重试
```

- 命中 `GetModuleHandleA` → 直接返回（**绝大多数情况都走这条**，行为与改动前完全一致）。
- 未命中 → `LoadLibraryExA(mod, nullptr, LOAD_LIBRARY_SEARCH_SYSTEM32)`。
  **只从 System32 找**（32 位进程由 WOW64 重定向到 SysWOW64），不查 cwd / PATH / 目标目录。
- 老系统（缺 KB2533623）该 flag 会失败 → 退回 `LoadLibraryA` 并记日志。
- **永不 `FreeLibrary`**：目标随后自行 `LoadLibrary` 同名模块时会复用我们这份并自增引用计数，
  vtable 与函数地址完全一致，hook 依然有效；反过来若我们提前释放，可能把它的引用计数打穿。

### 2.2 遮蔽防护：目标自带同名 DLL 时拒绝加载

如果目标 exe 目录 / cwd 下有**同名** DLL，说明它可能用的是**私有**图形/输入库
（dgVoodoo、ReShade/ENB 这类 d3d9 wrapper，或手柄映射用的 dinput8 包装器）。
此时抢先加载 System32 版本会让模块名被我们占住 —— 目标随后的 `LoadLibrary("d3d9.dll")`
直接复用我们这份，**静默替换掉它的图形栈**。所以这种情况下**拒绝加载**，保持原行为。

**例外（实测踩到的坑）**：目标 exe 本身落在系统目录时（`notepad.exe` 在 `SysWOW64`），
"exe 目录"与"系统目录"是同一个 —— 那里出现 `dinput8.dll` 完全正常，不是私有库。
不加这个例外，按需加载对**所有系统目录里的目标**永久失效（记事本实测：bind=0 且无加载记录）。

### 2.3 关闭方式

环境变量 `OP_NO_ONDEMAND_LOAD=1`（注入侧读取**目标进程**的环境块；宿主 `CreateProcess`
启动的游戏会继承宿主环境）。默认**开启**。

只认明确的真值（`1` / `true` / `yes` / `on`），避免 `=0` 与 `=false` 产生歧义。

## 3. 接入点

| 位置 | 行为 |
|---|---|
| `DisplayHook::locate_render_method` 前 | 按 render_type 预加载：`d3d9` → d3d9.dll；`d3d10/11/12` → dxgi.dll + 对应 d3d*.dll；OpenGL 各分支 → opengl32.dll |
| `libEGL.dll`（`RDT_GL_ES`） | **故意不加载** —— 它是模拟器/运行时的私有库，System32 里没有正品；走的 fallback 搜索反而可能把我们自己找来的那份抢先塞进目标进程、顶替它本该用的 |
| `InputHook::load_dinput_vtables` | `ResolveApi` → `ResolveApiLazy`（dinput8.dll） |

加载失败**不致命**：kiero 随后仍会如实报 `Error_ModuleNotFound`，`setup` 照常返回 0。

## 4. 验证

### 4.1 display 侧：模块从无到有（模块级硬证据）

靶子 `dx_carrier.exe --backend d3d9` 的导入表是
`DINPUT8.dll, GDI32.dll, KERNEL32.dll, OPENGL32.dll, USER32.dll, d3d11.dll, d3d9.dll`
—— **没有** d3d12/d3d10，正好当"未加载"的靶子。

| 模式 | 绑定前相关模块 | 绑定后相关模块 | bind |
|---|---|---|---|
| `dx.d3d12/windows/windows` | dinput8, opengl32, d3d11, d3d9, dxgi | **+ d3d12.dll** | 1 |
| `dx.d3d10/windows/windows` | 同上（+d3d12） | **+ d3d10.dll, d3d10core.dll** | 1 |

`d3d10` 这条顺带修好了本机此前恒失败的通路（旧日志：`DisplayHook locate D3D10 failed error=2`）。

### 4.2 input + display 合并：gtest 端到端

`dx_carrier` 静态导入 dinput8，所以它**永远**构不成"未加载 dinput8"的前提 —— 必须另起靶子。
新增素载体 `scripts/plain_carrier.cpp`：

- 只依赖 `user32/gdi32/kernel32`（导入表实测：`GDI32.dll, KERNEL32.dll, USER32.dll`）
- 真窗口 + 四象限配色（与 `dx_carrier` 同色序，万一拿它测 gdi 抓取判据通用）
- `--report` 格式与 `dx_carrier` 一致，测试侧 `CarrierProcess` 直接复用

用例 `HookCaptureTest.BindLoadsMissingGraphicsAndInputModulesOnDemand`：

1. 启动素载体 → `ASSERT_FALSE(d3d9.dll)` + `ASSERT_FALSE(dinput8.dll)`（前提，防假绿）
2. `BindWindow(hwnd, "dx.d3d9", "dx", "dx")` → `ASSERT_EQ(ret, 1)`
3. 从**外部**枚举目标进程模块 → `EXPECT_TRUE(d3d9.dll)` + `EXPECT_TRUE(dinput8.dll)`

第 3 步必须用 Toolhelp32 外部枚举：按需加载是把模块塞进**目标进程**，宿主侧
`GetModuleHandle` 什么都看不到。

### 4.3 反向验证（A/B，零代码改动）

同一用例在 `OP_NO_ONDEMAND_LOAD=1` 下：

```
hook_capture_test.cpp(671): error: Expected equality of these values:
    Which is: 0
    Which is: 1
[  FAILED  ] HookCaptureTest.BindLoadsMissingGraphicsAndInputModulesOnDemand (1060 ms)
```

⇒ 用例具备真实判别力，不是恒真摆设；同时证明 bind=1 确实是按需加载带来的。

### 4.4 顺带纠正的历史误判

上一轮 CHANGELOG 把「`dx_carrier` 无 `--dinput` → bind=0」归因于"Dinput8 未加载"。
**这个归因不成立**：载体静态导入 `DINPUT8.dll`，"是否加载"根本不是变量（见 4.1 的导入表）。
历史那次 bind=0 的确切成因不再断言（当时未做 A/B 隔离）。对蜀门的定性不受影响 ——
蜀门确实没加载 dinput8，而 `ResolveApi` 只 `GetModuleHandleA`，那条链条本身成立。

**教训：靶子的静态导入表要先看再下结论**，否则会把"一直加载着"当成"未加载"。

## 5. 已知取舍

**加载成功 ≠ 该通道一定能拦到东西。** 目标若根本不走这条 API（例如只用 Raw Input 的游戏
从不碰 dinput8），hook 装上了也不会被调用。所以每次按需加载都写
`api resolver: loaded <dll> on demand` 日志，让"绑上了但一帧都没有"可被追溯 ——
而不是变成又一次"谎报成功"。

（注意：`InputHook::setup` 会把 `RuntimeEnvironment::m_showErrorMsg` 置 0，
所以注入侧的这些日志**默认不落盘**；排查时需先在宿主侧开日志，或从模块列表反推。）
