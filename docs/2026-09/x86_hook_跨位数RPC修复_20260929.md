# x86 hook 真机 P0 修复：跨位数 RPC 调用约定 + 句柄传参宽度（2026-09-29）

> 触发：x64 宿主绑 32 位目标走 `dx` 注入，蜀门 `client.exe` / 32 位记事本**稳定 0xC0000005**。
> 这是「自建 x86 hook DLL 能否替代上游预编译件」的最后一道缺口。
> 结论：**两个叠加的跨位数传参 bug，均已修复并在真机端到端验证通过**。

---

## 1. 现象与里程碑

| 阶段 | 结果 |
|---|---|
| blackbone attach | ✅ |
| `op_c_api_x86.dll` 注入 | ✅ |
| 导出名解析（消 `@N` 装饰） | ✅ `_SetDisplayHook@8` |
| `SetDisplayHook` 远程调用 | ❌ 函数体执行完 → 目标进程崩溃 |

事件日志：`client.exe` `0xC0000005`，错误模块 **unknown / 偏移 0x0**
（= 远程 stub 代码区，或跳转到 0）。关键证据来自**注入侧日志**（落目标进程 cwd）：
崩溃前最后一行 `DisplayHook setup locate failed`，说明 **DLL 函数体已经完整跑完**。

## 2. 根因（两层叠加）

### P0① 调用约定：cdecl stub 调 stdcall 函数

blackbone `RemoteFunction.hpp` 原文：

```cpp
// Under AMD64 these will be same declarations as __cdecl, so compilation will fail.
#ifdef USE32
template<typename R, typename... Args>
class RemoteFunction <R( __stdcall* )(Args...)> : public RemoteFunctionBase<cc_stdcall, R, Args...>
```

`__stdcall` 特化**只在 32 位 blackbone 构建下编译**。x64 宿主上 `long(__stdcall*)(HWND,int)`
被归一化成 `long(*)(HWND,int)` → 落进 `__cdecl` 特化 → `RemoteFunctionBase<cc_cdecl,...>`
→ 跨 Wow64 时 `AsmHelper32` 生成 **cdecl stub**（caller `add esp,N` 清栈）去调 **stdcall 导出**
（callee 已 `ret N`）→ 每参 4 字节栈漂移。

修法：**绕过特化体系**，直接实例化 `RemoteFunctionBase<cc_stdcall, R, Args...>`。
（x64 目标 `AsmHelper64::GenCall` 忽略约定参数，行为不变；32 位宿主与 USE32 特化等效。）

### P0② 句柄传参宽度：`AsmVariant` 用**宿主** `sizeof(T)`

这是**真正致崩**的那一条。

```cpp
// AsmVariant 构造：argSize = sizeof(RAW_T)   ← 宿主（x64）的 sizeof
else if constexpr(std::is_same_v<RAW_T, HWND>)
    set( imm, argSize, reinterpret_cast<uint64_t>(arg) );   // size = 8

// PrepareCallAssembly：x86 目标下把「imm 且 size>4」转成 dataStruct
if (arg.type == AsmVariant::imm && arg.size > sizeof(uint32_t) && arch == kArchX86) {
    arg.type = AsmVariant::dataStruct;   // 8 字节按值压栈
    ...
}
```

后果：

1. **参数串位**：`[HWND 8字节][int 4字节]` 压栈，callee 读 `arg2` 时拿到的是 struct 高 4 字节
   —— 恒为 0。真机实证：修复前注入侧日志 `render_type=0`（**不匹配任何渲染分支，静默返回**）；
   修复后 `render_type=131072`，正确进入 `locate D3D9`。
2. **栈布局不符 32 位 ABI** → 远程 stub 收尾踩坏栈 → `0xC0000005`。

修法：`CallHookHwndIntFn`（`libop/hook/HookRemoteCall.h`）按目标位数选句柄宽度：

```cpp
if (proc.core().isWow64()) {
    using f32_t = long(__stdcall *)(uint32_t, int);   // 32 位 ABI：HWND 就是 4 字节
    ...
} else {
    using f64_t = long(__stdcall *)(HWND, int);       // 64 位：AsmHelper64 走 64 位立即数
    ...
}
```

顺带修掉同源问题：`SetDllDirectoryW(nullptr)` 恢复调用（生产路径）——`nullptr_t` 在 x64 宿主上
同样 `size=8` → 误走 dataStruct → 取结果抛异常。改传**裸 4 字节立即数 0**
（形参声明为 `uint32_t`）。

## 3. 定位方法（可复用判据）

1. **注入侧日志落目标进程 cwd** —— 崩溃前最后一行就在那，比猜快得多。
2. **控制变量对照实验**：同一宿主下 RPC 调用
   - `kernel32!GetCurrentProcessId`（0 参）→ ✅
   - `kernel32!MulDiv(9,2,3)`（3 个 int）→ ✅ result=6
   - 注入 DLL `SetInputLock(0)`（1 个 int）→ ✅ result=1
   - `SetDisplayHook(HWND,int)`（含句柄）→ ❌

   → 一步锁定「句柄宽度」而非「参数个数」或「DLL」。
3. **`release()` 返回 `0xC000010A`（STATUS_PROCESS_IS_TERMINATING）** 说明目标已在
   上一个 RPC 收尾期间死亡——用它给崩溃时间点划界。
4. `GetCallResult` 返回的 `status` 是 blackbone 内存 `Read` 的 NTSTATUS；
   `0x8000000D`（STATUS_PARTIAL_COPY）表示目标内存状态已坏。

## 5. 遗留（非阻塞）

- **`dx/dx/dx`**（display/mouse/keyboard 全 dx）：display 绑定成功（`render_type=131072`），但
  `SetInputHook` 返回 0。**已定性：目标进程尚未加载 `dinput8.dll`**——判据
  `python workbench/_t_mods.py client.exe`（Toolhelp32 `SNAPMODULE|SNAPMODULE32` 跨位数枚举）：
  蜀门停在「版本检查 Ver8.2.06」界面时 `d3d9.dll` **已加载**、`dinput8.dll` **未加载**。
  `InputHook::setup` 里 `hook_dinput()` 无设备可挂 → 按 P1-9「不再谎报成功」直接返回 0
  （RPC `status=0x0`，是干净的功能性失败，不是崩溃）。**需游戏进入真实场景后复验**。
  > 探针陷阱：`is_bind=0` 时 `OpGetScreenData` 仍可能 `ret=1`（抓到的是桌面），
  > 所以 `dx/dx/dx` 那行 `capture OK uniq=481` 是**假阳性**——唯一色统计只在 `is_bind=1` 时可信。

- 本机 150% DPI 下 `OpGetScreenData` 用的是**客户区物理像素**；探针窗口 rect 与画布一致。

## 5.1 发布件 x86 分发（同批收口）

- `build/_sync_release_b2.py` 重写：`SOURCES` 按**文件名**映射源目录（x64/x86 分属
  `nmake-x64-Release` 与 `ninja-x86-Release` 两棵构建树），`TARGETS` 纳入 `op_x86.dll` /
  `op_c_api_x86.dll`——此前脚本只覆盖 x64，导致 SetPath 指向的 libop 目录缺 x86 hook DLL
  （`op_c_api_x86.dll not exists`，dx 绑定首败的直接原因）。
- `workbench/sync_extra_copies.py` 重写：x64 只刷新**已存在**的副本、x86 **源存在即补建**。
- 结果：6 处主副本 + 2 处运行时目录（`OPTool/Common/bin/.../Dll`、
  `optool_verify/bin/Release/net10.0-windows7.0/`）四件套 sha1 全一致
  （`3a543a669bc3` / `1277312ea402` / `42d64020cb14` / `fa25a29a84cd`）。
  **校验只认 sha1**（`cp` 返回值与时间戳都不可靠）。
