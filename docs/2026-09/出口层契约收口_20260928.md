# 出口层返回值契约收口（2026-09-28）

## 结论（先）

**出口层已无"负错误码泄漏"遗留。** 全库 319 处 `internal::set_result` + 73 处能力层
`return -N` 双向普查后，只有 **4 处**对外的负值返回，且**全部是设计语义、全部被既有测试钉住**：

| 出口点 | 值 | 语义 | 钉住的既有用例 |
|---|---|---|---|
| `Op::FindPic` / `OpFindPic` | `-1` | **大漠索引**：命中的图片序号，-1=未找到 | `ImageColorTest.FindPicReturnsMinusOneWhenTemplateIsMissing` |
| `Op::FindStr` | `-1` | **大漠索引**：命中的字符串序号，-1=未找到 | （同族，语义与 FindPic 一致） |
| `Op::IsLineBlocked` | `-1` | **三态**：1=被挡 / 0=通 / -1=未设地图 | `AlgorithmTest.AStarBMUnreachableOrNoMapReturnsEmpty` |
| `OpRequestCaptureForTest` | `-1` / `-2` | 测试钩子：-2=参数非法、-1=模式设置失败 | `image_color_test.cpp:2694` 用 `< 0` 钉住 |

本轮**没有改任何返回值**，只做了三件事：把语义写成注释钉在代码里、补上防复发的普查与回归、
把 `IsLineBlocked` 的"待拍板"收敛为结论。

---

## 一、普查怎么做（两个方向对撞）

单向扫容易漏，所以两个方向各跑一遍、只取交集：

1. **正向**（`scripts/return_contract_survey.py`）
   扫 `libop/op/*.cpp` 的 319 处 `set_result(target, expr)`，对**透传型** expr 回溯被调方定义，
   看它体内有没有 `return -N`。
2. **反向**（同一脚本 `--trace-neg`）
   扫全库 73 处 `return -N`，反推所属函数，再 grep 该函数是否被 op 层 `set_result` 直接透传。

两边都只报出 `FindPic` 与 `FindStr` 两个透传点 —— 互为印证，说明没有第三处漏网的负码透传。

---

## 二、差点改错的地方（判据）

上一轮真机测试期间，我曾把 `OpFindPic` 的 4 条 `-1` 按"布尔契约"改成 0，**这是错的**，
被既有测试当场打脸（`docs/CHANGELOG.md` 已记录）。本轮起把判据固化：

> **改任何出口层返回值之前，先回答两个问题：**
> 1. 这个 API 的返回值是**布尔**（0/1）还是**索引 / 计数 / 句柄**？
>    索引类（FindPic / FindStr）的 `-1` 是"未找到"，与 0（命中第 0 个）必须可区分。
> 2. 既有测试里有没有用例**钉住**这个值？
>    `grep -rn "OpXxx" tests/` 没跑过就不许动 —— `OpRequestCaptureForTest` 的 `< 0`、
>    `IsLineBlocked` 的 `-1` 都是这么找出来的。

`IsLineBlocked` 原本挂在"待拍板"上（改成 1 还是 0）。查完既有用例后收敛为**保持 -1**：
调用方按「非 0 = 被挡 = 走 A*」判定，-1 与 1 行为完全等价，且 -1 还能把
"忘记 SetAStarMap"这条诊断信息带出来；改成 0 则会把未设图误判成"畅通"，直线撞墙。

## 三、本轮新增的三件防复发机制

| 机制 | 位置 | 作用 |
|---|---|---|
| 返回值契约普查 | `scripts/return_contract_survey.py` | 正向扫 `set_result` + 反向扫 `return -N`，改出口层后跑一遍 |
| **null-handle 契约冒烟** | `scripts/gen_c_api_null_handle_test.py` → `tests/c_api_null_handle_test.cpp` | 给 256 个 C API 各挂一条回归：handle=nullptr 必须返回失败值（0 / 空串），索引语义 API 例外（-1） |
| CMake 源清单门禁 | `scripts/check_cmake_sources.py` | 比对磁盘 .cpp 与 CMakeLists 显式清单，防"新增文件忘登记 = 静默不编译" |

### 为什么补 null-handle 冒烟

`复查覆盖总览_20260928.md` 记着：256 个 C API 里 **211 个从未在 gtest 里出现过**。
后果是——某个 API 忘了 null 检查、忘了异常护栏、或把内部负码透出去，回归网**一个都抓不到**，
只能等真机撞上（本轮真机就撞出 `inject_dll` 与 `run_app` 两个）。

生成测试把"每个 API 至少被调一次"变成默认状态：

- 带 `op_handle` 的 253 个：用 `nullptr` 调用，断言失败值（`int`/`intptr_t` → 0，`const wchar_t*` → 空串）
- 索引语义白名单：`OpFindPic` 期望 `-1`
- 无 handle 的 3 个：`OpCreate` 必须拿到句柄、`OpVer` 必须非空、`OpRequestCaptureForTest` 只保证不崩溃
- 新增 API 后重跑生成器即可，漏登记会当场暴露（返回值契约不对会直接 FAIL）
