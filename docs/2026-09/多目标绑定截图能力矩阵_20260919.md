- 日期：2026-09-19

- 环境：Windows 10 build 18363 / i5-13400 / 7 个目标同时在线，**桌面处于多窗口互相遮挡状态**
- 探针：`workbench/probes/bind_capture_matrix.py`（真实 C-API）、`uwp_capture_probe.py`、`stitch_shots.py`
- 关联：`UWP窗口截图全黑根因_20260919.md`（本次把该结论从 UWP 扩展到**全部 GPU 合成窗口**）

## 1. 结论

1. **`gdi` / `dx2` 能不能用，只取决于目标窗口有没有 GDI 表面**：
   - 有（Qt、微信自绘）→ **正常**
   - 没有（Chromium、UWP，走 GPU 合成）→ **整幅全黑**
2. **`normal` / `normal.dxgi` 能不能用，只取决于窗口 Z 序**：不在最上层就**截到遮挡物**。
   `ret=1`、尺寸正确、非黑占比 100% —— 但画面是别人的。**7/7 目标在遮挡状态下 normal 都是错的**。
3. **一个改动可同时修复 5/7 目标的 gdi/dx2**：`PrintWindow` 加 `PW_RENDERFULLCONTENT` 标志，
   对 UWP + 全部 3 个 Chromium 实测**从全黑变为正确内容**，对 Qt 不劣化。

## 5. 优化建议

### 建议 1（P0，收益最大）：把 `gdi`/`dx2` 改为 `PW_RENDERFULLCONTENT` —— ✅ 已实施（见 §7）

**实施时修正一处代码事实**：`dx2` 并不走 `PrintWindow`。`GdiCapture.cpp` 里三条 GDI 家族模式实际是：
`gdi` = `PrintWindow(hwnd, hdc, 0)`；`gdi2` = `UpdateWindow` + `PrintWindow(hwnd, hdc, 0)`；
`dx2` = `BitBlt(窗口 DC)`（`requestCapture` 中 `RDT_GDI_DX2` 分支在 PrintWindow 分支之前命中，从不落入后者）。
三者对合成窗口都是全黑，只是失败点不同。

改后两种模式的语义变得清晰互补：

| 模式 | 语义 | 依赖 |
|---|---|---|
| `normal` | **屏幕所见**（含遮挡） | 窗口须可见、未被遮挡 |
| `gdi` / `dx2` | **窗口真实内容**（穿透遮挡） | 无（PrintWindow 直接向窗口索取） |

这恰好补上当前的能力缺口：普通用户直觉上会按"normal 截屏、gdi 抓窗口"来选，
而现在 gdi 对一半主流应用返回黑图。

**风险**（实施后复核结论附后）：
- `PW_RENDERFULLCONTENT` 需 **Win 8.1+** —— 已确认项目最低支持 **Win10**，无需运行时判断
- 对个别窗口可能返回与旧行为不同的画面（实测 BlueStacks 色数 998 → 1040）—— **§7.3 已给出像素级定位结论**
- 必须补**端到端成功用例**（UWP / Chromium 目标 + 非黑断言）。仅测 `ret=1` 无效 —— 已补 `tests/capture_mode_test.cpp`

### 建议 2（P1）：修复 `normal.dxgi`

实测 `normal.dxgi` 几乎处处等于 `normal`（数值完全一致），唯独 **WorkBuddy 例外：
`normal` 有内容而 `normal.dxgi` 全黑**。说明该通道要么未真正走 DXGI 复制，要么在特定窗口上失败后
静默返回黑图。需定位 —— 若它本意是"桌面复制"，那它应当不受遮挡影响，是比 `normal` 更有价值的通道。

### 建议 3（P1）：把"截图有效性检测"纳入验收判据

本轮之前的所有验收都以 `ret=1` 为准，导致：
- 计算器／Chromium 的 gdi/dx2 全黑被记成"通过"
- `normal` 截到遮挡物被记成"通过"

建议在测试与验收中固定加入像素校验：**全黑（唯一色 ≤ 1 且亮度 = 0）判失败**；
涉及"内容正确性"的场景（遮挡、多窗口）必须落盘目视核对，不能只看统计量。

### 建议 4（P2）：模式选择文档化

| 目标类型 | 现状推荐 | 建议 1 落地后 |
|---|---|---|
| Qt（BlueStacks / 钉钉） | `gdi` / `dx2` | 不变 |
| 微信等自绘窗口 | `gdi` / `dx2` | 不变 |
| Chromium（紫鸟 / 汽水 / 各类 Electron） | **无可用模式** | `gdi` / `dx2` |
| UWP（计算器 / 商店应用） | **无可用模式** | `gdi` / `dx2` |
| 硬件加速视频 / 独占全屏 | `dx.d3d11` / `dx.d3d12` | 不变 |

### 建议 5（P2）：WGC 通道修复

WGC 是唯一能同时解决「遮挡 + 最小化 + 硬件加速」的通道，当前阻塞于 `WgcCapture::Init`
的 `0xC0000005`（本机 4 个虚拟显示驱动所致）。本机无法验证修复效果，需干净机器。

## 7. 实施记录（2026-09-19 落地）

### 7.1 决策

| 决策项 | 结论 |
|---|---|
| 建议 1 实施方式 | **直接改 gdi / gdi2 / dx2**（不加新模式） |
| `normal.dxgi` 异常 | **不立项** —— `normal` 系本就是"屏幕所见"，非最前窗口截到遮挡物属预期行为，只要有可用模式即可 |
| 最低支持系统 | **Win10 起** → `PW_RENDERFULLCONTENT`（Win8.1+）无需运行时判断 |

### 7.2 改动（`libop/capture/backends/GdiCapture.cpp`）

1. `gdi` / `gdi2`：`PrintWindow` 改用 `PW_RENDER_FULL_CONTENT(0x2)`；结果**整幅全黑**时退回 `flags=0` 再取一次（防御性分支）。
2. `dx2`：保留「窗口 DC 直接 `BitBlt`」快路径（不发消息、最轻），仅当 BitBlt 结果全黑时才回退到上面的 `PrintWindow` 分支。`gdi2` 独有的 `UpdateWindow` 前置步骤保留，dx2 回退路径刻意不发消息。
3. 新增 `frame_is_all_black()`：只查 B/G/R 三通道、命中首个非黑像素即返回，正常帧开销可忽略，仅真正全黑帧才整幅扫描；两条回退均以它为判据（**取图失败是静默的，必须靠像素判定**）。
4. 文档层：`scripts/gen_api_reference.py` 的 `DISPLAY_MODES` 重写（顺带修正 `normal` 原被误标为"PrintWindow 后台截图"），手册已重生成（注解覆盖 899/899）。

### 7.3 验证

**① 单元测试（新增 `tests/capture_mode_test.cpp`，2 例，150% DPI 环境）**

- `GdiFamilyCapturesWindowContentForAllModes`：gdi / gdi2 / dx2 断言**像素颜色**（FF0000，重绘后须变 00FF00 证明取的是实时帧）
- `GdiCaptureIgnoresOcclusion`：目标窗口被同尺寸顶层窗口盖满（用例内 `WindowFromPoint` 自检遮挡确实成立）后，gdi 仍读到目标自身颜色

**② 全量回归**：270 ran / **262 PASS** / 6 SKIP / 2 FAILED，零回归。
两条 FAILED 均为键鼠域既有环境项（`WaitKeyScanAllWithWaitFindsKey` 历轮恒定；`WaitKeyUsesNormalizedKeyStateForMouseButtons` 单跑即过）。

**③ 真机矩阵复跑（7 目标 × 4 模式，真实 C-API，改前/改后同机对比）**

| 目标 | gdi 改前 → 改后 | dx2 改前 → 改后 |
|---|---|---|
| 计算器（UWP） | 全黑 → 非黑 99.4% / 亮度 234.2 / 41 色 | 全黑 → 同左 |
| WorkBuddy（Chromium） | 全黑 → 非黑 99.9% / 246.0 | 全黑 → 同左 |
| 紫鸟（Chromium） | 全黑 → 非黑 100% / 248.8 | 全黑 → 同左 |
| 汽水音乐（Chromium） | 全黑 → 非黑 100% / 75.2 | 全黑 → 同左 |
| BlueStacks（Qt） | 非黑 89.7% → 96.7%（±像素差见下） | 非黑 → 非黑（0.3% 差 = 内容漂移） |
| 钉钉（Qt）/ 微信（自绘） | 非黑 → 非黑（8~10% 差 = 应用内容漂移，dx2 同幅变化可佐证） | 同 |

目视核对（`workbench/matrix_stitched/`）：计算器出计算器本体、汽水音乐出深色播放页、紫鸟出店铺页、BlueStacks 出完整窗口（含标题栏与右侧工具栏）。

**BlueStacks 色数变化的像素级定位**：同轮内直接对照 `PrintWindow(0)` vs `PrintWindow(0x2)`（`workbench/probes/uwp_capture_probe.py --save`）——窗口内容区**仅 0.3% 像素差异**，差异集中在顶端一条 74px 带（`PW(0)` 渲不出的自定义标题栏区，`PW(0x2)` 渲出来了）与底部 20 行。**结论：不是内容错位、不是动画帧，而是此前留黑的窗口边框/标题栏区被正确渲染。**
> 连带结论：裁剪偏移 `dx_`/`dy_` 语义不变 —— 位图仍是"整窗坐标系、客户区位于 `(dx_, dy_)`"，客户区裁剪结果不受影响。

**④ 两条回退分支实测触发次数**：`dx2 BitBlt 全黑 → 回退` 触发 **4 次**（正是 4 个合成窗口目标，机制端到端验证）；`PW 主路径全黑 → flags=0 重试` 触发 **0 次**（防御性分支，本机无目标触发，未获实测覆盖）。
