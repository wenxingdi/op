## 一、必修（崩溃/UB）

### B1 `setlog(wchar)` 二次格式化 UB —— Utils.cpp:106
- **现象**：宽字符版把**已格式化完成的文本**当作 format 再传给窄字符版：
  ```cpp
  long setlog(const wchar_t *format, ...) {
      ... vswprintf_s(...) // 得到 tmps
      return setlog(tmps.data()); // ← 已展开文本当 format，char 版内部再 va_start/vsprintf_s
  }
  ```
  char 版被调用时**实参只有 1 个（无 vararg）**，却执行 `va_start + _vscprintf + vsprintf_s`——读取不存在的可变参数属 UB。
- **触发**：格式化结果含 `%` 字面（如 `setlog(L"进度 %d%%", x)` 展开出单个 `%`，或 `%s` 展开的内容本身含百分号）。含 `%s/%d` 占位时 `vsprintf_s` 解引用垃圾指针 → **潜在崩溃/内存破坏**。
- **触发面**：全项目宽字符版调用 58 处（HookCapture 20 / BindingSession 12 / InputHookClient 12 / ICaptureBackend 4 / WgcCapture 3 / DllInjector 3 / 其余 4 文件 4 处）。多数展开无 `%` 而侥幸安全——隐患在含百分号的文本。
- **修复方案（~20 行，低风险）**：把窄字符版的"输出体"抽为内部 `setlog_text(const std::string &s)`（时间戳+级别+分发，不碰 va_list）；窄字符版 = 格式化 → `setlog_text`；宽字符版 = 转码 → `setlog_text`。消除二次解析。

## 二、建议修（边界可能错）

### S1 `rect_t::divideBlock` count<=0 除零 + count>span 产生 0 尺寸块 —— Types.h:96-119
- `NumberGen(height(), count)` → `_q = n / cnt`，count=0 时 **release 构建除零崩溃**（`assert(count>0)` 仅 debug 生效）；count>height/width 时尾部产生 **0 尺寸块**（分块结果含空 rect，调用方对 0 块处理未知）。
- 调用方：ImageSearchAlgorithms.cpp:658/773，count 源自用户可配置分块数。image 模块批 2 细查时确认取值域。
- 修复：入口防御 `if (count <= 0) return;`（或 clamp 到 [1, span]）。

### S2 `hex2bin` 不认小写 a-f、无范围校验 —— Utils.h:32
- `c <= L'9' ? c - L'0' : c - L'A' + 10`：输入 `'a'` 返回 -22、`'g'` 返回垃圾。调用方 ProcessMemory.cpp:597 先 `towupper`（安全），**:552 直调未转大写**——用户在小写 hex（记忆搜索/找数据特征码）时解析错乱。
- 修复：hex2bin 内 `c = std::toupper(c)` 再判，或 552 行补 towupper（后者属 memory 模块，批 1 顺手）。

### S3 `ThreadPool` 构造 0 线程无防护 —— ThreadPool.h:38
- `ThreadPool(0)` → workers 空，enqueue 的 future **永不 ready**（调用方 wait 死等）。
- 现状两调用方均已防护（TemplateMatcher `max(1u, hw)`、ImageSearch `hw==0?1:hw`）——**当前不触发**，纯防御加固。修复一行：`threads = threads ? threads : 1`。

### 7.4 附带发现：测试与生产编译标志不一致

| 目标 | CRT | 优化 | NDEBUG | 其他 |
