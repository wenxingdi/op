## 1. 颜色字节序 —— 决定性判定

### 1.1 为什么必须实测

仅凭代码注释不足以定论，且**游戏画面无法提供无歧义 ground truth**（不知道那个像素"本该"是什么色）。故自建**受控 Tk 目标**：白底两行大字，`fg` 用标准 `#RRGGBB`（Tk 的颜色语义无歧义）。

### 1.2 方法与数据（`_t_color_order.py`）

受控窗口：`RED`（`#ff0000`）/ `BLUE`（`#0000ff`），Arial 44 bold，白底。

**像素层先确认目标成立**（区分"渲染问题"与"OCR 问题"）：

```
BMP=295x256/32bpp   纯红 #ff0000 = 5730 px   纯蓝 #0000ff = 6758 px
```

**判定矩阵**：

| 传入 color | 结果 | 解释 |
|---|---|---|
| `ff0000` | **`RED`** | 命中红行 |
| `0000ff` | **`BLUE`** | 命中蓝行 |
| `ff0000\|0000ff` | `REDBLUE` | 两行都出（`\|` = 或） |
| `''`（不传色） | `REDBLUE` | 走自动反白路径也能识别 |
| `autoocr_ex('ff0000')` | `('57,41,235,92,1.00,RED', 1)` | bbox 仅覆盖红行，conf=1.00 |

### 1.3 结论

**op 对外 = `RRGGBB`（RGB 顺序）**。代码依据 `libop/image/Color.h:38-47`：

```cpp
color_t &str2color(const std::wstring &s) {
    int r = 0, g = 0, b = 0;
    ...
    swscanf(ss.c_str(), L"%02X%02X%02X", &r, &g, &b);   // 前两位→r、中两位→g、后两位→b
    this->b = b; this->r = r; this->g = g;              // 内部存 color_t{b,g,r,alpha}（BGRA 布局）
```

即**对外字符串是 RGB，内部结构体是 BGRA 内存布局** —— 两者不矛盾，是"外部口径 / 内部布局"的分层。

> **⚠ 使用注意（用户侧）**：部分取色器/游戏日志输出 **BGR 串**（`BBGGRR`）。
> **对称色**（如 `33ee33`，R==B）两口径结果相同 → 不会暴露问题；
> **非对称色**（如 `1111e0`）会**红蓝错位、静默失效**（表现为"这个色过滤不出东西"）。
> 实测：用户报 `1111e0` 为**红**色 → 其取色源为 BGR；转 RGB 应为 `e01111`。

## 2. 绑定态坐标语义 —— 客户区坐标

### 2.1 实测（`_t_ocr_coord.py`）

把受控窗口整体平移 **`+300, +200`**，对比两次返回值的位移：

```
客户区屏幕原点位移 = (+300, +200)
autoocr_ex 首项 x 位移 = +0        (A=0 B=0)
find_color 位移 = (+0, +0)         A=(40,17) B=(40,17)
==> 判定：客户区坐标
```

若为屏幕绝对坐标，返回值应同步位移 `+300/+200`。**实测零位移 ⇒ 客户区坐标**。

### 2.2 代码依据

`BindingSession::RectConvert` 的「客户区→屏幕」偏移**整段被注释掉**，只保留裁剪：

```cpp
long BindingSession::RectConvert(long &x1, long &y1, long &x2, long &y2) {
    /*if (_capture && (_display == RENDER_TYPE::NORMAL || _display == RENDER_TYPE::GDI)) {
        x1 += _capture->_client_x;  y1 += _capture->_client_y;   // ← 被注释
    }*/
    x2 = std::min<long>(this->get_width(), x2);                  // 只剩裁剪
```

另：`ImageSearchAlgorithms` 的 `_dx/_dy` 全仓库**仅构造时置 0**，无任何赋值点（恒 0）；`_x1/_y1` 由 `capture_region()` 内 `set_offset(x, y)` 设置，用于"还原窗口坐标"。⇒ 对外坐标 = **客户区坐标**。

### 2.3 修正清单（8 处权威接口文档，原写「屏幕绝对坐标」）

## 3. 免字库 OCR 颜色语义

### 3.1 区域与真实构成

User 指定区域 `1174,1,1356,17`（182×16，游戏顶栏坐标显示），color `33ee33-000000|1111e0-000000`，sim 0.8。

**像素构成 Top-12（全 182×16 像素统计）**：

```
#33EE33   251 px (8.6%)   ← 唯一显著色 = 绿色文字
#2C0807    10 px (0.3%)   ← 以下全是暗棕底/描边（暗色）
#140101    10 px (0.3%)
#2D0807     8 px (0.3%)
...
```

区域**只有绿色文字 + 暗棕背景**，不存在 `1111e0`（蓝）/ `e01111`（红）。

### 3.2 颜色过滤矩阵（单变量，只改 color）

| color | `autoocr_line` | `autoocr_ex` |
|---|---|---|
| `''`（空串） | `成都［258,-507]`（注意全角 `［`） | count=1 |
| `33ee33`（绿·原样） | `成都[258,-507]` | count=1 |
| `33ee33-000000`（带偏色） | `成都[258,-507]` | count=1 |
| `1111e0`（用户第 2 色，op 读作蓝） | `''` | count=0 |
| `e01111`（R/B 换位，op 读作红） | `''` | count=0 |
| `33ee33\|1111e0`（用户原串） | `成都[258,-507]` | count=1 |
| 近黑 `000000-303030` | `''` | count=0 |
| 纯白 `FFFFFF` | `''` | count=0 |

**目视核对**（`rect_x6.png`，6 倍最近邻放大）：区域内容为绿色字 `成都 [258,-507]`，**负号真实存在**。⇒ 识别结果**完全正确**。

### 3.3 修正一个长期误判

原探针注释写「空串 → colors 为空 → **恒不匹配**」—— **错**。
实际 `str2colordfs` 对空串 `return 1` → 走 `bgr2binarybk(colors)`，其 `bk_colors.size()==0` 分支为「灰度 + 自动取背景色」**反白**路径 ⇒ **仍能识别**。

**正确语义**：

| color | 路径 | 行为 |
|---|---|---|
| 空串 | `bgr2binarybk` 自动背景色反白 | **能识别**，可能混入全角符/杂字（精度略差） |
| 给对色 | `bgr2binary` 按色域二值化 | 去噪提纯，**结果最干净** |
| 给错色（区域无该色） | 同上，前景为空 | 返回空串 —— **看起来像"识别不了"，实为输入口径错** |

### 3.4 字库路径对比（同帧同区域）

| 入口 | 结果 | 评价 |
|---|---|---|
| `autoocr_line`（免字库 + 用户色） | `成都[258,-507]` | ✅ 正确 |
| `autoocr_ex`（免字库结构化） | `count=1` `1224,1,1331,17,0.98,成都[258,-507]` | ✅ 正确 |
| `ocr_auto`（自动主色，无 color） | `成都[258,507]` / `R成都[258,3507]`（多次跑不稳定） | ❌ 负号丢失 |
| `ocr`（字库路径） | `o成都[258,3507]` | ❌ 负号丢失 + 杂字 |
| `ocr_from_file`（同图文件路径） | `成都[258,3507]` | ❌ 负号→3 |

⇒ **读游戏坐标必须用免字库 `autoocr_line` + 正确颜色**。

## 4. 六通道绑定矩阵（含「截图前前台化」改进）

**改进动机**：`normal` 是**桌面级捕获**（DXGI/WGC 抓屏幕合成），游戏被遮挡时会截到遮挡者 → 单变量污染。
**改进**：G1 每个通道截图前先 `set_window_state(hwnd, 1)` 前台化。

| 通道 | bind | capture | 唯一色数 |
|---|---|---|---|
| `gdi/windows/windows` | 1 | ret=1 | 399325 |
| `gdi2/windows/windows` | 1 | ret=1 | 385041 |
| `normal/windows/windows` | 1 | ret=1 | **388402**（前台化后真画面） |
| `dx/windows/windows` | 1 | ret=1 | 394542 |
| `dx/dx/dx` | 1 | ret=1 | 387744 |
| `dx.d3d11/windows/windows` | 1 | **ret=0** | — |

**前台化效果对照**（`normal`）：`3314`（被遮挡，截到 WorkBuddy 窗口）→ **`388402`**（真画面）。
⇒ 改进前那条「`normal` 判 FAIL」实为**遮挡环境条件**，非通道缺陷。

`dx.d3d11` 与理论预测一致：装的是同一个 `IDXGISwapChain::Present` hook，但取图需要 `ID3D11Resource` → 对 D3D9 游戏「**绑得上、取不到帧**」。

## 7. 遗留

- **G4 键鼠真机**（`--input` 门控）：会**真的向游戏发键鼠输入**，待用户批准。
- **`gl.*` 子模式**真机：需 OpenGL 渲染目标。
- **x64 非阻塞缺口**（历史挂账）：真 D3D10/D3D12 后端载体 + 像素级验证；x86 AI OCR 返 `-1` 路径。
- **用户取色器 BGR 差异**：建议在取色/调参工具里**显式标注 RGB / BGR**，或在传入 op 前统一做 R/B 归一，避免"非对称色静默失效"。
