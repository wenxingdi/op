## 1. B 组 charset 白名单（闭环）

清单原要求：`set_ocr_engine("onnx","", "--charset=@zh0123456789[],-+")` 返回 1，且白名单生效。
语义见 `OnnxOcrEngine.cpp:298-320`：`@zh` 展开全部 CJK（U+4E00–U+9FFF），其余可打印 ASCII 按字面加入，
**空规则 = 全字典**（默认）。

靶子：自建 Tk 白底黑字窗口，文本 `许愿树[320,-778]12345`（客户区 534×78）。

| 配置 | 实测结果 | 判定 |
|---|---|---|
| `--charset=@zh0123456789[],-+` | `'许愿树[320,-778]12345'` | **PASS** — 集合内字符全识别，无拉丁乱入 |
| `--charset=@zh` | `''`（空串） | **PASS**（见下） |
| 恢复 `argv=""` | `charset_mask=0`，返回 True | **PASS** — 回到全字典 |

判据设计：`@zh` 的断言写为「**结果只含中文/空格**」而非「结果等于 `许愿树`」。
若白名单失效，结果会是含数字的完整串 → FAIL，**有区分度**；空串满足该条件故 PASS。

### 关键发现：`@zh` 下整行消失（记录，非缺陷判定）

`@zh` 把**数字确被屏蔽**了，但中文 `许愿树` 也一并消失（`text=''`）。
疑因屏蔽后 CTC 各步最优类别退化：非白名单类别的 logits 被整体剔除
（`ctc_greedy` 的 `mask[c]==0` 直接 `continue`，见 `OnnxOcrEngine.cpp:353-362`），
在数字步上剩余类别（CJK + blank）无稳定优势 → 全落 blank。

- **不判为缺陷**：`@zh` 属极端白名单（只留中文、连数字都不要），实用场景罕用；
  常用写法（清单推荐的 `@zh0123456789[],-+`）实测完全正确。
- **可观测性不足（记待办）**：`load()` 只打印 `charset_mask=<size-1>`（= keys 数），
  两次不同 charset 打印相同值，**无法从日志看出实际放行类别数**。
  建议 `build_mask()` 增打放行计数（改动需重编 x64/x86 + 同步发布件，本轮未做）。

## 2. G4 键鼠真机（闭环）

### 2.1 调用面（`dx/dx/dx` 绑定真实游戏，零点击）

副作用控制：**只移动、只按修饰键 SHIFT，不 click / wheel / drag**。

| API | 结果 |
|---|---|
| `move_to(2,2)` / `move_r(40,25)` / `move_to_smooth(中心,150ms)` | 全 True |
| `move_to_ex(1/4,1/4,10,10)` | `'343,195'` |
| `get_cursor_shape` | `'1,AA948A9D7E2A0E18,48,48,0,0'`（非空） |
| `key_down(SHIFT)` → `get_key_state(SHIFT)` | **1** |
| `key_up(SHIFT)` → `get_key_state(SHIFT)` | **0** |
| `get_key_state(VK_F24)` 未按键 | 0（排除「恒读非 0」的伪实现） |
| 解绑 | True，进程存活 |

`get_key_state` 实为 `GetAsyncKeyState`（物理键态）—— SHIFT 的 **1→0** 说明
`key_down/up` 真正改变了物理键态；配合 F24 的 0 构成可证伪判据。

`get_cursor_pos` 在绑定态返回 **(660,856)**，与 `client_to_screen(2,2)=(1242,685)` 不等 ⇒
**物理光标未动**（另见 2.3，这是 `windows` 模式的预期行为，该比对对后台模式无判别力）。

### 2.2 硬判据：原生 Win32 靶子 + WndProc（关键）

为避免「API 空转返 True 而什么都没发生」，用一个**自建原生 Win32 窗口**做靶子，
WndProc 直读消息 lParam。点击只落在自建窗口 ⇒ **对游戏零副作用**。

| 消息 | 收到 | 内容 |
|---|---|---|
| `WM_MOUSEMOVE` | 1 条 | `(119,72)` vs `move_to(119,72)` → **精确一致** |
| `WM_LBUTTONDOWN` | 1 条 | `(119,72)`，wParam=1 (MK_LBUTTON) |
| `WM_KEYDOWN` / `WM_KEYUP` | 2 条 | wParam=16 (VK_SHIFT) |

**结论：键鼠通路真机可用** —— 输入以窗口消息形式精确到达目标，坐标无偏移。

> 附注：`key_down/up` 的 wParam 是 VK（16=SHIFT，正确）；探针打印的 lParam 高位对键盘消息
> **不是坐标**（`-16342` 是扫描码/标志位），仅鼠标消息的 lParam 才是客户区坐标。

### 2.3 靶子方法学：连续三次纠正（值得复用）

| 方案 | 结果 | 根因 |
|---|---|---|
| ① 系统 `GetCursorPos` 回读 | **无效** | `windows` 模式是**消息式**（`WinMouse.cpp:300-303`：`SendTimeout(_hwnd, WM_MOUSEMOVE, ...)`），物理光标根本不动。实测读到 (1900,1539) = 操作者自己的鼠标 |
| ② Tk `<Motion>` 绑定 | **无效** | Tk 依据**真实光标位置**生成 Motion 事件，对不动物理光标的消息式投递不产生事件（实测 0 条）。**靶子不适配，不是 op 缺陷** |
| ③ 原生 Win32 窗口 + WndProc | **有效** | `SendMessageTimeout` 同线程直调 WndProc，消息与 lParam 可逐条核对 |

**可复用结论**：验证「后台消息式输入是否到达」**必须**用原生窗口读 lParam；
Tk/Qt 等框架层的鼠标事件依赖真实光标位置，**不能**作为消息式输入的判据。

### 2.4 `dx/dx/dx` 与 `gdi/windows/windows` 的差异

- `gdi` + `windows`：`WinMouse` 后端，走 `IN_WINDOWS` 分支 → 消息投递（2.2 已验证）
- `dx` + `dx`：`DxMouse` 后端（注入式），同样不改物理光标，API 调用面全通 + 不崩

两类后端本轮「消息到达」硬证据取自 `windows` 模式；dx 模式的到达验证需在游戏内观察，
或用 dx 模式绑自建窗口（当前 `DxMouse` 对非 D3D 窗口不适用），**未覆盖**。
