### 4.3 `move_r` 相对位移偏差 —— 系统指针加速，非 op 缺陷

实测倍率（注册表 `MouseSpeed=1, MouseThreshold1=6, MouseThreshold2=10, MouseSensitivity=10`）：

| 请求 dx | 实际 dx | 倍率 |
|---|---|---|
| +10 | +16 | 1.60 |
| +20 | +42 | 2.10 |
| +50 | +170 | 3.40 |
| +100 | +372 | 3.72 |
| +200 | +774 | 3.87 |

倍率**随幅度非线性上升** = Windows 指针加速曲线。op 的 `MoveR` 在 `IN_NORMAL` 模式下走
`SendInput(MOUSEEVENTF_MOVE)`（**相对**鼠标单位），必然经过 OS 加速/灵敏度换算；而 `MoveTo` 走
`MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`，实测像素级精确。

> **结论（要写进使用约定）**：要精确落点用 `move_to`；`move_r` 只能当"大致挪一下"，不能做像素断言。

### 4.4 新增语义发现（非缺陷，但容易踩）

| 项 | 事实 | 影响 |
|---|---|---|
| **`add_dict` 只吃单条字形** | `detect_text_entry_format` 按 `$` 切分：3 段 = op 单条、4 段 = 大漠单条，其余 = unknown → False。而 `fetch_words` 输出是**多行**（每行一条） | 多行产物直接喂 `add_dict` **必然 False**；要逐行加，或走文件（`set_dict` 内部逐行解析）。建议文档补一句 |
| **`set_ocr_engine` 忽略 engine/dll 参数** | 源码 `OnnxOcrEngine::init` 内 `(void)engine; (void)dllName;` —— 内置 ONNX 引擎不读这两个参数 | 传不存在路径**仍返 True**（因为它加载的是内置模型）。唯一拒绝路径 = `http*`/`tesseract`/`paddle` 别名（HTTP 后端未编译）→ 返 False |
| **本地字库优先级高于 AI 引擎** | `FindStr/FindStrEx/AutoOcr*` 都是 `if (!dict) → AI 引擎 else → 本地字库` | 字库 0 里残留字符会让后续测试**整体换口径**（本轮就出现过：D 段装完字库后 E 段全返 `'xxxx'`）。测 AI 路径前必须 `clear_dict(0)` |

## 6. 阶段 3：真实点击 / 按键 / 后台消息 / 布局 / 注入 / 字库完整闭环（84 PASS / 3 FAIL / 4 NOTE）

报告：`report_phase3.md`。**不碰游戏** —— 用 Python + ctypes 自建 Win32 窗口当靶子（WndProc 把收到的

### 6.1 核心手法：自建靶子窗口

| 设计 | 作用 |
|---|---|
| WndProc 记录 `WM_LBUTTONDOWN/UP/DBLCLK`、`WM_RBUTTON*`、`WM_MBUTTON*`、`WM_MOUSEWHEEL`、`WM_MOUSEHWHEEL`、`WM_XBUTTON*`、`WM_KEYDOWN/UP/CHAR` | 断言"消息真的到达窗口"，而不是只看返回值 |
| 窗口**故意不激活**，绑 `mouse="windows"` | 直接证明**后台消息投递**语义（真后台：`get_foreground_window() != 靶子`） |
| 另建 3 个窗口 | `layout_windows` 可自主验证（3 个窗口被摆成 2 列宫格） |
| 黑底白字 `AB12`（Consolas 48px，`CreateFontW` 在 WM_PAINT 外建一次） | `extract_word_rects` 稳定切出 **4 块**；字库闭环 21 项全绿 |

**踩坑（值得固化）**：`CreateFontW` 是 **14 个参数**（5 int + 8 DWORD + 字符串）。argtypes 少写一个时
ctypes **不会静默容忍**，而是在 WndProc 回调里抛异常 → 回调返回 0 → **窗口安静地不画字**，最后表现为
"字库功能全 FAIL"。所以脚本里加了一条**自检**：先手写解析 BMP 数白像素（`bright_pixels`，不依赖 PIL），
`亮像素 = 1564 / 唯一色 48` 通过后才继续 —— 避免把"图的错"算成 op 的错。

### 6.3 两个真缺陷（本轮新增，均已定位到行）—— **两个都已修**

> 都是**返回值/参数推导**类，不是 hook 或显示链路问题。① 与 ② 均于 2026-09-28 夜修复并回归。

**① `inject_dll` 永远无法上报失败**（`libop/op/OpProcess.cpp:41`）—— ✅ **已修**

```cpp
// 修复前：失败返回 -1..-7 被直接透传，调用方把 -1 判成"成功"
internal::set_result(ret, DllInjector::InjectDll(pid, dll_name, error_code));
// 修复后：归一化为对外约定的 0/1，失败原因落 __op.log
internal::set_result(ret, injected > 0 ? 1L : 0L);
```
`DllInjector::InjectDll`（`DllInjector.cpp:85`）在失败时返回 **-1 ~ -7**，而 C API / Python 绑定 / 大漠约定
都是「0 = 失败、非 0 = 成功」，`_ok()` 里 `if value:` 把 **-1 也判成成功**。唯一返 0 的路径是
`EnablePrivilege` 失败 ⇒ **该 API 实际上永远返回成功**。

实测：`inject_dll("no_such_process_xyz.exe", minhook.x64.dll)` → **True**；
`inject_dll("python.exe", <不存在的 dll>)` → **True**。（`error_code` 被 `op::Op::InjectDll` 丢弃。）

最小修法：`set_result(ret, inject_ret > 0 ? 1 : 0)`，配套 `m_context->set_last_error`（另议）。

**② `run_app(cmd, mode=1)` 在裸文件名下必失败**（`libop/window/WindowProcess.cpp:314-328`）—— ✅ **已修**

`mode==1` 时用 `pos = cmd.find(".exe")` 反推工作目录；若往前找不到 `\` 或 `/`（裸文件名就是这种情况），
`pos` 保持不变 → `curr_dir = cmd.substr(0, pos)` 把 `"notepad.exe"` 截成 **`"notepad"`**，当作
`lpCurrentDirectory` 传给 `CreateProcessW` → 返回 **ERROR_DIRECTORY(267)**（`__op.log` 实测）。

| 调用 | pid | 结论 |
|---|---|---|
| `run_app("notepad.exe", 1)` | 0 | ❌ 缺陷（err=267） |
| `run_app("notepad.exe", 0)` | 32120 | ✅ |
| `run_app("C:\Windows\System32\notepad.exe", 1)` | 38300 | ✅ |
| `run_app("C:\Windows\System32\notepad.exe", 0)` | 通常 ok | ✅ |
| `run_app("%windir%\system32\calc.exe", 1)` | 0 | 期望行为（`CreateProcessW` 不展开环境变量，须用全路径） |

最小修法：只有 `pos` 确实落在分隔符上（或 `cmd.find_first_of("\\/") != npos`）才设置 `curr_dir`，
否则传 `nullptr` 让新进程继承当前目录。

**实际修法**：把目录推导抽成 header-only 纯函数 `libop/window/RunAppPath.h`
（`op::runapp::ExtractAppDirectory`，零 Windows 依赖 → 可直接编进测试做边界用例）。
「返回空串」= 无法确定 = 调用方传 `nullptr`。同时修掉旧实现两个次生问题：
循环条件 `i >= 1` 漏掉索引 0 的分隔符（`\notepad.exe`）；`C:\a.exe` 得到 `C:`
（那是「C 盘当前目录」而非根目录）→ 补成 `C:\`。

测试 `tests/run_app_path_test.cpp`（9 条）：7 条边界（裸文件名 / 全路径 / 盘符根 / 前导分隔符 /
带引号含空格 / 退化输入 / 非 .exe 后缀）+ 2 条端到端真起 notepad。
**反向验证**：改回"找不到分隔符就不重置 pos" → 3 条如期 FAIL（含端到端那条 pid=0）。

修复后实测（同步后的 dll，sha1 `7363be458ee1`）：`run_app("notepad.exe", 1)` → **pid=13000 且存活**
（修复前恒 0）。

### 6.4 一次误判与回滚：`find_pic` 的 `-1` **不是**缺陷（重要判据）

顺着 ① 做"出口层不得泄漏负错误码"同族排查时，扫出 `OpFindPic` 有 **4 条失败路径返回 -1**
（`!handle` / 两个 catch / `OpImage.cpp` 的 `-1L` 初值），实测未绑定、bind 到无效 hwnd、区域非法
**一律返回 -1**，于是把它按"布尔契约"改成了 0 —— **错了**。

`FindPic` 走的是**大漠索引语义**：返回值是**命中的图片序号**，`-1 = 未找到`。既有测试
`ImageColorTest.FindPicReturnsMinusOneWhenTemplateIsMissing` 明确钉住了它（连 `OpFindPic(nullptr)`
都断言为 -1）。改成 0 会让"未找到"与"命中第 0 张图"无法区分 —— 比原状更糟。

**判据（改任何出口层返回值前先问）**：这个 API 的返回值是**布尔**还是**索引/句柄/计数**？
- 布尔（`inject_dll` / `bind_window` / `run_app`）：内部 `-N` 是**私有错误码**，必须归一化到 0/1；
- 索引/计数（`find_pic` / `find_color` 的坐标 / `get_dict_count`）：`-1` 常常是**对外契约值**，
  有既有测试钉着，**不能**按布尔契约改。

本轮已回滚为原行为，只在两处加了澄清注释（`OpImage.cpp` / `op_c_api.cpp`），防止下次再"好心修复"。
全量回归确认 0 FAILED。
