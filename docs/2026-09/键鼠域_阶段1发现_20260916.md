## 五、核心发现：9 条 SKIP 的真实机制（证据链，可复跑）

### 5.1 推翻旧结论

旧记"13 条 DX 用例 SKIP 是环境不支持 / 门槛 A 未满足" —— **本轮实测推翻**。

### 5.2 单跑即 PASS

```
op_test --gtest_filter=MouseKeyTest.DxModeFeedsDirectInputBufferedData
  → [       OK ] (1278 ms)          # 全量跑却 34ms SKIP

op_test --gtest_filter=MouseKeyTest.DxModeDeliversAdvancedMouseButtonsAndWheel
  → [       OK ] (1940 ms)          # 全量跑却 SKIP

op_test --gtest_filter=MouseKeyTest.DxModeFeedsDirectInputBufferedData:MouseKeyTest.DxModeDeliversWindowAndRawInput
  → [  PASSED  ] 2 tests.
```

**→ 不是环境门槛，是顺序依赖的状态污染。**

### 5.3 二分定位污染源

| 前置用例 | 之后跑 `DxModeFeedsDirectInputBufferedData` |
|---|---|
| `DxModeChannelSwitchStopsWindowMessages`(820) | **OK** ✅ |
| `DxModeChannelSwitchStopsRawInput`(874) | **OK** ✅ |
| `BindWindowDxSuffixDefaultsToAllWhenNoSuffix`(927) | **SKIP** ❌ |
| `BindWindowDxSuffixNarrowsToDinput`(939) | **SKIP** ❌ |
| `BindWindowDxSuffixCombinesMouseKeypad`(950) | **SKIP** ❌ |

**污染源 = 927 / 939 / 950**（950 只是继承者）。

### 5.4 差异点：显式解绑 vs 依赖析构

```cpp
// 874 用例（结尾 912-914）—— 显式解绑，窗口仍存活
long unbind_ret = 0;
op.UnBindWindow(&unbind_ret);       // → 远端 hook 正确 release，后续 OK
EXPECT_EQ(unbind_ret, 1);

// 927 用例（932-937）—— 无 UnBindWindow，靠析构
op.BindWindow(hwnd, L"normal", L"dx", L"windows", 0, &ret);
if (ret != 1) GTEST_SKIP();
op.GetDxAttr(&ret);
EXPECT_EQ(ret, DX_ATTR_ALL);        // ← 函数结束，无 UnBindWindow
```

而用例内声明顺序决定了析构顺序（C++ 后声明者先析构）：

```cpp
op::Op op;                 // 先声明 → 后析构
MouseEventWindow window;   // 后声明 → 先析构 ★ 窗口先被销毁
```

→ `op` 析构时才调 `UnBindWindow`，此时**窗口已销毁**。

## 六、【产品缺陷】hook 残留 → 目标进程内 dx 永久失效

**不是测试问题，是产品缺陷。** 链路如下（每步可核对）：

**① 窗口已销毁时解绑不生效** — `libop/hook/InputHookClient.cpp:66-92`
```cpp
long call_release_input_hook(HWND hwnd) {
    DWORD pid = 0;
    ::GetWindowThreadProcessId(hwnd, &pid);   // 窗口已销毁 → pid = 0
    if (pid == 0)
        return 0;                             // ★ 直接返回，远端 hook 永不释放
    ...
}
```
宿主侧 `g_bind_refs` 该条目仍被 erase（`:229`），**宿主认为解绑成功，远端实际仍 hooked**。

**② 远端状态残留** — `libop/hook/HookExport.cpp:89-98`
```cpp
long __stdcall ReleaseInputHook() {
    if (InputHook::is_hooked && g_input_ref_count > 0 && --g_input_ref_count == 0) { ... }
    return 1;                                  // 没被调用 → is_hooked 保持 true
}
```
残留项：`is_hooked = true`、`input_hwnd = 已销毁的旧窗口`、`g_input_ref_count = 1`、MinHook 未卸载、WndProc 仍是 `opWndProc`。

**③ 后续任何新窗口绑定都被拒** — `libop/hook/HookExport.cpp:72-87`
```cpp
long __stdcall SetInputHook(HWND hwnd_, int) {
    if (!InputHook::is_hooked) { ret = InputHook::setup(hwnd_); ... }   // 走不到
    else if (InputHook::input_hwnd == hwnd_) { g_input_ref_count++; ret = 1; }  // 旧 hwnd ≠ 新 hwnd
    return ret;                                // ★ ret = 0 → 绑定失败
}
```

**④ 宿主侧表现为绑定返回 0** → `BindWindowEx` 折叠成 `return 0` → 上层看到"绑定失败"，无原因码。

### 影响面（真机场景）

| 场景 | 结果 |
|---|---|
| 脚本绑 dx → 正常调 `UnBindWindow` → 绑新窗口 | ✅ 正常（874 用例即此路径） |
| 脚本绑 dx → **目标程序先退出/窗口先关闭** → 解绑或析构 | ❌ 目标进程内 hook 残留 |
| 同上，随后脚本**重启重试绑定** | ❌ **仍失败**（hook 在目标进程内，目标不重启就清不掉） |
| 宿主进程自身反复 bind/unbind | ❌ 一旦踩中，后续全废（本轮 9 条 SKIP 即此现象） |

**这与"DX 三通道代码已落地但从未真机验证"叠加**：真机验证（BlueStacks）每次都是干净的 bind→验证→退出，从未覆盖"解绑后重绑"路径，所以该缺陷此前未被发现。

### 修复方向（三选，可组合）

| 方案 | 位置 | 改动量 | 风险 | 效果 |
|---|---|---|---|---|
| **F1 缓存 pid** | `InputHookClient.cpp`：`g_bind_refs` 值从 `long` 扩为 `{refs, pid}`，UnBind 时 `pid==0` 则用缓存 pid attach | ~25 行 | 低（进程已退出则 attach 失败，与现状一致） | 修主因 |
| **F2 自愈重绑** | `HookExport.cpp`：`is_hooked && input_hwnd != hwnd_` 时先 `release()` 再 `setup(hwnd_)` | ~8 行 | 中（多窗口并发会互踢；但当前设计本就是单 hook） | 兜底，彻底消除"永久失效" |
| **F3 测试补显式解绑** | `mouse_keyboard_test.cpp` 927/939/950 各补一行 `op.UnBindWindow(&ret)` | 3 行 | 无 | 解锁 9 条 DX 用例，但**不修产品缺陷** |

**按"够用原则"推荐：F1 + F3**（F1 修根因、F3 立刻解锁回归覆盖）。F2 属"更彻底"，可记录为可选。
