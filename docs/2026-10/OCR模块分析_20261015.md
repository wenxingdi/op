## 结论概览

热路径（免字库 ONNX 推理）质量不错且有大量加固注释；问题集中在**推理输入的冗余大拷贝（O1）**、**两处样板重复（O2/O8）**、**几个微项（O3/O5）**。字库维护路径（AddDict/FindDict）有 O(n²) 线性扫描（O7）。O4/O6 是行为敏感项，列观察。

## O1【效率·中·推荐做】`ort_run` 每次推理全量拷贝输入张量

**位置**：`OnnxOcrEngine.cpp` L199-218。`std::vector<float> buf(in)` 只为满足 `CreateTensor` 的非 const 指针签名。

**成本**：det 输入 960×960×3 float ≈ **11MB memcpy 每次 OCR 调用**；rec 输入 320×48×3 ≈ 184KB × 每个检测框。ORT 推理不写输入张量，直接 `const_cast<float*>(in.data())`（或改 ort_run 签名收 `const std::vector<float>&` + const_cast）即可整份省掉。低风险高效益——免字库 OCR 是最高频接口，直接收益每次调用 11MB 内存带宽。

## O2【精简·中】`HttpOcrService::ocr/ocr_line` 懒初始化样板 ×2

**位置**：`OcrService.cpp` L295-331。两个函数的「加锁 → 判空 → 懒初始化/失败记忆 → 快照 shared_ptr」块几乎逐行相同（仅日志前缀不同）。提取 `lazy_engine(const char *caller)` 助手，-25 行左右，无行为变化。

## O3【精简·微】`db_postprocess` 死参数 + 变量遮蔽

**位置**：`OnnxOcrEngine.cpp` L224。签名收了 `float sx, float sy` 但函数体从未使用（坐标映射用 `iw/WW`、`ih/HH`，注释已说明）；循环内 `int mx = int(cw*0.1f)+5`（外扩量）遮蔽外层 `float mx`（sigmoid 探测的最大值）。删死参数（调用点同步删 `sx/sy` 实参）、内层改名 `pad_x/pad_y`。纯整洁性。

## O4【观察项·记录不动】`pca_angle` 等权 PCA 求的是矩形主轴而非文字主轴

**位置**：`OnnxOcrEngine.cpp` L157-180。对**所有像素等权**累加坐标——求出的是裁剪框（矩形）的主轴方向，不是墨迹分布。文字行裁剪通常是扁矩形（w≫h），此时矩形主轴≈文字方向，配合 `w>1.3h` 守卫工作正常；但方形/紧凑裁剪下"倾斜校正"名不副实。改成暗度加权才名副其实，**会改变倾斜校正触发行为**（OCR 精度影响需真机验证）——列观察项不动。

## O5【精简·微】`is_removed_remote_backend` 手写 trim+tolower

**位置**：`OcrService.cpp` L61-71`。手写循环与 Utils 的 `to_lower_copy(trim_copy(...))`（同文件 #ifdef 上半分支就在用）重复；注释称"自包含实现"，但 `base/Utils.h` 明明已 include。一行替换，-13 行。

## O6【观察项·效率】`to_bgr` 整图拷贝可零拷贝（bpp=3 时）

**位置**：`OnnxOcrEngine.cpp` L68-91。输入已是 bpp=3 时仍完整拷贝一份 BGR。若给 `BGR` 加"借用视图"模式（at() 按 3 字节步进直读原 data，旋转/缩放等写操作前再物化），可省一次整图 memcpy（大图 8MB+）。要动 BGR 结构所有权语义，**风险中**，且 det 前必有 resize_bilinear（整读一次）——收益主要在 ocr_line 单行直识路径。列观察项，O1 落地后再评估是否值得。

## O7【效率·中】`Dictionary::find` 线性扫描 → AddDict/Erase 字库维护路径 O(n²)

**位置**：`Dictionary.h` L669-674。`find` 全字库逐条 `operator==`（后者还逐字节比 data）。`add_word`/`erase` 都走它：AddDict 批量导入 n 条 → O(n²) 次全等比较。字库几百到几千字时是百万级比较。方案：`add_word(word1_t)` 先按 `(w,h,bit_cnt)` 分组内查（words 本来 stable_sort 后同尺寸相邻，`sort_dict` 后可用 `equal_range` 风格范围查找），行为不变纯提速；或另挂 `std::unordered_multimap<key, index>` 索引。中优先级——识别热路径不走 find（匹配走 _bin_ocr），字库维护频率低，但批量导入可感知。

顺手微项：`word1_t::operator==` 的 data 比较改 `memcmp`（编译器可能已优化，改了更稳）。

## O8【精简·微】`read_dict_dm` / `read_memory_dict_dm` 完全同构

**位置**：`Dictionary.h` L539-591。两函数逐行相同，仅流来源（fstream/stringstream）与行解析入口（dm 专用/格式分发）不同。提取公共 `read_text_lines(stream, importer)`。另：`idx1/idx2 = find('$')` 预检与 parse 内部的 `split('$')` 重复扫描，预检可并入（parse 失败即跳过）。微项。

## 其余结论（无实质问题）

- **OnnxOcrEngine 热路径**（det 前处理/DB 后处理/CTC 解码/倾斜校正守卫/置信度口径）注释完整、数值处理有判据（sigmoid 自探测、softmax 白名单子集归一、[N,T,C]/[N,C,T] 双布局），无实质问题。
- **懒初始化锁纪律**（m_mutex 只护引擎选择、推理在锁外、shared_ptr 快照防销毁）已按 OP_OCR_INTERNAL_PLAN 9.2 落地，单例 leak-by-design 有 minidump 依据注释，不动。
- **HTTP 远程后端**整个 `#ifdef OP_ENABLE_HTTP_OCR_BACKEND` 块（~200 行）当前编译期休眠，属可选远程兜底，保留。
- **字库文件格式**（v0/v1 兼容、内存格式嗅探、dm 文本兼容层）近年已有加固（长度校验/hex 校验/ACP 转换线程安全化），无实质问题。
- `word_t/word1_t::operator==` 非 const 成员（历史写法，能编译）——记录不动。

## 提速空间分析（2026-10-15 17:34 追加，随第八批一并记录）

通读 `OnnxOcrEngine.cpp` 全链（读图 → det 前处理 → det 推理 → DB 后处理 → 逐框 crop/矫正 → rec 推理 → CTC 解码）后的结论，按收益排序：

1. **rec 批量推理【最大杠杆，需用户拍板】**：当前每个检测框单独一次 `session.Run`（单行约 10-15ms，N 框串行 N 次）。`rec_image` 本来就统一 pad 到 320×48，输入尺寸一致，可将 N 个 ROI 叠成 `{N,3,48,320}` 一次 Run，CTC 逐行解码（输出按 n 切片传 `{1,T,C}` 给 `ctc_greedy`）。文本密集场景 N=10 可从约 100-150ms 降至约 20-30ms。数学等价但 batch 数值可能有微差，属"行为邻近"改动，须用户确认后实施。
2. **PCA 惰性化【零行为，可直接做】**：`ocr()` 每框无条件 `pca_angle(roi)`（三趟 double 全像素遍历），但旋转守卫 `w>1.3h` 仅用 roi 尺寸——把 pca 挪进守卫内，非扁矩形框（大多数）直接跳过。
3. **中项（动 BGR 结构，O1 落地后再评估）**：crop+resize 融合（每框省一次区域拷贝，从源图直接采样缩到 48 高）；det 的 resize+normalize 融合（省 11MB 中间图）；bpp=3 零拷贝（即 O6）。
4. **微项**：两次 3×3 膨胀合并为一次 5×5（结构元近似，需核对）；det 输出 `out.assign` 约 3.6MB 拷贝可让 `db_postprocess` 直接读 tensor 内存。
5. **只记录不调**：det 上限 960 降 736 可快约 1.7× 但伤小字召回，属精度权衡，仅作为可调参数提示。

参照基线：sopts 已 `min(4, 核数)` 线程，rec 单行 4 线程约 10-15ms（注释记载目标 9-13ms），线程数已无压缩空间。
