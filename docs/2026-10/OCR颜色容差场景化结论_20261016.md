# OCR 颜色容差场景化结论（2026-10-16 实测批次）

## 数据来源

- 游戏绑定窗口 dx 后台截图，区域 180x22（客户区坐标 1173,0,1353,22），`D:\GMPLUG\net10.0-windows7.0\captures` 下 58 张有效样本（另有 7 张其他区域/误截已剔除）
- 文本特征：彩色字（红 E01111 / 绿 33EE33 等，随场景切换）+ 深红花纹装饰底，字高约 20px
- DLL：op 9a1111a 构建（x64 sha1=5180ac260bdc），识别 AutoOcrFromFile 路径，sim=0.8

## 结果矩阵（合格率 = 匹配 `名字[-数字,数字]` 结构）

| 参数 | 合格率 | 说明 |
|---|---|---|
| E01111（默认 0x60） | 3/58 (5%) | 0x60 逐通道容差把近色花纹底/边缘渐变混进 mask，乱码 |
| E01111-000000（零容差） | 红字部分可用，小字碎裂 | 上一轮白底场景的结论，不适用本场景 |
| E01111-101010 ~ 303030 | 49/58 (84%) | 红字帧全对；9 张空结果全是**绿字帧**（颜色不匹配 mask 为空） |
| E01111-202020\|33EE33-202020（双色枚举） | **58/58 (100%)** | 字色变化场景的标准解法 |
| OcrAutoFromFile（原图直识） | 1/58 | 花纹底干扰 det，结构残缺（掉 `]`/`,`、数字误读） |
| CvToBinary(Otsu) → 直识 | 0/58 | 全局 Otsu 被花纹底打败，不可用 |

## 结论（已写入 api_llm.md/json + api_reference.html）

1. **容差按场景选，不存在通用默认值**：
   - 浅色底（白/浅灰）+ 深色小字 → 不带偏色段走默认 0x60（包全抗锯齿笔画）
   - 深色/花纹底 + 彩色字（游戏 UI 典型）→ 显式小偏色 0x10~0x30；0x60 是坑
2. **字色随场景变化 → `|` 枚举多色**（str2colordfs 原生支持），如 `E01111-202020|33EE33-202020`
3. **偏色段必须写满 6 位十六进制**：`E01111-20` 会被 str2color 静默解析成 b/g 通道错位值（swscanf 部分成功），行为诡异且无告警——潜在加固点
4. 花纹/装饰底上原图直识与 Otsu 均不可用，颜色二值化仍是唯一可靠路径
