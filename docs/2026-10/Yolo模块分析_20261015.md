# YOLO 模块分析（2026-10-15，逐模块专项第 7 弹）

> 范围：`libop/yolo/` 全部——引擎抽象（YoloService）、检测器单例（YoloDetector）、
> ONNX 引擎（OnnxYoloEngine，461 行）、HTTP 引擎（HttpYoloEngine，编译期休眠）。
> 分析方法同前：先出清单 → 用户确认 → 再实施。

## 结构总览

```
YoloDetector（单例，故意泄漏同 OCR；m_mutex 串行化 detect）
  └─ YoloEngine（抽象）── OnnxYoloEngine（pimpl 隔离 ORT 头）
       模型来源：内置资源段 / 外挂 .onnx；输出形状自适应 v5/v8/v11
       预处理：私有极简 BGR 容器 → letterbox(灰114) → CHW/255 RGB
       后处理：候选解码 → 类别感知 NMS → 类别名（metadata / --labels / @file）
       HTTP 引擎整个 #ifdef OP_ENABLE_HTTP_YOLO_BACKEND 休眠（同 OCR 远程后端）
```

整体评价：模块年轻、结构干净（pimpl、锁纪律、懒加载、明确的错误码链
-1~-9），版本自适应解码注释完整。**主要问题是一个跨模块重复**：极简 BGR
图像工具链与 OCR 模块逐字节相同。

## Y1【精简·中】极简 BGR 图像工具链与 OCR 逐字节重复（跨模块）

**位置**：`OnnxYoloEngine.cpp` L26-132（匿名命名空间）vs `OnnxOcrEngine.cpp` 同名区域。
**实证**（脚本逐函数提取对比）：`struct BGR`、`make_bgr`、`to_bgr`、
`resize_bilinear`、`utf8_to_wstring` **五个函数/结构 byte 级相同**
（OCR 另有多出的 `crop/rotate/pca_angle/planar_rgb_imagenet` 等自用件，不在此列）。

**方案**：提取到共享头 `libop/algorithm/MiniImage.h`（algorithm = 内部通用计算逻辑，
现有 AStar.h/PathTools.h 同类），命名空间 `op::img`。两个引擎删本地副本改 include，
纯搬运零行为变化（函数体 byte 级相同）。预计 -110 行 ×2，新增共享头 ~120 行。

## Y2【效率·微】`ort_run` 每次 detect 拷贝 4.7MB 输入

**位置**：`OnnxYoloEngine.cpp` L137 `std::vector<float> buf(in); // CreateTensor 需要非 const 指针`。
与 OCR 第八批 O1 完全同型：640×640×3 float = 4.7MB，每次 detect 一次 memcpy。
**OCR 批已实证 ORT Run 不写输入张量**——同样改 `const_cast<float*>(in.data())` 借用，
注释引用同一依据。零行为变化。

## Y3【观察项·记录不动】`to_bgr` bpp=3 整图拷贝

**位置**：`OnnxYoloEngine.cpp` L73-78。输入已是 BGR 仍完整拷贝一份。
与 OCR O6 同型：要动容器所有权语义，且 letterbox 前必有 resize 整读，
收益主要是理论上的。列观察项。

## 其余结论（无实质问题）

- **版本自适应解码**（v5 objectness / v8v11 通道前后双布局，anchor 数由输入尺寸推得）
  与**类别感知 NMS**实现标准、注释完整；`parse_names_dict` 有 4096 索引防御。
- **单例锁纪律**与 OCR 对齐：init/detect 持锁、engine 切换有 dynamic_cast 检查、
  release 回默认引擎；OP_HAS_ONNX=0 的 x86 路径空指针保护齐全。
- **HTTP 引擎**（143 行）整个 `#ifdef OP_ENABLE_HTTP_YOLO_BACKEND` 休眠，属可选远程
  兜底，保留（同 OCR 批结论）。
- **`is_removed_remote_name`** 的手写 tolower 循环：network 已移出构建，
  `#ifndef` 分支拿不到 Utils 助手（OCR O5 同款约束），**保持手写不动**。
