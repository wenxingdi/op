# com/ + c_api/ 门面模块分析（2026-10-15，逐模块专项第 12 弹）

> 范围：`libop/com/`（COM 自动化门面：OpAutomation 257 个 STDMETHODIMP +
> IDispatch Invoke + ComVariant 出参封送 + ATL 注册胶水）与
> `libop/c_api/`（C ABI 门面：op_c_api.cpp 1716 行，~230 个导出）。
> 两门面同包一层 `op::Op`（include/libop.h 268 个入口），分别服务
> 易语言/VBScript/PowerShell（COM late-binding）与 C/ffi 调用方。

## 结构总览

```
OpAutomation.cpp  1857  257 方法，绝大多数 4-8 行直通 obj
op_c_api.cpp      1716  ~230 导出，217 个已走 call_* 异常骨架
ComVariant.h        88  InLong/OutLong/SetOutValue/RunCvRetOnly（已有测试覆盖）
op.cpp/dllmain/compreg/stdafx  ~100  ATL 胶水，无逻辑
```

整体评价：**本模块是全场"薄门面"的正面样本，此前已被收拢过一轮**——
c_api 侧 217/227 导出已收进 `call_int/call_ret/call_intptr/call_string/
call_json_string/call_memory` 六个异常骨架；COM 侧出参封送已抽 ComVariant.h
并挂回归网。剩余问题不多，真 bug 仅一处（CB1），其余是"收益审美向"的
可选收拢。

## CB1【fix·真 bug】GetScreenDataBmp x86 分支缺空指针校验

**位置**：`OpAutomation.cpp` L1093-1122。空指针校验（`!data || !size || !ret`）
只在 `#if OP64` 分支里（L1096），x86 分支（L1102-1107）直接
`data->vt = VT_I4; data->lVal = 0;`——x86 下调用方传 null VARIANT* 即在
目标进程 AV。仓库实际发布 x86 DLL（op_c_api_x86.dll 同步副本存在），
不是死配置路径。同方法 GetScreenData（L1081）两边都有校验，属明显笔误。
**方案**：把校验移到 `#if` 之前，与 GetScreenData 对齐。零行为变化
（非空路径逐字节相同），-2 行。

## CB2【精简·低·可选】OpAutomation 字符串出参模式 83 处

**位置**：`OpAutomation.cpp` 全文件。`wstring s; obj.X(..., s);
return CopyOutBstr(ret, s);` 重复 83 次（grep：CopyOutBstr ×83、
`wstring s;` ×81），加上 `return S_OK;` 直返模式共 147 处。
唯一收拢手段是宏（方法名/实参各异，模板无从下口）：
`#define OP_COM_BSTR_OUT(call) do { std::wstring s; obj.call; return CopyOutBstr(ret, s); } while (0)`。
预计 -160 行。
**不建议做的理由**（与前几个模块的收拢不同）：这里每个方法体只有 3 行、
名字即文档，宏化后断点/堆栈/文本搜索全部失真，且 STDMETHODIMP 方法
签名仍须逐个保留——**省的是行数，损的是门面层最需要的可检索性**。
裁定建议：跳过，除非用户明确要求行数指标。

## CB3【精简·低·可选】c_api 四处手写 try/catch 多出参函数

**位置**：`op_c_api.cpp` L878-906（OpFindPic）、L999-1019（OpGetScreenData）、
L1021-1046（OpGetScreenDataBmp）、L1048-1068（OpGetScreenFrameInfo）。
四处因"双出参 + 指针返回值 + 异常时回写默认值"的复合语义没进 call_* 骨架。
可提 `call_multi_out` 模板收拢，预计 -50 行；但四个函数的回退值
（-1/0/0/无返回）与回写目标各异，helper 要带 fallback+双 out 指针，
签名复杂化后可读性收益中性。
裁定建议：可选；必要性不大（门面层非热路径，行数不是负债）。

## 效率评估

门面层每次调用的成本（BSTR↔wstring 转换、VARIANT 判型、
Attach/Detach 不在本层）都是 ABI 强制封送，无可压缩项。
Invoke 的 try/catch 是零成本异常模型，不构成开销。
