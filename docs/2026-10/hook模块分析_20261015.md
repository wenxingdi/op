# hook 模块分析（2026-10-15，逐模块专项第 11 弹）

> 范围：`libop/hook/` 全部 27 文件 4882 行——注入式捕获/输入引擎：输入 hook
> （InputHook：DirectInput vtable / win32 键状态 / Raw Input / 窗口过程四通道）、
> 宿主侧 RPC（InputHookClient + BlackBone）、注入侧导出（HookExport + 异常护栏）、
> 显示 hook（DisplayHook + kiero 定位 + D3D9/10/11/12/OpenGL 五后端读回）、
> 导出名解析（HookExportName PE 解析 + 缓存）、按需安全模块加载（ApiResolver）。
> **本模块代码运行在目标进程（游戏）内**，改动正确性要求高于宿主侧。
> 分析方法同前：先出清单 → 用户确认 → 再实施。

整体评价：全场**注释/归因质量最高**的模块——几乎每个函数都带 H 编号归因
（H2 拆钩竞态、H10/N1 staging 缓存与设备失效、H11 围栏有界等待、H14 异常护栏
普查、H20 首帧诊断复位、H23 绑定态发布序、H27 D3D9 MSAA），且多处写明反向验证
方法。**真 bug 仅发现一处低概率缺口（HK5）**；效率上有一处注入热路径的实在浪费
（HK1）；其余是同构代码收拢。已做过的收拢（SharedFrame、staging 缓存、API 缓存）
说明本模块一直在维护，剩余项多为后来新增代码产生的新的重复。

## HK1【效率·高】GetDeviceState/GetDeviceData 热路径每帧一次 GetDeviceInfo

**位置**：`InputHook.cpp` L1158-1201 `hkGetDeviceState` / `hkGetDeviceData`。
两个 detour 每次被调用都先走 `dinput_device_kind()` → `device->GetDeviceInfo()`
（COM 虚调用 + 填 DIDEVICEINSTANCEW 含字符串拷贝）。游戏每帧轮询
GetDeviceState 数次，这是注入进程内的**每帧热路径**，而设备类型其实用
`same_vtable(device, g_mouseVtablePtr/g_keyboardVtablePtr)` 一次指针比较即可判定
——现有 fallback 分支在 `!known` 时本来就是这么判的。
**方案**：改成 vtable 优先：vtable 命中任一已知表直接定种类；都未命中才退
GetDeviceInfo（保留对"代理/包装设备"的兼容路径与 `!known` 尺寸启发式）。
语义可证明等价（GetDeviceInfo 只在 vtable 双未命中时调用，原有分支全部保留），
热路径从一次 COM 调用降为一次指针比较。

## HK2【精简·高】InputHookClient 五处 RPC 函数同构骨架收拢

**位置**：`InputHookClient.cpp` L98-259。`call_release_input_hook` /
`call_set_input_lock` / `call_set_input_attr` / `call_ping_hook` /
`call_cursor_shape` 五个函数共享同一骨架：`GetWindowThreadProcessId → Attach →
resolve_hook_dll → MakeHookRemoteFunction → 调用 → Detach → catch (...)`，
每处 30-50 行，仅导出名片段、参数与异常回退值不同。
**方案**：提 `call_remote_body(pid, fallback, body)` 模板（attach/解析 dll/detach/
异常兜全在骨架里，body 只写导出调用），五处各缩到 ~10 行。预计 -110 行。
差异处理：release 用 pid 且异常回退 -1（骨架加 fallback 参数）；ping 的 attach
失败不记日志（骨架日志做成可关）。宿主侧代码，风险低。

## HK3【精简·中】gl_capture / egl_capture 逐行级重复

**位置**：`OpenGLCapture.cpp` L35-83 / L103-155。两函数 ~55 行仅三处不同：
缓存槽（g_gl* / g_egl* 各三个 atomic）、dll 名（opengl32/libglesv2）、日志文案。
**方案**：提 `gl_capture_common(std::atomic<void *>(&)[3], const char *dll, const char *tag)`，
两路变一行转发。顺带删除 egl 解析失败分支里一段** misplaced 的 DEBUG_HOOK 日志**
（复制残留，条件是 mem.open 却出现在解析失败路径，DEBUG_HOOK=0 时虽为死代码但
严重误导阅读）。预计 -60 行。

## HK4【精简·中】写共享内存块五处重复 + 打开失败策略不一致

**位置**：D3D9 L171-186 / D3D10 L170-186 / D3D11 L170-189 / D3D12 L180-200 /
GL L63-81、L135-153。五处"open mem+mutex → 判容量 → 写帧头+像素 → else 写
裸帧头"块结构相同，但**打开失败的策略四分五裂**：d3d9/d3d10/d3d12 静默跳过
下帧再试，d3d11 与 gl/egl 关捕获。持久失败时前者每帧白付 OpenFileMapping 开销
且不留证据。
**方案**：在 SharedFrame.h 提 `bool write_frame_to_shared(const void *data, int rows,
int cols, int pitch, int fmt)`（GL 直写型另给一个 `bool open_frame_target(...)`
变体或复用同一 helper），五处收敛为一行调用，**策略统一为"记一次日志 + 关捕获"**
（多数派策略；名字由 setup 先于捕获使能发布，打开失败基本只意味着宿主已消失）。
⚠️ 对 d3d9/10/12 是行为统一（向 d3d11/gl 看齐），需用户点头。预计 -70 行。

## HK5【疑似缺口·低概率】D3D12Capture 换设备不失效拷贝队列/读回资源

**位置**：`D3D12Capture.cpp` L87-127, L155-164。`copyQueue_`/`fence_`/
`commandAllocator_` 只在首次创建；重建判据只有 width/height/pitch（L155-157），
**不含设备变化**。D3D11 侧 N1（DxCaptureCommon.h L63-80 注释）专门论证过同一
风险：TDR 恢复/切显卡/独占全屏重建后，旧 context 操作新设备资源是"返回 void、
无报错、静默错帧"。D3D12 的同构场景：新 swapchain 的设备 + 旧设备的
commandAllocator 建命令列表、旧 copyQueue 提交、旧 readback 资源当拷贝目标 ——
跨设备命令提交，校验层报错乃至目标进程崩溃。
**方案**：缓存 `device`（CaptureFrame 里已 GetDevice），设备指针变化时
`copyQueue_/fence_/commandAllocator_/readbackResource_` 整套 Reset（仿 N1）。
发生频率低（需设备重建），但后果对齐 N1 描述的静默错帧。属**行为修正**，修前
建议补一条"重建设备后绑定仍可用"的用例或至少人工过一遍。

**实现细节与清单的差异说明**：

- **HK1 实现为指针→种类缓存**而非清单所述的"vtable 优先"：分析后发现
  mouse/keyboard 设备的 vtable 很可能相同（hook_dinput 中存在按 vtable 去重的
  分支为证），vtable 优先不可靠。改为 8 槽 round-robin 缓存（mutex 保护，
  `release()` 时清空）；残余风险（设备地址复用误命中）已写进代码注释。
- **HK4 实现为 `SharedFrameWriter` RAII 类**（构造 open mem+mutex 并 lock，
  `prepare(hwnd,w,h,&open_failed)` 返回像素区 span，析构 unlock），比清单建议的
  独立 helper 更贴合 GL 直写与 D3D 拷贝两种用法。原有 `make_shared_frame_span`/
  `write_shared_frame` 保留（tests/shared_frame_test.cpp 在用）。D3D11 的
  `static_assert(sizeof(FrameInfo)==28)` 随之保留。
- **HK2 例外**：`call_ping_hook` 保留直接用 MakeHookRemoteFunction——
  收拢后的 `call_hook_export` 无法区分"导出存在但返回 0"与"导出不存在"，
  ping 的真假语义依赖这个区分。

代码净行数（`git diff --numstat -- libop/`）：+297/-245。行数略升的原因是
新增缓存机制（HK1）与 RAII 类（HK4）的一次性结构开销；消除的是五处写帧块、
五处 RPC 骨架、gl/egl 整份重复的实现冗余。
