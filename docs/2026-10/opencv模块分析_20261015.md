# opencv 模块分析（2026-10-15，逐模块专项第 10 弹）

> 范围：`libop/opencv/` 全部 6 文件 5152 行——找图引擎核心：OpenCv 桥接门面
> （OpenCvBridge）、图像处理 helpers（OpenCvHelpers）、模板匹配引擎
> （TemplateMatcher：模板缓存、金字塔预筛、条带并行、缩放/旋转/特征/边缘/形状匹配）。
> 分析方法同前：先出清单 → 用户确认 → 再实施。

## 结构总览

```
OpenCvBridge.h/.cpp   183 行  COM/外部门面：颜色模式解析、4 个 BuildMatchJson、
                              模板名/缩放/角度列表解析、CaptureRegion（截图→ImageHandle）
OpenCvHelpers.h/.cpp 1421 行  ~30 个图像 helper：Mat 视图互转、灰度/二值/边缘/形态学/
                              模糊/锐化/细化、轮廓提取、collectTemplateMatches（全量收集）、
                              findFirstTemplateMatch（四方向分块命中即停）
TemplateMatcher.h     296 行  纯头声明：8 个公开匹配变体、模板缓存管理 7 函数、各枚举
TemplateMatcher.cpp  3217 行  引擎主体：模板缓存（shared_mutex 全局锁 + 缩放档 LRU 清空）、
                              金字塔预筛（≤4 层 + 粗阈值松弛 + definitive_miss）、
                              峰值抑制收集、条带并行、三处"命中即停"worker 循环、
                              ORB 特征 / 边缘 / 形状匹配、缩放自动探测（probe+refine 两阶）
```

整体评价：逻辑密度最高的模块，但工程质量在线——金字塔预筛、退化模板判据
（TM_CCORR_NORMED 零方差 ⇒ 伪命中）、缩放缓存上限、ORB thread_local、
findHomography 几何校验都有带证据的归因注释。**未发现真 bug**；线程模型
（shared_mutex 读 / unique_lock 写 + ThreadPool 分块）干净。问题集中在
**四份复制粘贴的 gray 前导**、**三份同构并行 worker**、一处**已成冗余的旧重载**、
一对**同构细化算法**，以及金字塔粗层一处**全量收集的效率候选**。

## CV1【精简·高】gray 模式"裁 ROI + 转灰度 + origin 回加"前导复制 ×4

**位置**：`TemplateMatcher.cpp` L2549-2564（MatchTemplate）、L2756-2769
（MatchTemplateRotated）、L2868-2883（MatchAnyTemplate）、L2983-2998
（MatchAllTemplates）。四处 16 行代码逐行相同：`clampRegion → crop → toGray →
search_source/search_region/origin_x/origin_y` 赋值，仅失败出口不同
（`result={}` vs `results.clear()` vs 直接 `return false`）。
**方案**：提 `prepareGraySearchSource(source, region, gray_source, origin_x, origin_y,
error)` 返回 `const ImageHandle* search_source + Region`，失败出口仍由调用方各自
处理。预计 -60 行，消除"改一处漏三处"的漂移风险（Rotated 与 Any 的失败出口
今天已有细微差别，正是漂移的实证）。

## CV2【精简·高】三个"命中即停"并行 worker 循环同构

**位置**：`TemplateMatcher.cpp` L1954-2013（findAnyNamedMatchParallel）、
L2017-2075（findAnyStripMatch）、L2078-2167（findAnyNamedStripMatchParallel）。
三处 ~55 行：相同的全局 ThreadPool 取池、`atomic<size_t> next_index` 分发、
`atomic<bool> found` + CAS、`result_mutex` 保护结果、`task.get()` 汇总。仅
"取第 index 个任务 → 执行匹配 → 命中写结果"的载荷不同（模板名 / 条带 /
模板×条带扁平任务）。
**方案**：提泛型 `runFirstHitWorkers(task_count, tryOne, onHit)`，三处收敛为
~15 行载荷定义。预计 -90 行。附带清掉三处 worker lambda 均未使用的 `worker`
形参。

## CV3【精简·中】probeScaleCandidate 旧重载已成冗余

**位置**：`TemplateMatcher.cpp` L1599-1679（独立重载：自带降采样循环）与
L1730-1802（缓存重载：配 `scaleProbeDownsampleSteps` L1713 + 源缓存
`ScaleProbeSourceCache`）。调用点 L1830-1833：`has_source_cache ? 缓存版 :
独立版`——但 `prepareScaleProbeSourceCache` 失败的唯一前提是 source Mat 为空
或 ROI 非法，而独立重载对同样前提也会失败（它第一步就是 createMatView +
clampRegion）。**fallback 分支实际不可能成功**，是缓存版落地时留下的旧路。
**方案**：删独立重载 + fallback 三元，调用点只走缓存版（缓存构建失败直接跳过
该档）。预计 -85 行。回归用 OpenCvTest 缩放相关用例把关。

## CV4【精简·中】thinZhangSuenMat / thinGuoHallMat 骨架同构

**位置**：`OpenCvHelpers.cpp` L981-1035 / L1037-1088。两个 ~54 行函数外壳
完全相同（`/=255` 归一、do-while、step 0/1 两轮、marker 扫描、`&= ~marker`、
`*=255` 还原），仅像素保留谓词不同（跳变数+邻域和+连通积 vs 成对邻域+m 项）。
**方案**：谓词作 `std::function<bool(p1..p9, step)>` 或模板参数，外壳收一份。
预计 -50 行。两算法均有 OCR 预处理调用方，行为必须逐比特不变（谓词原样搬运）。

## CV5【精简·低·观察】findFirstTemplateMatch 四方向 case 可表驱动

**位置**：`OpenCvHelpers.cpp` L262-440 一带：四方向 switch + 四个结构同构的
分块扫描循环（L376-423）。可表驱动为"方向 → (块序, 块内扫描序)"两对迭代器。
属命中即停核心路径，四份 today 逐字节等价，改坏难察觉；**收益 ~40 行，风险收益
比一般，建议仅作观察项**，本批不动。

## CV6【效率·候选】金字塔粗层全量收集换峰值收集 —— 评估后不做

**位置**：`TemplateMatcher.cpp` L535-593 `collectBestCandidates` →
`collectRegionCandidates` → `OpenCvHelpers.cpp` L205 `collectTemplateMatches`
（reserve 后逐像素 push）。粗层阈值 = 用户阈值 - 0.12 松弛，低阈值下粗层
**几乎每个像素都过阈**，候选 vector 接近 O(W×H)（¼ 图也不小），先全收再筛。
而峰值版 `collectPeakCandidates`（L628-736）已存在且注释自证替代意图，
`MatchAllTemplates` 的金字塔路径（L3029 `use_peak_candidates=true`）已在用、
有测试覆盖。
**方案**：金字塔 find-first 路径（pyramidFindAllMatches 的
`use_peak_candidates=false` 分支）也改走峰值版；粗层候选经 refine 后本就由
`suppressOverlappingMatchResults` 按模板半径合并，语义相容。
**这是行为邻近改动**（候选集从"全过阈"变"局部峰"），须全量回归 + 重点看
OpenCvTest 金字塔/条带/多模板用例。预计粗层内存与扫描开销显著下降。

## CV7【效率·微·观察】buildPyramidLevels 每级从原图直接 resize

**位置**：`TemplateMatcher.cpp` L514：`resizeForPyramid(source, W/2^N, …)` 每级
都从原图直接缩小，而非从上一级链式减半。成本多一次大 resize，但 ≤3 级、每次
匹配仅一次，收益小；且链式会变动数值（可能扰动边界用例）。**不建议改，仅记录。**

## CV8【效率·微·观察】alphaToMask 逐像素双循环

**位置**：`OpenCvHelpers.cpp` L683-721。RGBA 打包字节逐像素拆 alpha。可改
stride Mat 视图 + `extractChannel` + `compare`，但仅在模板加载时调用一次，
非热路径。**收益可忽略，仅记录。**

## 观察项（不动）

- **CaptureRegion 全图 memcpy**（OpenCvBridge.cpp）：每帧 `bytes.assign` 全图
  拷贝进 ImageHandle，与 op 层 `with_captured_region` 同款既有设计，跨模块
  议题，维持记录。
- **BuildMatchJson 4 变体**：失败 JSON 文案各有差异，门面层记录；op 层同类
  已在第十二批对齐，bridge 属 opencv 自有门面，保持现状。
- **collectPeakCandidates 的 minMaxLoc×k 循环**：O(k·W·H)，k≤256 且作用于
  ¼ 粗层，实测可接受。
- **模板缓存锁粒度**：全局 shared_mutex，读路径（getTemplateSnapshot）拿共享
  锁且只拷贝句柄，写路径低频；热路径无竞争实证，不细化。
