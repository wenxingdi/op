# op 主接口层分析（2026-10-15，逐模块专项第 8 弹）

> 范围：`libop/op/` 全部 15 文件 4016 行——COM/C API 门面与能力层之间的薄转发层：
> 每函数做参数守卫 / set_result 初始化 / 异常兜底 / 坐标换算后，转发给
> `window_service`（窗口）、`image_proc`（图色/OCR）、`bkproc`（绑定/键鼠）、
> 各单例引擎（OCR/YOLO）或直接 Win32。
> 分析方法同前：先出清单 → 用户确认 → 再实施。

## 结构总览

```
OpContext/OpContext.h   会话状态聚合（window_service/bkproc/image_proc/astar_map/vkmap），
                        构造函数：DPI 感知提升（有归因注释）、进程级 rand 播种、vkmap 键码表
OpRuntime               Ver/SetPath/GetPath/Delay/GetMachineCode/IsElevated 等薄封装
OpClipboard/OpProcess   16+90 行纯转发（剪贴板、进程/注入/命令行）
OpYolo                  111 行：统一引擎入口（.onnx 自动切进程内引擎）+ 检测 + JSON 构造
OpMemory                187 行：15 个内存读写包装，hwnd=0 归一到绑定窗口
OpAlgorithm             333 行：A* 寻路系（点串版 + 障碍位图版 + 多点途经 + LOS 拉直
                        + RDP 抽稀 + 三态遮挡判定）与几何工具（最近点/点在多边形内）
OpInput                 391 行：键鼠延迟/键码表查询/组合键助手/key_combo 系
OpImage                 392 行：找图找色全薄转发（大漠索引语义有测试钉住）
OpWindow                553 行：窗口枚举/几何/样式 + 布局排列 + 几何锁守护线程 + IME 动态加载
OpOcr                   567 行：引擎入口/字库管理/免字库 OCR 门面（AutoOcr 按 color 分路）/
                        词组结果解析（GetWordsNoDict + 按 '/' 走项取值）
OpOpenCv                922 行：模板库管理 + 28 个文件级图像操作 + 8 个 MatchTemplate 变体
OpCaptureHelpers.h      74 行：capture_region/with_captured_region/guard_exceptions 模板（干净）
OpResult.h              15 行：set_result 空指针守卫模板（干净）
```

整体评价：作为门面层，守卫纪律与注释意识是全库最好的（FindStr 大漠索引语义、
IsLineBlocked 三态 -1、InjectDll 归一化均有「勿改」注释与钉测试）。**问题以
「同构代码重复」为主，集中在 OpOpenCv 一个大文件；真 bug 仅 SetPath 一处。**
效率类问题基本没有——本层全是薄转发，无热点。

## OP1【精简·高】OpOpenCv：五个模式解析器同构 if-else 链

**位置**：`OpOpenCv.cpp` L17-105。`parse_cv_threshold_mode` / `parse_cv_color_space` /
`parse_cv_morphology_mode` / `parse_cv_thin_mode` / `parse_cv_blur_mode` 五个解析器
结构完全相同：copy + wstring2lower + 逐条 if-else 别名匹配 + 失败 setlog。
**方案**：每个解析器收为一张静态别名表 `{别名, 枚举值}` 循环匹配（五张表 + 一个
公共匹配函数）。纯排版收拢，零行为变化。预计 -60 行。

## OP2【精简·高】cv_pipeline_apply_step：七组无参步骤别名 if 链

**位置**：`OpOpenCv.cpp` L240-260。gray/binary/edge/outline/denoise/equalize/cropvalid
七组 `if (name == ...)`，每组 2-4 个别名，函数体均为一行转发。
**方案**：别名→`bool (*)(const ImageHandle&, ImageHandle&)` 的静态映射表线性查名，
查不到再走带参步骤的既有 if 链（clahe/blur/sharpen/threshold/inrange/morph/thin/
resize 逻辑各异，保留）。预计 -35 行。

## OP3【精简·中】OpOpenCv：8 个 MatchTemplate 变体共享骨架 + 两个 JSON 构造近似重复

**位置**：`OpOpenCv.cpp` L155-184、L679-922。`build_cv_components_json` 与
`build_cv_contours_json` 拼 JSON 的框架（ok/code/数组头尾）逐行相同，仅数组元素
序列化不同；8 个 Cv*MatchTemplate 变体（Match/Scale/MatchAny/MatchAll/Feature/Edge/
Shape/Rot）各自重复「解析区域 → 取模板 → 执行匹配 → 结果加截图 origin → 拼 JSON →
set_result」整段流程。
**方案**：①两个 build_cv_*_json 合并为一个，元素序列化用传入的 lambda；②提取
`cv_match_run` 模板助手承载公共骨架，各变体只留参数解析与匹配调用两行。
单项最大，预计 -150 行。**风险点**：变体间默认值/失败 JSON 细节略有差异，实施时
逐变体对照既有测试（Cv*Test）确认行为等价。

## OP4【精简·中】OpMemory：15 个包装函数 try/catch 骨架完全同构

**位置**：`OpMemory.cpp` L26-186。每个函数都是「set_result 置 0 → 参数守卫 →
resolve_memory_hwnd → try { ProcessMemory mem; ... } catch (...) { 复位 }」。
**方案**：提取模板助手 `with_memory(self, hwnd, default, fn)` 承载 hwnd 归一 +
异常兜底；各函数体缩为 1-2 行。`resolve_memory_hwnd` 的语义注释一并搬入助手。
预计 -100 行，纯机械收拢。

## OP5【精简·中】OpWindow：几何锁三函数共享「找/建条目 + 剪除删除」块

**位置**：`OpWindow.cpp` L431-529。LockWindowPosition / LockWindowSize /
DisableMinMax 三个函数各自重复约 25 行：lock 下找条目（无则 push_back 新建并锚定
GetWindowRect）、置标志、`geo_lock_prune` 后 find_if + erase 删除。
**方案**：提取 `geo_lock_entry_for(hwnd, create)`（含锁内 push_back/锚定）与
`geo_lock_drop_if_empty(hwnd)`（prune+erase）两个助手，三函数只留各自的标志语义。
预计 -50 行。守护线程与 IME 动态加载部分不动。

## OP6【精简·低】OpContext：vkmap 62 条手写赋值

**位置**：`OpContext.cpp` L82-143。back/ctrl/f1-f12/num0-9 等 62 条逐行 `vkmap[L"..."] = VK_...`。
**方案**：一张静态 `const std::pair<const wchar_t*, long> kVkTable[]` + 循环 insert。
纯排版收益（-45 行），价值在便于一眼查重查漏；行为完全等价。

## OP7【精简·低】OpOcr：GetWordResultPos/GetWordResultStr 共享按 '/' 走项循环

**位置**：`OpOcr.cpp` L355-415。两个函数各有约 20 行「从头按 '/' 走到第 index 项」
的相同循环（含坏格式提前返回逻辑），随后一个取坐标、一个取词串。
**方案**：提取 `find_word_result_item(result, index, &item_begin, &item_end)`，
两函数各自只做解析。预计 -25 行。

## OP8【bug·待确认】OpRuntime::SetPath 第二成功分支写入原始串而非解析结果

**位置**：`OpRuntime.cpp` L26-50。首分支成功时 `curr_path = fpath`（已规范化：
`/`→`\`）；第二分支（相对路径拼接到旧 curr_path 并验证存在）成功时却是
`curr_path = path`——**把未拼接、未规范化的原始入参写进了 curr_path**。
后果：SetPath("sub") 成功后 GetPath 返回 "sub" 而非 "C:\base\sub"，后续
Path2GlobalPath 相对解析基于错误基准。既有测试只覆盖绝对路径分支与空串，
该分支行为未被钉住。
**方案**：`curr_path = fpath`。这会改变「相对路径 SetPath 后 GetPath 的返回值」
（从错误值变为正确值），需用户确认接受行为修正。

## 观察项（记录不动）

- **SetMouseDelay/SetKeypadDelay if-else 链**（`OpInput.cpp` L303-316/360-375）：
  可表驱动，但每处只省 3-4 行且分支语义直白，收益低于改动成本。
- **geo_lock_worker 常驻 50ms 轮询线程**：设计取舍已注释（跨进程子类化需注入 DLL，
  轮询+SetWindowPos 零注入足够），不动。
- **GetWordResultPos 按 index 从头走 O(n)**：调用方一般逐个 index 取会累计 O(n²)，
  但词组结果串短（典型 < 100 项），无感知。
- **OpImage/OpClipboard/OpProcess/OpYolo/OpAlgorithm/OpCaptureHelpers/OpResult**：
  薄转发与纯计算，无实质问题（OpYolo 的 build_yolo_json 手写拼接若未来加字段再考虑）。

## 其余结论（无实质问题）

- **守卫纪律好**：每个出参先 set_result 初始化再进入捕获区；OcrFromFile 三件套用
  guard_exceptions 兜底（C++ 异常不能穿出 COM 边界）。
- **AutoOcr 门面**（color 空→OcrAuto / 非空→OcrAutoColor）已按用户 14:10 拍板的
  门面方案落地，注释完整。
- **OpAlgorithm 的 A* 系列**：astar_segment 助手 + pathtools 分工清晰，IsLineBlocked
  三态 -1 的「勿改 0」注释与测试钉住，SmoothPathByLOS 贪心最远可见跳点注释完整。
