# 截图模块分析（2026-10-15，逐模块专项第 6 弹）

> 范围：`libop/capture/` 全部——后端接口（ICaptureBackend）、帧头（FrameInfo）、
> 四个截图后端（GDI / DXGI / Hook / WGC）与内存图源（MemoryImageSource）。
> 分析方法同前：先出清单 → 用户确认 → 再实施。

## 结构总览

```
ICaptureBackend（基类：Bind/UnBind 模板方法 + 共享段/互斥名约定 + getFrameInfo）
  ├─ GdiCapture（408 行）normal/gdi/gdi2/dx2 四模式
  │    normal：桌面 DC BitBlt 按需大小；dx2：窗口 DC BitBlt + 全黑回退 PrintWindow；
  │    gdi/gdi2：整窗 PrintWindow（PW_RENDER_FULL_CONTENT 优先，全黑回退 flags=0）
  ├─ DxgiCapture（421 行）输出复制器：AcquireNextFrame → staging CopyResource
  │    → CPU map 按客户区夹取拷贝；跨显示器/设备丢失/访问丢失均自重建
  ├─ HookCapture（435 行）BlackBone 注入 op DLL 到目标进程，读共享帧
  │    BindEx（按 pid）/ BindNox（NoxVMHandle.exe）两条 attach 路径
  └─ WgcCapture（1317 行）WinRT 捕获：Win11 事件回调直驱；Win10 18362 走
       worker 线程 + SEH 熔断 + 全局 cleanup 栅栏（真机 WgcTest 血泪史）
```

整体评价：四个后端近年都经历过多轮真机加固（异常护栏、共享段容量双检、
全黑静默失败检测、ABA 防护、删重建互斥），注释质量高，**大部分代码不宜再动**。
问题集中在「重复实现」与个别死代码/微效项。

## C1【精简·中】`fmtFrameInfo` 三份复制 + `FrameInfo::format()` 死代码

**位置**：`GdiCapture.cpp` L398-406 / `DxgiCapture.cpp` L411-419 / `WgcCapture.cpp` L1305-1313
三份逐行相同的私有实现（Dxgi/Wgc 带 `inc` 参数，Gdi 恒递增），各自配一个
`m_frameInfo` 成员。而 `FrameInfo.h` L20-27 的 `format()` 方法**全库无调用者**（grep 实证）。
另有一处不一致：三份后端实现用 `GetTickCount64()` 截断到 u32，`format()` 用
32 位 `GetTickCount()`（49 天回绕）。

**方案**：基类 `ICaptureBackend` 收拢——加 `FrameInfo m_frameInfo` 成员 +
`void writeFrameInfo(void *dst, int w, int h, bool inc = true)`（tick 统一
GetTickCount64），删三个后端各 ~10 行复制；`FrameInfo::format()` 死代码删除
（或改造为被 writeFrameInfo 调用的核心，二选一）。行为完全等价。

## C2【精简·微】GdiCapture `_bfh`（BITMAPFILEHEADER）是死写入

**位置**：`GdiCapture.cpp` L221-223 与 L296-298 两处给 `_bfh` 三个字段赋值，
但该成员**从不被读取**——数据走 `GetDIBits`（只用 `_bih`），没有任何文件写出。
删成员 + 两处赋值（-8 行）。顺带：`BindEx` L122 `setlog("hdc == NULL", _hdc)`
格式串没有 `%p`，多传参数（无害但 sloppy），一并修。

## C3【精简·微】GdiCapture::BindEx 三分支可并为两个

**位置**：`GdiCapture.cpp` L110-119。`RDT_GDI` 与 `else` 分支完全相同
（都是 `GetDC(_hwnd)`），仅 `RDT_GDI_DX2` 多取一次 device caps。
改为 `render_type == RDT_NORMAL ? GetDC(NULL) : GetDC(_hwnd)`，
dx2 的 `GetDeviceCaps` 移出分支。-4 行，行为等价。

## C4【精简·中】HookCapture 四条 attach 护栏路径结构重复

**位置**：`HookCapture.cpp` BindEx / UnBindEx / BindNox / UnBindNox。
`blackbone::Process proc; try { Attach → … → proc.Detach(); } catch(…) {}` 的
骨架重复 4 份（~15 行/份）；此前 attach_display_hook 已收拢过注入+设钩子部分，
但 Attach 护栏本身没收拢。提取 `with_attached(pid 或进程名, 回调)` 模板助手
（成功 Attach 才回调，Detach 与双 catch 统一在助手内），4 份各缩至业务几行。
行为等价（Detach 时机、异常吞掉打日志语义保持）。

## C5【精简·微】WgcCapture 状态复位语句块双份

**位置**：`WgcCapture.cpp` UnBindExInternal L268-289 与 UnBindExOnWindows10 L317-332，
约 18 行的 `session_/framePool_/hasFrame_/frameSerial_/pending*_/lastClient*_/…` 复位
逐行相同。提取 `resetCaptureState()` 私有方法。纯整洁。

## C6【效率·微】GdiCapture normal 路径每帧重建位图

**位置**：`GdiCapture.cpp` L204-219——每次 requestCapture 都
`release_capture_bitmap` + `CreateCompatibleBitmap(w,h)` + SelectObject。
可按 (w,h) 缓存 `_hbmpscreen`，同尺寸复用（FindPic 循环通常同区域反复截）。
收益视 GDI 位图创建开销而定（微-小），改动局部。候选，非必做。

## C7【效率·记录不动】DXGI 全帧 CopyResource 与 GDI 每行 memcpy

- DXGI：`GetDesktopFrame` 每帧 `CopyResource` 整桌面纹理（L396）——
  API 层面无法在 acquire 时裁剪，用 DirtyRects 做增量又与本项目
  「任意区域随时可能读」的用法冲突。**记录不动**。
- GDI/Hook/WGC 的行拷贝均为 stride→紧凑行 memcpy，已是下限。**无问题**。

## C8【观察项·记录不动】WgcCapture 复杂度高但属必要

1317 行中约一半是 Win10 worker 路径的时序/熔断/cleanup 护栏
（每条注释都指向具体真机故障形态）。Win11 路径仅走其中主干。
**不重构**——这些护栏是 WgcTest 全组跑通的代价，挪动即失保障。

## 其余结论（无实质问题）

- **基类模板方法**（Bind 三步/BindEx、UnBind + DeferBindReleaseAfterUnBind 钩子）
  设计合理；WGC 覆写 getFrameInfo 防删重建悬垂的注释清楚。
- **MemoryImageSource**（209 行）解析/校验严谨（ptr/尺寸/格式/BMP 头全校验，
  span 约束读取范围）；`parse_ptr` 末尾 `return ptr != nullptr` 恒真（value==0 已拒）
  属无害冗余，不单列项。
- **FrameInfo 校验和**（fmtChk 异或链）与 operator<< 双版本正常。
- **DxgiCapture** 的多显示器定位、设备丢失重建、帧租约 RAII 均干净，无实质问题。
