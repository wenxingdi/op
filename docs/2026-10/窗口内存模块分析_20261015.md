## W1【头条·需拍板】EnumWindowInternal：32 分支 switch 表驱动重构

**位置/规模**：`WindowService.cpp` L220–1690，约 1470 行，filter 0–31 共 32 个 case。

**结构分析**（逐 case 比对后确认行为完全规则）：

filter 为位组合，各 bit 语义：

| bit | 值 | 语义 |
|---|---|---|
| 0 | 1 | 枚举循环内做标题匹配（title 有效） |
| 1 | 2 | 枚举循环内做类名匹配（class_name 有效） |
| 2 | 4 | 只匹配父窗口第一层子窗口；**带 process_name 时激活"每进程取第一个窗口"逻辑** |
| 3 | 8 | 匹配 owner==0（顶级窗口），作为 `isGW_OWNER` 传入 FindChildWnd |
| 4 | 16 | 只匹配可见窗口，作为 `isVisible` 传入 FindChildWnd |

每个 case 末尾的 `FindChildWnd(...)` 调用参数恰好等于 `(filter&8, filter&16, process_name)` 的组合——**case 1–15 传 (false,false)、16–23 传 (false,true)、24–31 传 (true,true)**，与位一一对应。真正特殊的只有 2 处：

1. **case 0**：全枚举、无谓词；与 process_name 互斥（两者同时给直接 return false）。
2. **case 16**：把 parent 强制设为桌面窗口再枚举（无视调用方传入的 parent）。

**方案**：分解为「匹配谓词（标题/类名，由 bit0/bit1 决定）+ 递归标志（bit3/bit4）+ bit2 的首层/进程逻辑」驱动的单循环 + case 0/case 16 两个特例分支。预计 1470 → 约 200 行，减约 1200 行。之后新增 filter 语义或修 bug 只改一处。

**风险：中高**。32 种组合的行为保真依赖逐组合核对，而现有测试覆盖**很薄**：

- `WindowServiceTest.EnumWindow` 只跑 filter=1+2=3 一条，且无结果断言（只打印前 50 字符）；
- filter=56 仅出现在 FurMark 真机 helper 里（`EnumWindowByProcess`，无 FurMark 环境即跳过）；
- null-handle 测试不进实现。

**建议路径**：先做 W1a——为 EnumWindow/EnumWindowByProcess 补 6–8 条**特征化测试**（代表性组合 0/1/2/3/4/8/16/24 + 两个特例：case0 与 process_name 互斥、case16 桌面父窗口），跑通基线；再做 W1b 表驱动重构，重构前后用同一批测试对拍。

## W4【观察项·记录不动】get_cpu_usage 双开句柄

`WindowProcess.cpp` L141–225：Sleep(1000) 前后各 `OpenProcess` 一次。首次句柄在采样间隔内完全可复用（进程退出后句柄与 GetProcessTimes 依然有效），第二次打开可省。但本身在 1s 阻塞调用里，收益可忽略，**建议不动**。

## W5【观察项】SendString / SendStringIme 主体几乎相同

`WindowText.cpp` L223–261：两函数唯一差异是 WM_IME_CHAR 兜底是否限 `>0x7f`（SendString 限、SendStringIme 不限）。可用一个内部 bool 参数统一，减约 20 行。两函数均为独立导出 API（大漠语义），动实现不动接口，风险低。

## 内存模块结论：无实质问题

- `checkaddress` 只查方括号配对（够用）。
