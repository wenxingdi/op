## 一、改动清单

### 1. E-A OCR 管理器锁外推（perf，最大一项）

**问题**：`HttpOcrService::ocr()/ocr_line()` 从入口到返回全程持有 `m_mutex`，
130ms+ 的推理本体被锁包住，多线程/多 Op 实例并发 OCR 被完全串行化。
实施文档（`OP_OCR_INTERNAL_PLAN` 9.2）原设计即"OnnxOcrEngine 可重入、锁外调用"，
但代码未落实——锁一直在锁内。

**改法**（`libop/ocr/OcrService.h/.cpp`，约 40 行）：

- `m_engine` 从 `std::unique_ptr` 升级为 `std::shared_ptr`；
- 锁内只做：引擎选择 / 懒初始化 / `shared_ptr` 快照；
- 推理本体 `engine->ocr(...)` 移到锁外；
- 并发 `release()` / 重 `init()` 时，在飞调用持有的引擎实例不会被销毁（快照保活）。

### 2. C-A 找图死代码变体删除（refactor，净 -120 行）

**问题**：算法层同时存在 4 套找图实现（线程/非线程 × 裸图/预处理），
非线程版还是线程版的**陈旧副本**——双份维护源，行为漂移风险
（5.2.0 修 FindColorEx off-by-one 时要逐版本核查的痛点即源于此）。

**核实**（删除前全仓 grep）：服务层（`ImageSearchService.cpp:316,332`）只走
`FindPicTh/FindPicExTh` 的 `PicMatchTemplate*`（预处理+线程池）重载；
被删变体在 libop / tests / bindings / tools 零调用方。

**删了**：非线程版 `FindPic/FindPicEx`、裸 `Image*` 双重重载、`prepare_pic_views`。
**保留**：唯一一套 `FindPicTh/FindPicExTh`（PicMatchTemplate*）。

### 3. E-B `OcrEx` 免字库路径上限 off-by-one（fix）

`ImageSearchService.cpp` 原"先拼串收集、后判上限"实际可返回 `_max_return_obj_ct+1` 条；
改为与同文件 `autoocr_ex` 一致的先判后收。5.2.0 修 FindColorEx 同款时的漏网一条。

### 4. 顺手项

- `autoocr_ex` / `OcrEx` 结果串拼接：`std::to_wstring(...) + L","` 链式临时对象
  统一为单次 `swprintf` 小缓冲（坐标+置信度一次成形）；
- `FindColorNum`：`goto _quick_break` → 64 位计数 + 循环条件早退，行为不变。

### E-A 专项：A/B 反向验证（决定性）

新增回归探针 `scripts/probes/_t_ocr_concurrency.py`：

- **判别器设计**：`SetOcrEngine("--threads=1")` 把推理压回调用线程——
  无锁时两线程的前/后处理单线程段天然重叠（总耗时 ≈ 1×t1），
  有锁时 = 2×t1。本机负载波动 3 倍、单路默认即近带宽饱和，
  默认线程数下计时判据不可用（numpy 4 线程对照也只有 ~2×），
  threads=1 是本机上最稳的判别器。
- **结果**：同一探针打**旧 DLL 比值 1.87 → FAIL**（绊线触发）；
  打**新 DLL 1.54~1.62 → PASS**。回归可被抓。

### 关键发现（已记入 CHANGELOG）

本机 i5-13400（16 逻辑核）上，ORT 默认 intra-op 线程 = 全核，
**单路推理即逼近内存带宽饱和**——4 进程并发 OCR 比 4 线程更差（每进程 374ms→2.2s）。
因此锁外推的提速在**默认线程数 + 本机**上测不出；
其价值在 ① 消除人为串行点（`--threads` 调低、多实例、高核数机器直接受益）
② 消除锁本身的代价（锁等待、优先级翻转、ocr_line 与 ocr 互斥）。

# 附录：OCR 命名规范化（同日第二批，refactor）

## 问题

免字库 OCR 两套命名混用且语义不同：`OcrAuto/OcrAutoFromFile`（原图直识别，无颜色参数）
与 `AutoOcr/AutoOcrLine/AutoOcrEx/AutoOcrFromFile`（先按颜色二值化再识别，必须给颜色）。
`autoocr`/`ocrauto` 字面近似极易用错族，且违反大漠风格"Ocr 前缀"的项目主流约定。

## 方案

- `AutoOcr*` → `OcrAutoColor*`（Color 后缀精确表达"带颜色二值化"语义）；
  Service 层 `autoocr*` → `ocr_auto_color*`；`OcrAuto` 系保持不动。
- 全层兼容：**旧名全部保留为废弃别名**（C API 一行转发 / COM 旧 dispid 不动 /
  pyop %extend 别名 / ctypes alias / Go 转发），已有脚本与 OPTool 零迁移。

## 改动面与验证

- 契约/实现：`libop.h`、`OpOcr.cpp`、`ImageSearchService.h/.cpp`；
  C API：`op_c_api.h/.cpp`（+4 新名，旧名转发）；COM：`op.idl` 新 dispid 380-383 + `OpAutomation`；
  绑定：SWIG 三层重生成（4.4.1，check_swig_sync 通过）、ctypes 绑定、Go 绑定；
  测试：C++ 用例改用新名，空句柄测试新旧名并测；`_t_dict_ocr.py` D5 组用新名，其余探针保留旧名作别名覆盖。
- 验证：构建 0 error（MIDL 一次通过）；全量 gtest 371 PASS（2 条已知项）；
  OCR 专项 28/28；`_t_dict_ocr.py` 49 PASS/0 FAIL；`api_reference.html` 已重新生成。

## 追加：归一入口 AutoOcr（同日第三批，feat）

用户决策：AutoOcr（带色二值化）使用更高频，按门面方案归一。

- **语义**：`AutoOcr(x1,y1,x2,y2,color,sim)` —— color 空 → 原图直识别（= OcrAuto）；
  非空 → 按颜色二值化（= OcrAutoColor，含字库协同）。非空行为与旧 OpAutoOcr 别名完全一致，零迁移风险；
  唯一变化：空颜色从"返回空串"变为有用的原图识别。
- **实现**：门面一层 `if (color.empty()) OcrAuto(...) else OcrAutoColor(...)`，OpOcr.cpp 薄封装；
  显式入口全部保留。
- **全层**：C API OpAutoOcr 由别名升级正主名；COM dispid 384；pyop AutoOcr 由 %extend 别名改为真实方法
  （三层重生成）；ctypes 新增 `autoocr()`；Go 新增 `AutoOcr`。
- **验证**：新用例 AutoOcrFacadeDispatchesByColor（三分支钉死）；全量 372 PASS（+1）；
  `_t_dict_ocr.py` 49 PASS/0 FAIL；api_reference 重新生成。
