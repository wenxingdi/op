# 32 位发布验证抓到的两个构建/发布缺陷（2026-11-21）

> 本轮做 64 位发布验证（走注册表 `CoCreateInstance` + `LoadRegTypeLib`）时，
> 顺带按"32 位大概验证"的要求跑了一遍 32 位，结果连炸两次。
> 两个都不是"功能代码写错"，而是**构建/发布链路**的问题 —— 这类缺陷单测和免注册探针都看不见。

## 一、缺陷 1：`op_i.h` 更新不触发 COM 源重编（x86 尤重）

### 现象

32 位走 vtable（早期绑定）调 `SetAStarMapData` → **访问违例 0xC0000005**；
走 IDispatch → `E_POINTER`（该方法唯一的 E_POINTER 来源是 `if (!ret)`，即
OLEAUT32/ATL 传了 NULL 的返回值指针）。

同一个 dll 用 64 位路径测则完全正常。

### 根因

```
build/ninja-x86-Release/libop/com_generated/op_i.h          20:42   (350 个方法)
build/ninja-x86-Release/libop/CMakeFiles/op_x86.dir/com/*.obj  20:18   (旧!)
```

`op_i.h` 是 midl 生成的 **GENERATED 文件**。CMake 里有
`set_source_files_properties(${OP_COM_GENERATED_FILES} PROPERTIES GENERATED TRUE)`，
但**生成规则（custom command）与 COM 源之间没有显式依赖**。ninja 的 `depfile`
虽然记录了 `op_i.h`，但对"被重新生成的 GENERATED 头"没有强约束，
结果 `OpAutomation.cpp.obj` 停留在旧版 —— DLL 里 `IOpAutomation` 的 vtable
**少 10 个方法**，按新布局调用直接跳错槽。

x64 侥幸没暴露只是因为那次是整棵重编。

### 修法（`libop/CMakeLists.txt`）

```cmake
set_source_files_properties(${OP_COM_SOURCES} PROPERTIES OBJECT_DEPENDS "${OP_COM_I_H}")
```

验证：删掉 x86 的 4 个 COM obj 重编后，vtable 与 IDispatch 双双 PASS。

## 二、缺陷 2：`bin\x86` 陈旧 + 32 位依赖放错目录

### 现象

修好缺陷 1 后，从 `bin\x64\op_x86.dll` 起 32 位进程仍然
`LoadLibrary failed 1114 (ERROR_DLL_INIT_FAILED)`。

### 根因（两层）

1. **`bin\x86` 从来没在发布同步清单里**：目录停在 2026-11-20 14:33，
   所以"32 位验证"一直在跑旧 dll。`_sync_release_b2.py` 只把 x86 件同步到
   `bin\x64`（为了 blackbone 按 SetPath 目录找注入模块）。
2. **同名依赖不可能共目录**：`op_x86.dll` / `op_c_api_x86.dll` **静态导入**
   `onnxruntime.dll`。`bin\x64` 里那份是 **64 位**，32 位进程加载 op_x86.dll 时
   解析依赖失败 → DllMain 失败 → 1114。

### 修法

`_sync_release_b2.py` 新增目标与运行时文件：

```python
X86_RUNTIME = ["onnxruntime.dll", "onnxruntime_providers_shared.dll"]
(r"...\op\bin\x86", X86 + X86_RUNTIME),
```

并把这个目录的用途写进注释：

| 目录 | 用途 | 同目录 onnxruntime |
|---|---|---|
| `bin\x64` | 64 位宿主；里面的 x86 件**只供注入 32 位目标进程** | 64 位 |
| `bin\x86` | **32 位宿主直接加载**（易语言 32 位、32 位 exe） | 32 位 |

## 三、验证结果

**32 位 IDispatch（`bin\x86\op_x86.dll`）**：

```
[diag] Ver -> DISPID 1               argc=0 -> hr=0x00000000
[diag] SetAStarMapData -> DISPID 478 argc=7 -> DISP_E_BADPARAMCOUNT(0x8002000E)
                                     argc=6 -> hr=0x00000000   ret=1
[diag] IsLineBlocked  -> DISPID 373  argc=4 -> hr=0x00000000   ret=1
RESULT: PASS   EXIT=0
```

**32 位 vtable（早期绑定）**：

```
vtable SetAStarMapData   hr=0x00000000 ret=1
vtable IsLineBlocked     hr=0x00000000 blocked=1     （穿 4x4 黑块）
vtable IsLineBlocked(空地) hr=0x00000000 blocked=0
vtable OcrFromMemEx2     hr=0x00000000               （DISPID 464，历史上被 midl 吞掉的那个）
RESULT: PASS
```

**64 位发布验证（走注册表）**：`PASS (FAILS=0)`，
19/19 新方法在类型库中、最大 DISPID 478。

## 四、新的验证口径（重要）

1. **免注册探针 ≠ 发布验证**：`DllGetClassObject` 能看到分发映射，但**看不到类型库
   缺方法**（本轮 10 个方法就是这么藏的）。发布必须再跑一次走注册表的
   `scripts/probes/com_release_verify.cpp`。
2. **32 位必须从 `bin\x86` 跑**；拿 `bin\x64` 里的 x86 件测会得到 1114，与代码无关。
3. **32 位别只测 IDispatch**：vtable 与 IDispatch 是两条路径，
   本轮就是 vtable 错位、IDispatch 各自不同表现，两条都测才能定位。

## 五、遗留

- `build/ninja-x86-Release` 的 ninja 依赖图对"GENERATED 头"仍未强约束，
  `OBJECT_DEPENDS` 是兜底。若将来再加生成头，同样要显式声明。
- `bin\x64` 里的 x86 件在"注入到 32 位目标进程"时，其 onnxruntime 依赖解析
  依赖目标进程环境（既有行为，非本轮引入），若要彻底解决需改成 delay-load。
