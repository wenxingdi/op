# C API 覆盖收口 + 并发基线（2026-11-21）

> `scripts/probes/coverage_gaps.py`：**缺口 10 → 0**（353/353 都有端到端调用证据；口径=头文件 `Op*` 剔除 `OpCreate`。DLL 实际导出 354 个 `Op*`（含 OpCreate），另有源码内未导出别名 `OpUnbindWindow`）。
> 过程中修掉一个真实缺陷：`OpTerminateProcessTree` 的成功判据在"调用方自己持有进程句柄"时必然误报失败。

## 一、为什么先做这件（而不是继续调性能）

本轮定点核查了三件"看起来必做"的事，结论都是**不需要动**：

| 候选 | 实测结论 |
|---|---|
| OCR 多档位切换（文档记 40% 失败率） | 同进程切 4 档 × 2 轮 = **8/8 成功**；LRU 淘汰（cap=1）已生效，不再是内存耗尽问题 |
| 二维码 3 接口零测试 | `OpCreateQRCode` → `OpDecodeQRCodeFromFile` **往返还原原文**，功能是好的 |
| OCR 性能 | rec 占 77%（14 行 499ms/单行 28.5ms），small 模型 + 批量 + 4 线程，**8 线程无提升** → 已到模型成本下限 |

所以真正该做的是**消盲区**：10 个导出从来没有过任何端到端调用证据，出问题时无法判断是不是它。

## 二、10 个缺口怎么补的

新增 `tests/c_api_coverage_test.cpp`（14 个用例）：

| 接口 | 测法 | 断言强度 |
|---|---|---|
| `OpCreateQRCode` | 生成 256 / size<=0 两种 | 落盘 >1KB + 可解码 |
| `OpDecodeQRCodeFromFile` | 与上闭环 | **还原原文**（`OP-COVERAGE-2026`） |
| `OpDecodeQRCode`（屏幕区域版） | GDI 建窗口贴 BMP → `gdi` 绑定 → 按客户区解码 | 与文件版结果**一致** |
| `OpGetWindowScale` | 真实窗口 + 无效 hwnd | 数值在 (0.5,5.0) 且含小数点 |
| `OpTerminateProcess` | CreateProcess 起 `ping -n 30`，杀自己起的 | 返回 1 **且进程确实退出** |
| `OpTerminateProcessTree` | `cmd /c ping`（父+子）| 返回 1 且父进程退出 |
| `OpOcrAutoColorFromFile` | 黑底白字合成图，空色 / 带色两路 | 能识别出 `909` |
| `OpOcrAutoColor` | 未绑定窗口 | 空串不崩 |
| `OpAutoOcrLine`（废弃别名） | 空色 / 有色两分支 | 空串不崩 |
| `OpKeyPressHotkey` | 空串 / `notakey+a` / `ctrl+` | 返回 0（**不发真实按键**） |

### 如实记录（不夸大覆盖度）

- `OpKeyPressHotkey` 只覆盖**拒绝路径**：合法组合会真的往系统发按键，测试不制造这种副作用。
  合法路径的正确性仍无端到端证据（需要抓 WM_KEYDOWN 的自建窗口，属另一件事）。
- `OpAutoOcrLine` 只覆盖"分发不崩 + 契约"。把"有色分支"故意改成调 `OpOcrAuto`，
  该用例仍然绿（都返回空串）—— **它证明不了分支差异**，分支正确性由
  `OpOcrAutoColorLine` 自己的用例负责。

## 三、修掉的缺陷：`OpTerminateProcessTree` 判据不可靠

```cpp
// 旧实现：terminate_process_tree() 之后用"还能不能 OpenProcess"判定
const auto check = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, FALSE, pid);
set_result(ret, check ? 0L : 1L);       // 打不开 = 成功
```

**问题**：只要调用方自己还持有该进程的句柄（`CreateProcess` 之后立刻杀，这是最常见的用法），
进程对象就不会销毁，`OpenProcess` 依然成功 → **明明杀掉了却返回 0**。

新判据：

```cpp
const auto check = OpenProcess(SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION, FALSE, pid);
long ok = 1;                                  // 打不开 = 进程已不存在
if (check && WaitForSingleObject(check.get(), 1000) != WAIT_OBJECT_0)
    ok = 0;                                   // 1 秒内还没退出才算失败
```

**反向验证**：把判据改回旧的 `check ? 0L : 1L` → `CoverageProcessTest.TerminateTreeKillsChildren`
**变红**（`Expected equality: 1 vs 0`）；恢复后绿。证明用例能区分对错，且修的是真缺陷。

## 四、并发基线（新增 `tests/concurrency_test.cpp`）

宿主（GMAJ）是多窗口多线程，但此前**没有任何用例真的多线程调过这套 API**。四条路径分开测：

| 用例 | 共享的东西 | 断言 |
|---|---|---|
| `MultiHandleColorReadInParallel`（8 线程×20 轮） | 只有全局注册表 | 每线程读回的 RGB 高两位 == 自己的颜色（防串扰） |
| `SharedHandleImageRegistryNoLeak`（4×15） | 同一个 `op_handle` | 尺寸正确 + 释放后 `GetImageCount == 0`（不泄漏） |
| `SharedHandleFindColorFromMemParallel`（6×10） | 同一 `op_handle` + 同一 `img:` 句柄 | 结果必须是确定值 `(18,18)`（不变形） |
| `SharedHandleOcrInParallel`（2 线程×2 轮） | 同一个 OCR 引擎实例 | 无空/失败结果，至少一路成功 |

> `OcrService.h` 的 profile 注释已写明"并发时数值对应任意一次调用，最后写入者胜"
> （加锁采样会污染计时）。所以并发用例**不断言 profile 数值**，只断言"不崩 + 结果正确"。

## 五、结论

- C API 覆盖：**353/353，缺口 0**
- 并发：4 条路径有基线，全绿
- 修 1 个真缺陷（`TerminateProcessTree` 判据），有反向验证
- 遗留：`OpKeyPressHotkey` 合法路径、`OpAutoOcrLine` 分支差异 —— 明写在这里，不假装覆盖

## 六、写这些用例时踩的两个"隔离"坑（对后续写测试的人有用）

并发/覆盖用例在**单个跑时全绿、全量跑时变红**，两处都是测试自己的假设错，不是产品缺陷：

**① 图像句柄注册表是进程级全局的**

`OpGetImageCount()` 统计的是整个进程注册的句柄（`ImageSearchService` 里的 `g_image_registry_mutex`），
不是某个 `op_handle` 私有的。所以"全部释放后应为 0"在全量跑时必红（前面用例还留着 14 个）。
→ 断言改成**增量基线**：开始前记 `baseline = OpGetImageCount()`，结束断言回到 `baseline`。

**② OCR 引擎是进程级单例，会被前序用例的 `--charset` 污染**

`OcrEx2Test` / `FindStrBatchTest` 会把全局引擎切到带 `--charset=` 白名单的实例（cache key 含 argv，
实例各自独立但 `m_engine` 是"当前"那一个）。并发用例没显式指定档位，就沿用了白名单实例 ——
`BP 909` 里的字符被过滤干净，串行也返回空。
→ 用例开头 `OpSetOcrEngine(handle, L"onnx", L"", L"")` 切回全字典 v6，并做一次**串行自检**：
串行就空则 `GTEST_SKIP`（说明是环境/状态问题，并发测试无意义），不假绿也不假红。

> 通用教训：凡是"进程级单例 / 全局注册表"的东西，测试必须**自己把它推到已知状态**，
> 或者在断言里用增量而不是绝对值。
