## 二、三处真加固

### 2.1 `OpDestroy` —— 唯一有实际危害的一条

```cpp
// 修前
void OP_CALL OpDestroy(op_handle handle) { delete handle; }
```

析构链会释放抓屏后端、COM、注入线程、共享内存。**任何一个节点的异常穿过
`extern "C"` 边界就是 `std::terminate`**，而 `OpDestroy` 恰恰是宿主退出/重载时
最后调用的那个函数 —— 崩在这里等于"退出必崩"，且现场最难查。

修后吞掉并记日志：

```cpp
try { delete handle; }
catch (const std::exception &e) { setlog("op_c_api: OpDestroy caught exception in destructor: %s", e.what()); }
catch (...)                       { setlog("op_c_api: OpDestroy caught unknown exception in destructor"); }
```

顺带补了 `if (!handle) return;`（`delete nullptr` 本来也合法，但显式更好读）。

> 取舍：吞异常后内存不回收。**宿主卸载期崩溃比泄漏几十字节恶劣得多**，这条优先。

### 2.2 `OpRequestCaptureForTest` —— 测试钩子，之前裸调能力层

原来直接 `BindingSession session; session.requestCapture(...)`，没有护栏。
现在整段包进 try/catch，`out.ptr<>()` 也补了空判。

⚠ 负返回码 `-2`（参数非法）/ `-1`（显示模式设置失败）是**设计意图**，
`image_color_test` 用 `< 0` 钉住，**不要按布尔契约归一为 0**。
新增的 catch 分支返回 `0`，与"抓取失败"同档，不影响现有断言。

### 2.3 `OpUnbindWindow` —— 去掉裸转发层

```cpp
// 修前：多一层转发，静态普查看不到护栏
int OP_CALL OpUnbindWindow(op_handle handle) { return OpUnBindWindow(handle); }
// 修后：直接调同一实现
int OP_CALL OpUnbindWindow(op_handle handle) {
    return call_ret(handle, [](op::Op &op, long *ret) { op.UnBindWindow(ret); });
}
```

行为等价（`OpUnBindWindow` 内部也是 `call_ret`），只是让普查看得见。

## 三、4 条白名单（`delegate_no_throw`）

静态分类器看不到"被调方有没有护栏"，会把纯转发误报成 UNGUARDED。
`scripts/c_api_throw_survey.py` 新增 `DELEGATE_SAFE` 白名单：

| 导出 | 为什么安全 |
|---|---|
| `OpVer` | 只返回编译期字面量 `OP_VERSION`（`/D` 注入） |
| `OpAutoOcrLine` | 转发 `OpOcrAuto` / `OpOcrAutoColorLine`（均 `call_string`） |
| `OpAutoOcrEx` | 转发 `OpOcrEx` / `OpOcrAutoColorEx`（均 `call_string`） |
| `OpAutoOcrFromFile` | 转发 `OpOcrAutoFromFile` / `OpOcrAutoColorFromFile`（均护栏） |

白名单**不隐藏**它们：普查输出里单独一节 `delegate_no_throw` 连理由一起打印，
方便复核（不想让它变成"静默豁免"）。

### 4.1 如实记录：做不到的部分

**析构抛异常这条路径没法构造用例**。要验证得人为让某个后端的析构函数抛，
这需要往产品代码里塞测试钩子（污染面大于收益），所以本轮只能靠：

1. 代码审查（确认 catch 覆盖 `std::exception` 与 `...`）；
2. 全量回归证明正常路径零影响。

**这是"护栏存在"的证明，不是"护栏被触发过"的证明** —— 不写成"已验证"。

同理 `OpRequestCaptureForTest` 的 catch 分支也无法主动触发。
