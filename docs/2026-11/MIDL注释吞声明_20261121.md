# MIDL 把 idl 注释里的中文当续行，吞掉 10 个 COM 方法（2026-11-21）

> 一句话：`op.idl` 是 UTF-8、注释里写中文，MIDL 用 cl 预处理器按代码页 936 读，
> 字节错位后偶发把 `//` 注释行尾配出一个 `\` → 续行 → **紧邻的下一行声明整行消失**，
> 而 midl 依然 `exit=0`。累计 10 个方法从来没进过类型库，易语言调它们报
> `DISP_E_UNKNOWNNAME`。

## 一、是怎么发现的

发布 64 位版本后做注册验证（`scripts/probes/com_release_verify.cpp`，
走 `CoCreateInstance` + `LoadRegTypeLib` 的**注册表路径**，而不是免注册探针）：

```
[ok]   AudioSetSessionMute   DISPID=460
...
[FAIL] OcrFromMemEx2         GetIDsOfNames hr=0x80020006   <- DISP_E_UNKNOWNNAME
类型库函数总数=347
```

`OcrFromMemEx2` 在 `op.idl` 里有声明（`[id(464)]`）、`OpAutomation.cpp` 里有实现、
C API 和 Python 绑定都能调 —— 只有类型库不认识它。

## 二、根因（逐步证伪过程）

| 猜测 | 验证 | 结论 |
|---|---|---|
| idl 里这行有隐藏字符 | 打印该行字节 | 纯 ASCII，干净 |
| idl 里 id 重复 | `grep 'id(464)'` | 只有 1 处 |
| midl 生成物是旧的没重跑 | 比对 mtime（都是最新） | 不是 |
| 手写 `Invoke` 的映射漏了 | 类型库里**根本没有**这个名字 | 不是分发问题 |
| **编码 / 预处理** | 把 idl 的 3570 个非 ASCII 字节**逐个换成 `X`**（长度不变）重跑 midl | **`OcrEx2`/`OcrLastProfile`/`OcrFromMemEx2` 全部出现，C4819 归零** |

机制：UTF-8 中文三字节（如 `E4 B8 80`）被 GBK 按双字节配对消费后**错位**，
后续字节可能配出 `0x5C`（`\`）。C 预处理器在注释识别之前先做「反斜杠-换行」续行拼接，
于是 `// ...中文...` 行尾的 `\` 把**下一行**拼进注释 —— 那一行正好是方法声明。

旁证：长期存在的 `warning C4819`（该文件包含不能在当前代码页(936)中表示的字符）
就是这个问题的信号，但 midl `exit=0`，所以从来没人管。

## 三、影响面：不是 3 个，是 10 个

用「修复前 vs 修复后」的生成物做方法名集合差分
（`workbench/tmp/midlv_base/op_i.h` = 复刻修复前的 midl 命令）：

```
new - old = CvMatchTemplateRot, DecodeQRCode, FindStrBatch, HttpGet, JsonIsValid,
            LoadImageMem, OcrAutoColor, OcrEx2, OcrFromMemEx2, OcrLastProfile
old - new = （空）
idl 声明的 350 个方法 - 修复后类型库 = （空）
```

其中几个是**用户直接感知的功能**：

| 被吞的方法 | 后果 |
|---|---|
| `LoadImageMem` (445) | 图像句柄注册表建不了句柄 → 整个「内存直操作」链路在易语言侧不可用 |
| `OcrEx2` (440) | 结构化 OCR 拿不到逐字坐标（P0 功能） |
| `DecodeQRCode` | 二维码解码不可用 |
| `HttpGet` | HTTP 族在 COM 侧不可用 |
| `FindStrBatch` | P1 多目标查找不可用 |
| `CvMatchTemplateRot` | 旋转模板匹配不可用 |

**这些功能在 C API 侧一直是好的，所以 gtest 全绿、Python 冒烟全绿 —— 只有 COM 用户被静默挡在门外。**

## 四、修法

`libop/CMakeLists.txt`：midl 不再直接吃源 idl，而是先由
`scripts/build/gen_midl_input.py` 产出**纯 ASCII 副本**再喂它。

```cmake
COMMAND "${OP_MIDL_PY}" "${PROJECT_SOURCE_DIR}/scripts/build/gen_midl_input.py"
        "${CMAKE_CURRENT_SOURCE_DIR}/com/op.idl" "${OP_MIDL_IDL}"
COMMAND midl "${OP_MIDL_IDL}" ...
```

脚本的三条硬约束：

1. **非 ASCII 字节 1:1 换成 `X`**，不增删字节 → 行号不变，midl 报错行号仍能对回源文件；
2. 校验替换后纯 ASCII、行数与源一致，否则拒绝写出；
3. 文件里一旦出现 `helpstring` / `L"` / `[string]` 就**直接报错退出**
   —— 那意味着非 ASCII 可能不在注释里，替换会改坏内容，需要人工判断。

当前 `op.idl` 的非 ASCII 全部在 `//` 注释中（67 行，3570 字节），无 helpstring、无字符串字面量，
所以替换是安全的。

> 试过但**否决**的两条：
> - `/cpp_args "/utf-8"`（两种引号写法都试过）：C4819 仍是 2 条，cl 没吃到该参数，无效。
> - `/nocpp`：`oaidl.idl` 里有 `#ifndef`，去掉预处理器直接语法错误。
> - 把 idl 转 UTF-16/GBK：能修，但一个 UTF-16 文件在 git 里变二进制（`op.rc` 已有这个痛点），
>   而 GBK 与仓库其余 UTF-8 文件不一致。生成 ASCII 副本的代价最小、且**不依赖 cl 的编码行为**。

## 五、验证

**发布验证探针**（`scripts/probes/com_release_verify.cpp`，走注册表）：

```
1) CoCreateInstance(IID_IDispatch)      hr=0x00000000  ✓
2) LoadRegTypeLib(1.0)                  hr=0x00000000  ✓
   类型库含本批 19 个方法（实际 19）     ✓
   区间内最大 DISPID == 478              ✓
3) GetIDsOfNames 抽查 19/19 全部命中     ✓  （含 OcrFromMemEx2 = 464）
PASS (FAILS=0)
```

修复前后同一探针：**FAILS=2 → FAILS=0**（这是 A/B 反向验证，不是"跑一次绿了"）。

- `midl` 阶段的 `C4819` 警告从 2 条降到 **0 条**
- `op.tlb` 从 43308 → 44676 字节
- x64 全量回归 551 PASS / 3 FAILED（既有 WGC 抓屏环境项）

## 六、vtable 顺序变化说明

新方法按 idl 声明位置插入（`OcrFromMemEx2` 在 463 与 465 之间），
**类型库 vtable 槽位随之后移**。影响面：

- IDispatch（易语言 / VBScript / PowerShell）：按 **DISPID** 调用，不受 vtable 顺序影响 —— 无影响；
- 早期绑定（导入 tlb 生成 C++ 头）：需重新导入类型库 —— 本轮之前这些方法根本没进 tlb，
  不存在"旧客户端依赖旧顺序"的情况。

## 七、防复发

- 修复脚本在构建里强制跑，`op.idl` 后续再加中文注释也不会复发（每次构建都重新生成 ASCII 副本）；
- 探针判据改为「**19 个方法必须在类型库中**」而不是数字总量，避免口径漂移；
- 另：这次是靠"发布后走注册表验证"才发现的 —— **免注册探针（`DllGetClassObject`）看不到
  类型库缺失**，两者要都跑。这条已写进发布检查清单。
