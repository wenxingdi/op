# OCR 模型基准：Dict 素材库 × 6 变体（2026-11-26）

> 目的：为单 DLL 化选择模型内容，对 PP-OCRv6 small / v4 mobile / v6 tiny 各分 FP32/FP16 共 6 变体做同基准对比。
> 性质：**模型级**对比（纯 Python onnxruntime 流水线），不含 op 引擎增强（智能选路/颜色二值化/ROI 预放大/CLS），
> 绝对字准低于引擎端到端（如引擎级 `ocr_ab_bench.py`）；**变体间相对差距可信**，最终采纳以引擎级复测为准。
> 复现：`python workbench/v4_eval/bench_dict.py`（数据 `results_dict.json`，真值 `dict_truth.json`）。

## 二、结论：单 DLL 模型选型 = v6 small + FP16 存储

1. **v6-FP16 与 v6-FP32 字准打平**（单行 93.77 vs 93.77，多行 66.16 vs 66.04），耗时无回退——权重 FP16 存储语义在真实素材上再次验证无损，**选型 v6FP16，模型 32.18→16.27MB，单 DLL 53.2→37.3MB**。
2. **v4 全系否决**：FP32 字准全面低 29~65 个百分点（与 2026-11-20 引擎级 A/B 结论互相印证）；FP16 的 det 概率图噪声底翻倍导致伪框爆炸（1~21 框 → 6~1142 框），耗时 ×2.5，不可用。
3. **tiny 否决（本场景）**：速度快 2~3 倍、体积最小（FP16 全套 3.75MB），但字准远低于 v6（单行 47.6~50.7 vs 93.8）。论文 OmniDocBench 上 tiny≈small 的结论**不适用于本素材**——游戏 UI 小字（12~20px）+ 彩色文字 + 深色纹理底正好是容量敏感场景。若未来素材换为常规文档截图，tiny 可重测。

## 三、口径与公平性说明（复测时必须保持一致）

- **素材**：`D:\GMPLUG\DmTools\Dict` 23 图；单行 11（文件名即真值 + 6.bmp）、多行 12（人工转写 `dict_truth.json`，与 v6 引擎基线交叉核对）。
- **分辨率策略全变体统一**：长边 960 缩放（小图放大）+ 右下补黑至 32 倍数。
- **归一化/DB 阈值按各模型 yml 契约**：tiny det = ImageNet 均值(0.485/0.456/0.406) + thresh 0.2/box 0.4/unclip 1.4；v6 small/v4 = 0.5 归一化 + 0.3/0.6/1.5（与 op 引擎一致）。rec 宽均 align32 动态：v6/v4 上限 960（引擎契约），tiny 上限 320（其 yml image_shape）。
- **CTC 解码**：Paddle 导出模型 blank=索引 0，字符 id-1（勿用"blank=末位"的通用说法）。
- **字典**：v6=18,708 字（按 `\n` 切分，勿用 splitlines——含 `\x85` 类字符条目）；v4=6,623；tiny=6,904（49 语无日文，从官方 yml 提取）。
- **tiny 模型来源**：hf-mirror `PaddlePaddle/PP-OCRv6_tiny_{det,rec}_onnx`，字节数与官方 usedStorage 一致（det 1,780,590 / rec 4,462,639 B），opset 14/11。

## 五、对"单行/多行算法改进"的支撑数据

- 两代 det 在双行/1.5 行/1.7 行/紧行距合成图上均正确分行（`v4_fp16_评估报告.md` §四），**分错行不是模型代际问题**。
- 真实多行素材上 v6 字准 66%（模型级）vs 单行 93.8%：差距主要来自低对比度彩色小字在**无引擎增强**下的固有难度；引擎级（颜色二值化智能选路）在 11-20 A/B 中同类图可达 85%+。改进方向仍是指引擎后处理（det 参数扫描 + 选路），不是换模型。
