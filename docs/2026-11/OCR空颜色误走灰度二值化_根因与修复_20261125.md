# OCR 空颜色误走灰度二值化（找字扫描大面积错字）——根因与修复记录

日期：2026-11-25　影响版本：修复前全部版本（`ocr_auto_color_ex` / `ocr_auto_color` 两入口）
修复提交：工作区未提交改动（`libop/image/ImageSearchService.cpp`），DLL sha1=2833f0c1

## 现象

GMAJ OP 助手"找字扫描"（`OcrRapBoxes` → `OcrAutoColorEx`）颜色留空（界面显示"色=原图"）时，
同一任务面板识别结果大面积错字：

- `二任二务二追踪(15)区`（应为 任务追踪(6/15)）
- `靄要80点元神力` / `露露120点元0力`（应为 需要…点元神力）
- `击到青螺山妖人` / `击青螺山割候者`（"倒/喉"偏旁被吃掉）
- `菌蛮山妖魔青劇`（应为 百蛮山妖魔清剿）

而同一张图走素材文件直识（`auto_ocr_from_file`）几乎全对，差异与 sim（0.8/0.9）、
字符集（全字典/白名单）无关（三档对照实测 1704/1744/1695 字，等价）。

## 根因

`ImageSearchService::ocr_auto_color_ex()` 与 `ocr_auto_color()` **没有空颜色分流**。
全族约定是"空色 = 原图直识"（`AutoOcr` 归一入口、`OcrAutoLine`、`ocr_auto_color_ex2`
都已遵守，ex2 还有历史 bug 注释 `#ocr-empty-color`），唯独这两个函数空色继续走
`str2binaryfbk("")`：

1. `str2colordfs("")` 对空串返回 **1**（"default"分支，`colors` 为空）；
2. `str2binaryfbk` 见返回 1 → 走 `bgr2binarybk(colors)`；
3. `bgr2binarybk` 空颜色表 → **auto 分支**：灰度化取众数当背景，`|灰度差| < 20` 判背景；
4. 游戏 UI 渐变底 + 抗锯齿边缘 + 绿/红彩色字 → 笔画边缘与浅色偏旁整块被判成背景
   → 字形残缺 → 识别崩坏。

即：UI 语义"原图"与插件实现"灰度阈值 20 二值化"不符。

## 修复

在 `ocr_auto_color_ex` / `ocr_auto_color` 开头补上空色分流（免字库分支）：

```cpp
if (!dict && color.empty()) {
    // 原图直识，与 AutoOcr/AutoOcrLine/ocr_auto_color_ex2 归一语义一致
    engine_ocr_filtered(_src.pdata, _src.width, _src.height, sim, res);
    ...
}
```

约束：

- ex 的输出格式保持 `x1,y1,x2,y2,conf,text|` 6 字段不变——**不能转调 `OcrEx`**
  （那个只给中心点 `x,y,` 两字段，GMAJ `OcrRapBoxes` 按 6 字段解析会整体错位）；
- 字库分支（`dict != nullptr`）行为不动：空色 = 自动背景二值化是既有口径；
- 填色路径代码不变。

## 验证

- 同图（`tpl_95618938923.bmp`，223×160）修复后空色 ex：11 行全对，
  "击倒青螺山妖人(1605m)5/5 / 每日百蛮山妖魔清剿 / 击倒冥府道长0/5"，
  置信度 0.97~1.00；
- 填色路径回归无崩溃、行为与修复前一致；
- 注意：`OcrEx2Test` 8 个用例在当前机器红（`failed to build glyph bmp`，
  GDI 字形测试图生成失败），**基线代码同样红**，是既有环境项，与本次无关。

## 教训 / 排查线索

1. **同族接口语义必须逐个核对**：ex2 有分流、ex 没有，新增接口时漏迁移旧入口是主因；
2. 界面显示"原图"但结果像"二值化残字"时，优先怀疑空色落到 `bgr2binarybk` auto 分支
   （`str2colordfs("")` 返回 1 是关键开关）；
3. 对比测试要控制变量：素材文件直识 vs 截屏区域识别，差异可能来自采集/预处理而非引擎。
