### 2.1 P0：逐字坐标 JSON（最重要）

**新增接口**（两层，共 4 个符号）：

| 层 | 接口 | 说明 |
|---|---|---|
| C API | `OpOcrEx2(handle, x1,y1,x2,y2, color, sim)` | 返回 JSON 字符串 |
| C API | `OpOcrAutoColorEx2(..., int* find_count)` | 返回 JSON + 行数 |
| COM | `OcrEx2` = **DISPID 440** | 易语言用 |
| COM | `OcrAutoColorEx2` = **DISPID 441** | 易语言用 |
| C++ | `op::Op::OcrEx2` / `OcrAutoColorEx2` | libop.h |

**JSON 格式**：
```json
[{"text":"测试文字","conf":0.988,"is_partial":false,
  "box":[1,20,144,47],"partial_chars":false,
  "chars":[{"ch":"测","conf":0.9998,"x1":31,"x2":49}, ...]}]
```

**核心设计（踩过坑，务必理解）**：

1. **行级 conf 与逐字 conf 口径不同、不可互推**
   - 行级 `conf`：所有时间步（含 blank）的概率均值，沿用旧口径，与旧 API 完全一致
   - 逐字 `conf`：仅该字符占用时间步的均值
   - 用户已确认接受这个设计

2. **`chars` 的坐标是原图绝对坐标**，`build_ocr_json` 只能加区域偏移 `off_x`，
   **不能再加 det 框原点**（重复加会导致坐标成倍越界，今天修过这个 bug）

3. **旋转行降级**：PCA 倾斜校正过的行无法精确映射逐字坐标，
   此时 `partial_chars=true`，`chars` 的 x1/x2 退化为整行框边界

4. **`is_partial`**：框底贴图边界 <2px 时置 true，额外给 `conf_partial = conf*0.8`
   （判据必须在除回 inv **之后**比较，否则 2x 放大时阈值退化成 1px）

**关键实现位置**：

### 2.2 逐字坐标的两个硬核发现（当时花了很久才查清）

**发现 1：`t/T*roi_w` 这个公式不成立**

交接记录原写的映射公式是错的。正确是：
- 分母是该行自己的 `tw`（`ceil(48*roi.w/roi.h)`），不是 `T` 也不是 320
- **`tw` 与 `roi.w` 差数倍**（如 66×16 的 ROI，`tw≈198`），必须先换算回 ROI 像素

**发现 2：CTC 步只铺在墨迹上，不铺在整个 det 框上**

- 实测：CJK 行 det 框 [1,144]，但墨迹只占 13~135
- 按 `[0,tw]` 映射会让每个字心整体左移约 11px
- 解法：`ink_extent()` 先探墨迹范围（列级背景色众数 + 非背景行占比 >20%）

**发现 3：该模型 T=40，但每个字符只占 1 个时间步**

- 5 字行的步位是 5/12/19/26，每个 char 只占 1 步
- 所以原始 `[t0,t1+1)` 跨度是「字心」不是「字宽」，直接当宽度只有 2-4px
- 解法：相邻字心中点切分 + 首末字外扩半个平均字距

**发现 4：字典里有空串条目**

- 模型偶尔输出空串（空格/占位符），会产生 `ch=""` 的条目
- 导致 `chars` 比 `text` 多一项，破坏一一对应
- 解法：三处回填循环都过滤 `if (c.ch.empty()) continue;`

### 2.3 P2：动态 rec 长宽比

`rec_images` 的 RW 从固定 320 改为：

```
RW = clamp(align32(max(320, ceil(48 * ratio_max))), 320, 960)
```

短行行为完全不变（RW 仍 320），只有批次里有超宽行才加宽。

## 四、必须知道的两个已知缺陷

### 4.1 同进程多档位切换不可靠（未根治）

**现象**：同进程内先后 `SetOcrEngine` 切 ≥3 种配置后，部分档位整批返回空结果。

**已排除的假设**（别重复排查）：
- ❌ 内存耗尽（放开容量到 8 不淘汰照样失败）
- ❌ LRU 误删在用实例（`use_count=1`，删的都是非当前实例）
- ❌ `--cls=1` 参数 bug（单独用完全正常）
- ❌ `Ort::Env` 不共享（改共享后改善但未根治）
- ❌ JSON 复杂度（15 行 7.2KB 单档测试 5/5 通过）
- ❌ 线程数竞争（`--threads=1` 无效）
- ❌ P0 引入（git 基线版本失败更严重，是既有缺陷）

**已做的缓解**：LRU 上限 2 个实例、淘汰前腾名额、`Ort::Env` 进程级共享、`ort_run` 加 try/catch。
内存从 1225MB 降到 550MB，失败率下降但未归零。

**当前规避约定**：同进程固定单一档位。文档写在 `docs/2026-11/P0_逐字坐标JSON_实施方案.md` §6.5。

**未查清的方向**：ONNX Runtime 多 session 共存的内部资源竞争。
可能的解法：严格串行销毁重建，或改「单实例 + 运行时可变参数」架构。

### 4.2 v4 档在颜色路径下有全角括号问题

`[` 会被识别成全角 `［`。v4 字典小（6623 字）导致。
建议：颜色路径固定用 v6。

## 五、待办任务（按优先级）

### P1：FindStr 增强（**下一个要做**，约 1 天）

来自 `OP全面增强建议.md` §9.2 P1。

**现状**：`FindStr`/`FindStrEx` 只支持单目标子串查找，N 个目标要跑 N 次全图 OCR。

**要做的三项**：

1. **`OpFindStrBatch(json_targets)`**：多目标一次传入（JSON 数组），
   一次 det+rec 后引擎内匹配，返回每目标命中坐标。
   N 个目标从 N 次全图 OCR 降到 1 次。
2. **正则模式**：`OpFindStrEx(pattern, is_regex=1)`，引擎内 `std::regex` 匹配已识别行。
3. **模糊匹配开关**：编辑距离 ≤1，用于形近字容错。

**关键点**：引擎侧 det 全框 + rec 文本已就绪，**纯匹配层工作，零新增推理成本**。

**参考实现位置**：
```
libop/image/ImageSearchService.cpp
  ├─ FindStr()      （L~1490）  单目标，返回 x/y/ret
  └─ FindStrEx()    （L~1510）  多目标，返回 "x,y|..."
libop/image/ImageSearchAlgorithms.cpp
  ├─ FindStr()      （含 ocr_res 的 map<point_t, ocr_rec_t> 匹配逻辑）
  └─ bin_ocr()      字库路径的识别结果收集
```

**建议做法**：
- 复用 `engine_ocr_filtered_ext()` 拿到全框结果（含逐字数据，可用于精确定位子串）
- 用 P0 的逐字坐标做「子串 → 精确 x 区间」定位，这是新增价值点
  例如在 `击倒机关兽(909m)0/5` 里找 `909`，可以返回 `909` 自己的框而不是整行框

### P3：OCR 分项耗时自省（约 0.5 天）

新增 `OpOcrLastProfile`，返回上次 OCR 的：
```json
{"det_ms":..,"cls_ms":..,"rec_ms":..,"boxes":N,"upscale":true,"rec_width":RW}
```

**实现**：`ort_run` 外包一层 `chrono` 累加。注意今天发现的状态：
- `ort_run` 已有 try/catch（P2 时加的），可在其中记录失败次数
- det/cls/rec 三次 Run 分别计时

**价值**：现在所有耗时分析都靠外部脚本，而且受本机方差干扰严重。
内置 profile 能给出稳定的分项数据，对调优（选档、是否开放大、颜色 vs 原图）至关重要。

## 六、关键数据（供你判断，不必重测）

### 6.1 接口一致性：v6 与 v4 完全相同

| 维度 | v6 | v4 |
|---|---|---|

| JSON 字段数 | 6 / 7 | **相同** |

**唯一差异是识别质量**。所以在 `ImageSearchService` 层实现逻辑对所有档位都生效。

### 6.2 识别效果（8 张真实小图，文件名即真值）

| 档位 | 原图路径 | 颜色路径（选路前） | 智能选路后 |
|---|---|---|---|
| **v6 完全正确** | 3/8 | 5/8 | **8/8** |
| v4 完全正确 | 3/8 | 0/8 | 3/8 |

### 6.3 速度（本机 UHD 730，方差大，仅参考）

| 场景 | v6 | v4 |
|---|---|---|
| 单行小图（155~207px） | 33~72ms | **21~40ms** |
| 多行 259×208 | **361ms** | 584ms |
| 多行 291×430 | **921ms** | 1374ms |
| 密集长行 220×236 | **701ms** | 1800ms |

**v4 优势只在单行小图**；大图反而更慢（切出的框更多）。

### 6.4 颜色（重大发现）

**颜色串是 RGB 顺序，不是 BGR**。依据 `libop/image/Color.h::try_str2color`：

```cpp
swscanf(L"%02X%02X%02X", &rv, &gv, &bv);   // rv=红, gv=绿, bv=蓝
```

用户素材里红色字是 RGB(224,17,17)，必须写 `e01111`（不是 `1111e0`）。
⚠ 交接记录写的「BGR hex」**是错的**。
