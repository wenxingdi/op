# OLA vs OP 能力对比与高收益差异化清单（2026-11-22）

> **左栏 OLA**：`https://doc.olaplug.com/olaplug/功能分类.html` 及全站（本次重抓，含 2026-11 新增模块）。
> **右栏 OP**：`op/include/libop.h`（348 个公开方法）+ `docs/CHANGELOG.md` 至第四十八批（2026-11-22）。
> **与前作的关系**：`docs/2026-10/OP_vs_OLA全模块对比_20261015.md` 的 P1~P2 项**已全部落地**，
> 本文是 11 月版本：修正旧结论、补 OLA 新增的 5 个模块、并按「收益」重排优先级。
> **口径提醒**：接口数量对比没有意义（OP 348 个 / OLA 993 个接口页，但双方都有大量 Xxx / XxxEx / XxxAddr 语法糖）。
> 本文只看**能力域**和**轴心差异**。

---

## 一、结论先行

**OP 现在是「识别引擎 + 后台绑定 + 内存内核」的强引擎型插件；OLA 是「全家桶 + 授权 SaaS」的平台型插件。**

三条一句话结论：

1. **OP 的护城河在「精度 / 速度 / 可自省」，不在「接口覆盖面」。** 字库 OCR 深度、FindStr 字符级定位、
   ONNX 本地 OCR/YOLO（零外部服务）、OpenCV 多策略匹配、键鼠拟人化、截图后端（UIA/Chromium 全黑已修）
   —— 这些 OLA 都没有对等深度。竞品是「什么都有」，OP 应当继续做「难做的事做得更好」，而不是去补 JSON/XML/SQLite 这类脚本层自带的东西。
2. **OLA 的差异化不在接口数量，在三条 OP 结构性缺失的轴：**
   **① 元素/控件层（UIA 桌面元素 + CDP 网页自动化，72+ 接口）、② 视觉呈现层（屏幕绘制 DrawGui，44 接口）、
   ③ 时间轴层（录制 / 回放 / 主从键鼠同步）。** 这三条都是「新能力轴」，不是「再加几个函数」。
   加上刚新增的 **VMware 命令模块（47 接口）**，OLA 正在把「模拟器/虚拟机多开农场」整个场景吃下来。
3. **最高收益的不是任何一个接口，是 OP 还没有的「商业化三件套」**：多实例/并发、性能基准、商用防护。
   OLA 靠 0.05~0.2 元/机/天 的授权 SaaS 变现（含加密模型包 OLAENC1/OLAYENC1、模块隐藏 HideModule），
   OP 目前这些能力在业务上完全不可用。这是「收益」而不是「功能」层面的最大差距。

## 三、OP 独有 / 明显领先（护城河，要保住并写进宣传）

| 能力 | 具体证据 | 为什么值钱 |
|---|---|---|
| **字库 OCR 全链路** | `FetchWord(s)`/`ExtractWordRects(Ex)`/`CheckWordDict`/`NormalizeWordDict`/`RenameWordDict`/`GetBinaryPreview`/`GetWordPreview` | OLA 只有 4 个接口（SearchFontByImage/BuildFontLibrary 等）。做**固定字体游戏/工业界面**的人只能选 OP |
| **FindStr 字符级定位** | `FindStrBatch`/`FindStrEx2`：正则、exact/prefix/suffix、编辑距离形近容错、**字符级 cx1/cx2 坐标**、按行约束不跨行 | 「在 `击倒机关兽(909m)0/5` 里精确拿到 `909` 的框」—— 这是脚本作者每天都要解决的事 |
| **内置 ONNX OCR/YOLO，零部署** | `SetOcrEngine("onnx")`；PP-OCRv4 内嵌；HTTP 后端已编译期移除 | OLA 要 NCNN 模型 + 加密包 + 预热流程；OP 开箱即用。**这是新用户留存的决定因素** |
| **键鼠拟人化** | 贝塞尔 + 3 种速度曲线随机 + 同号相关弯曲 + 末端过冲 + 正态落点偏移 + 双击独立间隔 + `SetMouseTrajectory` | 反行为检测的核心。OLA 只有 MoveTo/Ex，轨迹生成不进核心路径 |
| **OpenCV 多策略匹配** | `CvMatchTemplate`/`Scale`/`Any`/`All`/`Feature`/`Edge`/`Shape`/`Rot` + 金字塔加速 | 缩放/旋转/半透明/低对比场景的命中率 |
| **内存直操作识别** | 14 个 `*FromMem`：图不落盘，入参句柄 + 图像内坐标 | 批量截屏识别省一次磁盘 IO + 文件句柄；且便于模型/模板打包 |
| **截图兼容性** | `gdi/gdi2/dx2` 改 `PW_RENDERFULLCONTENT` + 全黑回退；UWP/Chromium 不再全黑 | 覆盖 Electron/CEF/计算器类应用，这是最常见的「OLA 截不到 / OP 能截到」场景 |
| **音频会话控制** | WASAPI 会话级 + 系统级音量/静音 | **OLA 完全没有**，小众但绝对差异化 |
| **OCR 分项耗时自省** | `OcrLastProfile` | 调优利器，OLA 无 |

> **建议**：这 8 条写成官网/README 的「为什么选 OP」对照表。差异化不是自证的，要显式对位竞品。

## 五、收益最高的五项（按 ROI 排序）

ROI = 覆盖面 × 用户可感知度 ÷ 实现门槛。以下五项是**真正值得排期的**。

### ★ 1 A1+A2：元素/控件层（UIA 桌面 + CDP 网页）—— 建议合并立项

**为什么收益最高**

- 图色识别是「事后猜」，元素/控件是「直接读」。前者每次 UI 改版、换主题、换分辨率、换 DPI 都要重做模板；
  后者用 `Edit[aid=txtUser]` 这样的稳定选择器一次写对。
- 这是**竞品唯一的、无法通过「多写几个接口」追平的代差**：OLA 的 72 + 26 接口是一整个抽象层。
- OP 现在的诊断报告里反复出现的坑（DPI 换算、坐标语义、截图全黑）本质上都是**图色路线的固有成本**。
  补上元素层，用户就有了「绕开这些坑」的选项。
- 实现路径明确、门槛中等：UIA 是系统 COM（不用注入，`IUIAutomation` → `FindFirst/FindAll`，
  选择器语法自定）；CDP 是本地 WebSocket（`/json/version` 拿 ws 端点 → `Page.navigate`/`Runtime.evaluate`）。

**建议首版范围（不要一次做 98 个接口）**

| 层 | 首版接口（约 14 个） |
|---|---|
| 桌面元素 | `ElementFind` / `ElementFindAll` / `ElementFindIn` / `ElementFromPoint` / `ElementGetText` / `ElementClick` / `ElementSetText` / `ElementWait` / `ElementDumpTree`（调试必备） |
| 网页 | `BrowserLaunch` / `BrowserConnect` / `PageNavigate` / `PageQuery(css/xpath)` / `PageEvaluate` |

**关键风险**：选择器语法一旦定型很难改，建议先写 `docs/` 规格再动手；
`ElementDumpTree` 要第一天就有（否则用户无法写出选择器）。

---

### ★ 2 B2：多实例 / 并发验证与加固 —— 最小投入、最高留存

**为什么收益高**：几乎不写新代码，只做验证 + 文档 + 少量锁优化，但直接决定「能不能多开」。

OP 现状（`CLAUDE.md` 已标注）：**全量回归 579 项，OpContext 构造会 `SetProcessDPIAware()`（全进程生效）**，
多个 `op::Op` 实例在同一宿主的交互、OCR/YOLO 引擎的并发行为、截图缓存的跨实例共享 ——
这些**没有系统验证过**。而 OLA 文档明确写了「同句柄多线程排队 / 双句柄真并发 / 预热后并发」。

**建议动作**

1. 写 `ConcurrencyTest`：N 个实例 × M 线程，跑 OCR/找图/截图/绑定，断言无崩溃、结果正确、坐标不串。
2. 明确文档三段：**同一实例能否多线程调用**、**多实例是否共享引擎**、**引擎预热与并发上限**。
3. 若发现共享状态竞争 → 按实例隔离（这是唯一可能要动代码的地方）。

**性价比**：纯验证 1~2 天，能挡掉「多开炸了算谁的」这类最高频售后。

---

### ★ 3 A3：屏幕绘制 / 绑定窗口内绘制（DrawGui 最小组）

**为什么收益高**：44 个接口不用全做，**8 个就够 90% 场景**。

- 用户感知强：找图结果直接标在屏幕上，调试效率翻倍；截图报障一目了然。
- `DrawGui*Ex`（画在**绑定窗口客户区**、**不进 DX 截图**、窗口移动跟随）—— 这个特性组合很巧，
  正好解决「调试标记污染截图 / 影响识别」的老问题。
- 顺带能做「悬浮控制面板」（启停按钮、状态显示），把脚本从「命令行黑框」升级成「有界面」。

**建议首版**：`DrawRect` / `DrawCircle` / `DrawLine` / `DrawText` / `DrawImage` +
`DrawClear` / `DrawSetVisible` / `DrawSetClickThrough`，以及 **`DrawRectEx`**（绑定窗口版）。

---

### ★ 4 B1：YOLO 多任务（先 Segment + Pose）

**为什么收益高**：OP 已有完整 ONNX 地基（`onnxruntime.dll` + 类别感知 NMS + v8/v11 解析 + FromMem/FromFile/Ex2），
加任务类型是「同一引擎换后处理头」，边际成本远低于从零实现。

- **Segment**：掩码点位 —— 场景里「从一堆重叠目标里只取最上面那个」这类需求
- **Pose**：关键点 —— 「按钮在哪、手指在哪」比检测框精确得多
- Classify / Obb 优先级低（Obb 需求窄，Classify 用 Detect 单类能凑）

**建议**：先把引擎接口从 `detect` 抽象成 `task`，加 `YoloSegment` / `YoloPose` 两个入口，
沿用现有 Ex2 的 `json_options` 过滤/截断语义（保持一致，降低学习成本）。

---

### ★ 5 B4+B3：加密补全 + 汇编（低成本高感知）

**为什么收益高**：工作量小、纯 Win32/现成库、直接补掉「OP 做不了」的硬空缺。

- **加密**（约 1 天）：`AesEncrypt/AesDecrypt`、`Hmac`、`Pbkdf2`、`GenerateGuid`、`Md5File/ShaFile` —— BCrypt 直包。
  用途：授权校验、接口签名、配置加密。现在用户必须外挂 Python/C# 才能做。
- **汇编**（约 3 天）：`Assemble` / `Disassemble` / `AsmCall`（keystone + capstone，CMake 已有 vcpkg 通道）。
  用途：内存修改系的最后一块拼图 —— OP 已有全套内存读写 + 模块枚举 + VirtualProtectEx，**独缺「执行」**。
  补齐后 `ReadData → FindData → Disassemble → AsmCall` 闭环，内存系用户才真正完整。

> 这两项加起来不超过一周，但对「内存系 / 商用系」用户的选型决策权重很高。

## 六、明确「不做」的高收益诱惑

| 诱惑 | 为什么不接 |
|---|---|
| 视频处理 44 接口全量 | 需求密度极低；真要做只做 `OpenVideo`+`ExtractThumbnail`+`ReadFrameAtTime` 三件套 |
| VMware 47 接口 | 与「绑定 vmware 画面」绑定才成立；OP 不做虚拟机画面模式，单独做命令模块是断头的 |
| SQLite / 图像数据库 | 脚本自带 sqlite3；「图像数据库」是 OLA 私有格式，抄了也没有生态 |
| 驱动内核 / DMA | 完全不同的产品形态（要签名驱动、专用硬件），且与开源定位冲突 |
| 授权 / 自更新 | OP 的定位是插件，不是 SaaS 平台 |

---

## 七、三句话战略建议

1. **不要追接口数量。** OLA 993 个接口里有 200+ 是 `Xxx / XxxEx / XxxAddr / XxxFromBin` 语法糖和 58 个驱动接口。
   OP 348 个接口的「有效能力密度」更高。
2. **要追的是「轴」。** 元素层、视觉层、时间轴层这三条是**用户使用方式**的差异，不是功能表的差异。
   补上其中任何一条，OP 的能力矩阵就从「识别引擎」升级为「自动化平台」。
3. **最难追平的是 OLA 的商业化（授权 SaaS + 加密模型包 + 模块隐藏 + 每日计费）。**
   这不是技术问题而是产品定位问题。如果 OP 有商业化打算，这是**比任何接口都高的收益项**，
   但它需要独立的排期和法务/运营配合，不应混在功能迭代里做。
