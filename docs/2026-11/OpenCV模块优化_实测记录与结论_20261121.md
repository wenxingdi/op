# OpenCV 模块优化：实测记录与结论（2026-11-21）

> 用户要求 OCR 之后依次优化 OpenCV → 内存 → YOLO → 音量。这是第一站。
> 全部结论基于**实跑数据**，不猜测。基准来自仓库自带的
> `OpenCvBenchmark.DISABLED_MatchingHotPaths`，取 median（本机 UHD 730 方差大）。

---

## 一、结论先行

**找到并修复了一个真实瓶颈**：尺度精修路径从未接入图像金字塔，
1920×1200 满屏匹配单次要 330ms，而走金字塔只要 76ms。

**优化后**（同机同进程 median，最终干净构建）：

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| `bench_real_named_match` | 76ms | **43ms** | **-43%** |
| `bench_hard_scale_auto` | 331ms | **60ms** | **-82%** |
| `bench_real_scale_manual` | 718ms | **337ms** | **-53%** |
| `bench_real_scale_auto` | 1208ms | **755ms** | **-37%** |
| `bench_real_direct_candidates` | 371ms | **261ms** | **-30%** |
| `bench_game_coin_all` | 621ms | **447ms** | **-28%** |

> 中间过程数据（第一次干净测量）为 named 57 / scale_manual 460 / scale_auto 1029 / hard 90，
> 同机不同时间点跑仍有差异（本机方差大），但**每一项都优于原始基线**，方向确定。
> `game_coin_all` 与 `direct_candidates` 的改善来自 `pyramidFindFirstMatch` 候选数从 12 降到 4。

正确性：`OpenCv*` + `*Cv*` **35/35 全 PASS**（新增 1 条金字塔坐标精度用例）。

**剩余瓶颈已查明且判定为"不该在模块层解决"**（见 §五）。

## 二、先推翻两个错误假设（过程留痕）

### 2.1 假设一：尺度粗筛没做 → 错

初版方案文档判"缺尺度粗筛"。读代码发现**全部已存在**：

| 机制 | 位置 |
|---|---|
| 尺度粗筛 | `probeAutomaticScaleCandidates` |
| 源图金字塔缓存 | `prepareScaleProbeSourceCache` |
| 自适应降采样步数 | `scaleProbeDownsampleSteps` |
| 快速路径（先试 2 档） | `kScaleAutoFastPathCandidates = 2` |
| 强探针跳过 | `kScaleAutoStrongProbeSimilarity = 0.96` |

方案作废，重新定位。

### 2.2 假设二：自动模式调用次数太多 → 错

加临时计数器实测（已移除）：

```
[PROBE] refine scale=1.5 templ=144x144 roi=1920x1200 340.37ms
[PROBE] refine scale=1.5 templ=144x144 roi=1920x1200 327.72ms
[PROBE] refine scale=0.75 templ=72x72  roi=1920x1200 276.85ms
```

- 一次自动尺度调用**只做 3 次**全分辨率精修（不是 10 次）
- 但**单次要 330ms**

### 2.3 假设三：探针阶段慢 → 错

二次探针实测：

```
ENTER probeAutomaticScaleCandidates first=0 last=2 scales=10
  PROBED n=2 ms=34.9
ENTER probeAutomaticScaleCandidates first=2 last=10 scales=10
```

探针只花 **35ms**，占 1029ms 的 3%。**瓶颈百分百在精修。**

## 三、真正的根因

`refineScaleCandidate()` 调 `findBestPreparedMatch()`——**纯全分辨率暴力匹配**。
而同文件的 `MatchTemplate(named)` 走 `pyramidFindFirstMatch()`（粗层定位 + 逐级精修），
同样条件下 76ms vs 330ms，差 4.3 倍。

**尺度精修这条路从未接过金字塔。**

## 四、两处改动

### 4.1 尺度精修接入金字塔

`refineScaleCandidate` 内，`shouldTryPyramid` 成立时改走 `pyramidFindFirstMatch`：

```cpp
bool used_pyramid = false;
if (shouldTryPyramid(rectToRegion(roi), templ.width, templ.height, opcv::StripMode::None)) {
    // ... 构造 roi_source，调 pyramidFindFirstMatch
    pyramid_match.x += roi.x;   // 金字塔返回 ROI 内坐标，必须加回原点
    pyramid_match.y += roi.y;
    used_pyramid = true;
    if (definitive_miss) return true;   // 粗层已确定不命中，不做无谓全分辨率复算
}
if (!used_pyramid && !findBestPreparedMatch(...)) return true;  // 小图/小模板自动回退
```

**保守性**：最终 `score`/坐标来自金字塔 level 0（全分辨率），阈值语义不变；
金字塔不可用时逐字节回退原路径。

### 4.2 `pyramidFindFirstMatch` 候选数 12 → 4

原实现只要**一个**最佳命中，却向 `pyramidFindAllMatches` 传 12 个候选，
导致 level 0 要做 12 次局部精修，只用第 1 个。

正确性论证：`pyramidFindAllMatches` 返回前经 `dedupeMatchResults` +
`suppressOverlappingMatchResults`，二者都按 score 降序，故 `results.front()` 是全局最高分。
候选数只影响"多远的分支参与竞争"，前 4 名已覆盖粗层主要峰。

新增常量 `kPyramidFirstMatchCandidates = 4`，附带论证注释。

## 五、为什么停在这里（剩余空间评估）

### 5.1 还能做的（已评估，判定不做或暂不做）

| 优化 | 预期 | 为什么不做 |
|---|---|---|
| 源图金字塔跨调用缓存 | 中高 | 需要帧级缓存失效机制（截图变了要重建），生命周期问题比收益复杂 |
| 精修窗口按 level 收窄 | 低 | 现有 `radius = max(8, templ/3 + level*2)` 已合理，再收有漏检风险 |
| **OpenCV 重编（OpenCL + AVX2 + SIFT）** | **高** | **基建级变更**：改第三方库与构建链，影响体积/依赖/全量回归，超出"模块优化"范围 |
| `bench_real_scale_auto` 单点提速 | 中 | 该样本是 **1920×1200 满屏 + 144×144 模板**，属最坏情况；真实游戏找图有明确 ROI，收益远没那么痛 |

### 5.2 关键判断

`scale_auto` 的 1029ms 里，绝大多数是"在 1080p 整屏上做 3 次带金字塔的精确匹配"。
**这是算法的固有成本，不是实现缺陷**——除非重编 OpenCV 用 AVX2/OpenCL，
否则不可能有数量级改善。

用户的真实场景（游戏找图）几乎总是给 ROI（任务面板 220×236、血条 400×20、
技能栏局部），那些规模下 `shouldTryPyramid` 可能不触发，走的是轻量路径。

**因此判定：OpenCV 模块在"不重编底层库"的前提下已无显著优化空间。**

## 六、验证

### 6.1 正确性

`OpenCv*` + `*Cv*` **34/34 PASS**（改动前后一致）。

### 6.2 反向验证（过程中发现了一个真实测试盲区）

第一轮跑 `scripts/probes/reverse_verify_opencv.ps1` 时，**故意把金字塔坐标的 ROI 原点写错，
全部 34 个 OpenCv 用例仍然 GREEN** —— 这是关键发现：**现有测试从未覆盖金字塔路径的坐标精度**。

根因：唯一相关用例 `MatchTemplateScaleFindsScaledTemplate` 用
`18x18` 源图 + `4x4` 模板，`shouldTryPyramid`（需 ≥960×540 且模板 ≥32×32）**不成立**，
金字塔分支从未被执行。

**补测过程（又一串坑，值得记）**：

| 尝试 | 结果 | 教训 |
|---|---|---|
| 96×96 模板 + 1.5 倍贴图 | x 偏 109px | 条纹图案 1.5 倍后周期非整数，自动尺度候选里没有 1.5 |
| 原样 1.0 贴图，ROI = 整图 | 通过，但 sabotage 也通过 | **整图时 roi.x 恒为 0**，偏移 bug 天然测不出 |
| 原样 1.0 贴图，**ROI 带偏移 (900,400)** | **sabotage 红了，偏差正好 900px** | 必须用带偏移的 ROI 才能暴露该类 bug |

最终用例 `PyramidMatchKeepsAccurateCoordinatesOnLargeImage`：
1920×1080 大图 + 96×96 模板原样贴在 (1500,700)，ROI 取 (900,400,1000,640)，
断言坐标误差 ≤4px。**反向验证：把 ROI 原点写错 → 偏差 900px → 用例 RED**（已实测）。

- **RV-CV3**（真 bug）：金字塔坐标不加回 roi 原点 → **RED**（补测后成立）
- **RV-CV1**（候选数 12）：暴露新用例 x 偏 27px → 说明候选数确实影响精度，
  这也是把候选数定为 4 的**上界证据**（12 时更差，非更好）
- **RV-CV2**（关掉金字塔分支）：GREEN，证明该分支是纯性能加速、行为等价

### 6.3 踩到的坑（重要）

反向验证第一轮所有场景"无输出"，排查后发现：**改 `.cpp` 也可能不触发重编**。
虽然 `.cpp` 在 `build.make` 里是显式依赖，但本次 `TemplateMatcher.cpp` 的 obj
时间戳确实早于源码修改时间。

> 应对：所有验证脚本一律**强制删 obj 再构建**，并校验 obj 时间戳晚于补丁时间，
> 否则判 `INVALID-STALE-OBJ`。这条已写进本脚本。

## 七、给后续模块的可复用经验

1. **先量后改**：本次三次假设全错，全靠探针纠正。没有探针的"优化"大概率是自嗨。
2. **同机同进程比 median**：min 受缓存影响、avg 受离群影响，median 最稳。
3. **区分"纯性能改动"与"语义改动"**：前者反向验证应保持 GREEN（证明等价），
   后者应 RED。两者都要有。
4. **头文件/某些 .cpp 改完必须确认 obj 重编**，否则验证结论全是假的。
