## 一、现状盘点（实测代码，不猜）

### 1.1 引擎侧（质量不错，不动）

`OnnxYoloEngine.cpp` 已具备：
- **类别感知 NMS**（`class_aware_nms`，同类才互相抑制）
- **v8/v11 anchor-free 解析**（`(H/8)²+(H/16)²+(H/32)²`）
- **labels 自动加载**：从 ultralytics 嵌入的 ONNX metadata `names` 解析，
  两种 repr 都兼容；显式 `--labels=` 优先
- `--conf=` / `--iou=` / `--labels=` 参数
- 异常保护（`InitCorruptModelFailsGracefully` 等用例覆盖）

### 1.2 API 层（缺口在这里）

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| Y1 | **无类别过滤** | `YoloDetect(x1,y1,x2,y2,conf,iou)` 只有 conf/iou | 模型有 80 类时，想只取"人"必须调用方自己遍历 JSON 过滤 |
| Y2 | **无最大结果数** | 同上 | 密集场景可能返回上百条，JSON 膨胀 |
| Y3 | **无 ROI 之外的区域限定** | 只能传截图区域 | 已有（ROI = 截图区），**不算缺口** |
| Y4 | **坐标缺客户区补偿** | `it.left_top.x += x1`（只有截图偏移，没有 `_dx/_dy`） | 窗口模式下与其他模块（OCR/找图）坐标口径**不一致** |
| Y5 | **JSON 手工字符串拼接** | `retjson += L"{\"class_id\":"` 逐段拼 | 与 P0/P1 已统一使用的 `op::json` DOM 不一致，结构改动易出错 |

### 1.3 只有 2 个 C API

`OpYoloDetect` / `OpYoloDetectFromFile`。对比 OCR（20+）与 OpenCV（38），明显偏薄。

## 三、设计

### 3.1 新增 `OpYoloDetectEx2` / `YoloDetectEx2`

```
OpYoloDetectEx2(handle, x1,y1,x2,y2, conf, iou, json_options) -> JSON
```

`json_options` 可为空（等价于原有行为，但 JSON 更完整）：

```json
{"class_ids":[0,2], "labels":["person"], "max_results": 20}
```

| 字段 | 默认 | 说明 |
|---|---|---|
| `class_ids` | 不限 | 数字数组，按 class_id 过滤 |
| `labels` | 不限 | 字符串数组，按 label 名过滤（**大小写敏感**，与模型 metadata 一致） |
| `max_results` | 0=不限 | 按 confidence 降序截断 |

**过滤语义**：`class_ids` 与 `labels` 同时给时取**并集**（满足任一即保留）。
理由：调用方可能只知道 id 或只知道名字，取交集会让"我以为能命中"变成空结果，反直觉。

**非法 JSON / 未知字段** → 返回 `nullptr`（与 P1 FindStrBatch 一致，不静默降级）。

### 3.2 JSON 结构（改用 `op::json` DOM）

```json
{"ok":1,"code":0,"total":3,"returned":2,
 "results":[{"index":0,"class_id":0,"label":"person",
             "bbox":[10,20,110,220],"confidence":0.91,
             "cx":60,"cy":120,"w":100,"h":200}]}
```

新增字段：
- `total` / `returned`：过滤前/后条数（**让调用方知道是否被截断**）
- `index`：原始序号（便于与不过滤时的顺序对照）
- `cx/cy/w/h`：中心点与宽高（游戏里"点哪里"最常用，省得调用方自己算）

**向后兼容**：旧 `OpYoloDetect` / `OpYoloDetectFromFile` 的输出**保持原结构不变**
（`op::json` 序列化的字段顺序与手拼一致，且数值格式相同）。新增字段只在 `Ex2` 出现。

### 3.3 Y4 坐标口径修正

现状：
```cpp
it.left_top.x += static_cast<int>(x1);   // 只有截图偏移
```

应为：
```cpp
it.left_top.x += static_cast<int>(x1) + _dx;   // 截图偏移 + 客户区偏移
```

**风险**：这会改变既有 `OpYoloDetect` 的输出（窗口模式下坐标会多一个 `_dx`）。
**但**这正是"与 OCR/找图一致"所需要的，且 `_dx/_dy` 在非绑定窗口场景下为 0，
不影响现有用例。

> 决策：**修正**。理由：坐标口径不一致是真实缺陷，调用方混用 OCR 与 YOLO 结果会错位。
> 在 CHANGELOG 明确标注这是**行为变更**。

## 六、现实约束（必须说明）

**本机没有可用于正向验证的 YOLO 模型。**

现有 `yolo_test.cpp` 的 10 个用例里，绝大多数在测**失败路径**
（缺失文件 / 损坏模型 / 非法句柄 / 远程别名拒绝）。唯一有模型的是
`UnifiedEntryAcceptsOnnxModelPathDirectly` 与 `EndToEndAutoLoadsLabelsFromModelMetadata`，
它们依赖 `testdata` 或内嵌资源。

因此：
- **过滤 / 截断 / JSON 结构**这些逻辑可以**脱离模型**单测（直接喂 `vyolo_rec_t`）
- **端到端检测**如果本机无模型，用例必须 `GTEST_SKIP` 并写明原因，**不假装验证过**

这是本阶段诚实性的关键：宁可跳过并说明，不写"跑了但没真跑"的用例。

## 七、实测与结论（2026-11-21）

### 7.1 交付

| 层 | 符号 | DISPID |
|---|---|---|
| C API | `OpYoloDetectEx2` / `OpYoloDetectFromFileEx2` | — |
| C++ | `op::Op::YoloDetectEx2` / `YoloDetectFromFileEx2` | — |
| COM | 同名 2 个 | **454 / 455** |

**`YoloDetectFromFileEx2` 是本轮新增的"可验证入口"**：
屏幕版 Ex2 依赖绑定窗口，测试机没有可绑定窗口，过滤逻辑无法闭环；
文件版让过滤/截断/JSON 契约**能用真实模型验证**（见 7.3）。

### 7.2 改动

1. **JSON 改 `op::json` DOM**：原实现手拼字符串（`retjson += L"{\"class_id\":"`），
   结构改动易漏转义。改用 DOM 后由 `Stringify` 统一负责。
2. **新增过滤/截断**：`{"class_ids":[],"labels":[],"max_results":N}`
   - `class_ids` 与 `labels` 取**并集**（满足任一即保留）
   - `max_results` 按 confidence **降序**截断
3. **坐标口径修正**：`it.left_top.x += x1` → `+= x1 + _dx`
   原实现只有截图偏移，窗口模式下与 OCR/找图**坐标错位**。
   > **这是行为变更**：非绑定窗口 `_dx/_dy` 为 0，不影响现有用例；
   > 但绑定窗口时 `OpYoloDetect` 的坐标会整体平移 `(_dx,_dy)` —— 这是**修正**，不是回归。
4. **Ex2 额外字段**：`total`（过滤前）/ `returned`（过滤后）/ `index` / `cx` / `cy` / `w` / `h`。
   旧接口**不**加这些字段（保持向后兼容，有用例断言）。

### 7.4 诚实记录：一个**没能闭环**的验证点

`solo_meta_test.onnx` 是脚本生成的极简模型，**NMS 后恒定只输出 1 条**。
实测过 320×240、1280×960、1280×1280 四块拼贴，conf 低到 `0.0001`，始终 `total=1`。

因此 **`max_results` 的"截断到小于总数"这一支无法用真实数据验证**。
`MaxResultsTruncatesAndReportsTotal` 已改为：
- `total > 1` 时断言真实截断（**换一台有多条检测结果的机器会自动生效，不会假绿**）
- `total == 1` 时 `GTEST_SKIP` 并写明原因

**这是本阶段唯一未闭环的点，明确记录，不掩饰。**

### 7.5 过程中发现的一个真实导出缺陷（重要）

`OpYoloDetectFromFileEx2` 一开始被追加到 `op_c_api.h` 的 **`extern "C"` 块之外**，
在 x64 下变成了 **C++ 修饰名导出**：

```
?OpYoloDetectFromFileEx2@@YAPEB_WPEAUop_c_context@@PEB_WNN1PEAH@Z
```

后果：**Python / 易语言 / 任何按裸名 `GetProcAddress` 的客户端都调不到**，
而 C++ 侧测试却能正常链接下来 —— **测试全绿但功能不可用**。

x86 靠 `.def` 生成裸名所以不受影响，**这个坑只在 x64 出现**。

已修正：声明移进 `extern "C"` 块内，实现补 `extern "C" { ... }` 包裹。
验证：`dumpbin /exports` 确认现在是裸名 `OpYoloDetectFromFileEx2`。

**这条已写进 CLAUDE.md 的踩坑速查**——新增 C API 一律要检查导出名。
