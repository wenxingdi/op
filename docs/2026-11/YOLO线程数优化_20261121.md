# YOLO 线程数优化 + DirectML 可行性评估（2026-11-21 19:10）

> 状态：**已实现并提交**。附带一个明确结论：**D1 DirectML 不做**，理由见 §六。

## 一、结论先行

| 项 | 结果 |
|---|---|
| 缺陷 | `OnnxYoloEngine::Impl` 构造里写死 `SetIntraOpNumThreads(1)` |
| 代价 | 纯推理 **36.9ms → 7.6ms**（放开线程后），单线程慢 **4.8 倍** |
| 端到端（含 BMP 解码 + 预处理 + NMS） | **57ms → 31ms**，约 **1.8 倍** |
| 修法 | 默认不设置（交给 ORT 用物理核）；新增 `--threads=N`；`--threads=0` 显式复位 |
| 回归 | `Yolo*` **19 PASS / 1 SKIPPED**（既有 skip）；全量 **547 PASS / 3 FAILED**（既有 WGC 环境项） |

## 二、先量后改：为什么要动这一行

改之前没有任何证据说明单线程是错的 —— 也可能当初是为了避免多实例抢线程。
所以先写探针，**不碰产品代码**。

### 2.1 基准模型的来源问题（必须解决的前置）

本机**没有可用 YOLO 模型**：仓库里只有 `tests/testdata/yolo_meta_test.onnx`，
那是单 `Constant` 节点的假模型（跑一次 0.2ms，任何线程配置都一样快，测不出东西）。

于是加了 `scripts/gen_yolo_bench_model.py`：用 onnx 现搭一个
`3→16s2 → 32s2 → 64s2 → 64×3x3 ×8@80x80 → 1x1 头` 的顺序卷积网，
输入 1×3×640×640，输出 `[1,84,8400]`，约 2.4 GFLOP
（YOLOv8n@640 约 8.7 GFLOP，同量级偏小）。**只用于线程/EP 扩展性基准，不是可用检测模型。**

### 2.2 裸 ORT 探针（`scripts/probes/yolo_thread_probe.cpp`）

直接 ORT C++ API，12 次取中位数：

| intra-op 线程 | median | 相对单线程 |
|---|---|---|
| 1 | 36.91 ms | 1.00 |
| 2 | 19.02 ms | 0.52 |
| 4 | 10.58 ms | 0.29 |
| 8 | 8.04 ms | 0.22 |
| 不设置（ORT 默认） | 7.63 ms | **0.21** |

极小模型（0.2ms 那档）各配置同为 0.19~0.23ms —— **说明放开线程不会在"小图快跑"
场景反而变慢**，因此可以放心把默认交回 ORT。

## 三、改法

```cpp
// Impl()：删掉 sopts.SetIntraOpNumThreads(1);
// load()：建会话前按需覆盖
if (m_threads > 0) { sopts.SetIntraOpNumThreads(m_threads); m_threads_applied = m_threads; }
```

`--threads=N` 解析加在 `init()` 的 argv 循环里（与 `--conf/--iou/--labels` 同处）：

| 取值 | 行为 |
|---|---|
| 不传 | 用 ORT 默认（物理核数） |
| `--threads=1..64` | 用指定值（多实例并发时压线程，免得 N 个会话各开满线程抢核） |
| `--threads=0` | **显式复位成默认**（见 §五） |
| `--threads=9999` / `--threads=abc` | 忽略，不报错（`abc` 经 atoi 得 0 → 等价复位） |

## 四、端到端实测（`scripts/probes/yolo_thread_bench.py`）

走**真实库**（ctypes → `op_c_api_x64.dll` → `OpSetYoloEngine` → `OpYoloDetectFromFile`），
640×640 输入，12 次取中位数，三轮重复：

| 配置 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 比值 |
|---|---|---|---|---|
| `--threads=1` | 54.18 | 58.88 | 59.14 ms | 1.00 |
| `--threads=4` | 29.64 | 34.28 | 33.62 ms | **0.55~0.58** |
| `--threads=0`（默认） | 29.33 | 31.93 | 32.50 ms | **0.54~0.55** |

> 端到端只快 1.8 倍，而纯推理快 4.8 倍 —— 差额是**串行部分**：
> BMP 解码 + resize + letterbox + NMS。这条账要算清楚，别拿"快 4.8 倍"对外宣传。

## 五、过程中发现的两个坑

### 5.1 日志会骗人（写死单线程时日志仍打 `threads=4`）

我先把"生效值"打到 init 日志里，以为可以当判据。反向验证时发现：
**把实现改回写死 `SetIntraOpNumThreads(1)`，日志照样打印 `threads=4`** ——
因为日志打的是"请求值"，不是"实际写进 SessionOptions 的值"。

结论：**这类改动的唯一可信判据是耗时比**。所以最终验证手段是 §四 的基准脚本，
其判据写死为 `t(4)/t(1) < 0.6 且 t(auto)/t(1) < 0.6`，不满足就非 0 退出。

### 5.2 `YoloDetector` 是进程级单例 → `--threads` 会残留

`YoloDetector::getInstance()` 是静态单例，所以同一个进程里第二次
`SetYoloEngine` 不传 `--threads` 时，**上一次的线程数还在**（`--conf/--iou` 同理，是既有行为）。

第一版基准就踩了这个坑：`auto` 测出来和 `threads=4` 一模一样，因为根本没复位。
修法：允许 `--threads=0` 表达"改回默认"，基准改用它。
（没有改成"每次 init 都复位"——那会与 `--conf/--iou` 的既有语义不一致。）

## 六、D1 DirectML：评估结论是**不做**

用户原始规划里 D1 是"DirectML GPU 推理"。本轮实测后判定**不值得投入**，理由三条：

1. **依赖面要换**：`build/_deps/onnxruntime/onnxruntime-win-x64-1.19.2` 是 **CPU-only** 包
   （`include/` 下只有 `cpu_provider_factory.h`，`lib/` 里没有 `onnxruntime_providers_dml.dll`）。
   上 DirectML 要换 NuGet 包 + 多分发一个 DLL + 加 EP 初始化代码，属基建级变更。
2. **收益上限已被串行段吃掉**：端到端 31ms 里推理只占约 8~10ms，其余是解码/预处理/NMS。
   就算 GPU 把推理压到 0，端到端也只有 ~31ms → ~22ms，**上限 25%**。
3. **本机 GPU 是 UHD 730（核显）**：YOLOv8n 这类小模型在核显上走 DirectML 通常比
   8 线程 CPU 更慢（PCIe 往返 + 核显算力不足）。要证伪得先装 DML 包实测，
   而实测前置成本已经高于预期收益。

**因此：D1 关闭。** 如果将来真实模型变大（yolov8m/l）或换独显机器，这个结论要重算。

D3（多模型热切换）仍属新增能力，不在"优化"范围。

### 7.1 做不到的部分（如实记录）

想过在 gtest 里直接断言"实际生效线程数"，写了 `OnnxYoloEngine::intra_op_threads()` 干这件事。
但 **`op_test` 不编译 libop 的 yolo 源**（YOLO 相关用例全部走 `op_c_api.dll` 的 C API），
引用 `op::yolo::OnnxYoloEngine` 会 LNK2019。为此给 op_test 加 yolo 源 + ORT 链接
属于为一条断言改构建结构，收益不划算 → **放弃**，改为 §四 的进程内基准脚本。

`intra_op_threads()` 保留（3 行，供将来诊断），但**没有用例覆盖它**，这一点明确记录。
