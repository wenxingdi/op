## 二、x86 打通的三个真实卡点

### 2.1 `cor.h` 找不到（C1083）

`image/Image.h → atlimage.h → BlackBone/PE/ImageNET.h` 需要 `cor.h`。
x64 的 cl 会从 VS 安装目录的 Team Tools 里找到，x86 不会 → 报 C1083。

修法：把 `BlackBone/src/3rd_party` 加进 `INCLUDE`（`BLACKBONE_3RD`）。

### 2.2 ninja 在沙箱下卡死（不 spawn cl.exe）

沙箱里 ninja 接不了子进程的输出管道：一有编译动作就卡在等 I/O，
CPU 0.06s、线程 WaitReason=15、从不启动 cl.exe。

修法：注入 `CMAKE_CXX_COMPILER_LAUNCHER` 指向 `_wb_ninja_record.py`，
由它把 stdout/stderr 重定向到**真实文件句柄**（不是管道）再 spawn 编译器。
`_wb_build_op_x86.py` 自己也改成**不留管道**（`DEVNULL`），输出全部落
`workbench/tmp/ninja_compile.log`。

### 2.3 ⚠ launcher 不能用 `os.execv`（引号被吃掉 → 假象编译错误）

第一版 launcher 用 `os.execv` 做"进程替换"。Windows 的 CRT `_wexecv`
**只是把 argv 用空格拼成命令行、不做任何引号转义**，于是：

```
-DOP_VERSION="5.2.0"   →  子进程重新解析时引号被吃   →   -DOP_VERSION=5.2.0
OP_WIDEN_TEXT(OP_VERSION) 展开成 L5.2.0  →  error C2065: "L5": 未声明的标识符
```

这个错误看起来像是 `op_c_api.cpp(205)` 的代码有问题，实际是**包装器在破坏命令行**。
换成 `subprocess.run(cmd, stdout=fh, stderr=fh)` 后正常（走 list2cmdline，转义正确），
退出码用 `sys.exit(returncode)` 精确转发。

> 曾担心"spawn 再返回会丢退出码"——不会。丢退出码的传言来自管道卡死那次的误判。

## 三、⚠ `OP_VERSION` 那个"修复"是误判（已回滚，勿再改）

上一轮把 `OpRuntime.cpp::Op::Ver()` 的 `_T(OP_VERSION)` 判成 bug，理由是
"本 TU 没包含 `base/AutomationModes.h`，OP_VERSION 是未定义标识符"。**这个判断是错的**：

```
libop/CMakeLists.txt:422   OP_COMMON_DEFINITIONS 里
    OP_VERSION="5.2.0"          ← 编译器 /D 注入，值本身就是窄字符串字面量
```

所以 `_T(OP_VERSION)` = `__T("5.2.0")` = `L"5.2.0"`，**本来就是对的**，输出 `OpVer() = "5.2.0"`。
`base/AutomationModes.h` 里那个 `#ifndef OP_VERSION` 的 `MAKE_OP_VERSION(5,2,0,0)` 是**死代码**
（CMake 总会先定义），不要拿它当归一来源。

由此可知：上一轮报的 `OpRuntime.cpp(30): error C2143` 是**自己改坏引入的**
（`L"" OP_VERSION` 把宽字面量和窄字面量拼接 → 非法），不是真 bug。
已 `git checkout` 回滚，源码与 `7e8d0ae` 一致。

> 教训：判断"宏未定义"之前先 grep `CMakeLists.txt` 的 `DEFINITIONS`，
> 别只看头文件包含链。运行期验证一次 `OpVer()` 返回值，比读 20 分钟头文件快。
