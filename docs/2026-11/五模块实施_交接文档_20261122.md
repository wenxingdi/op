## 二、各批交付明细

### 批 A · 多实例/并发（已提交 `2fd2206`）

**做了什么**
- `OpContext` 新增原子计数：`in_flight` / `peak_in_flight` / `reentrant_hits` / `calls_total`
- C API 门面 `CallScope` 统一计入；首次撞并发打一条日志（每句柄仅一次）
- 新增 `OpConcurrencyInfo`（C++ / C API 裸名导出），返回：
  `{"id":1,"in_flight":0,"peak":3,"reentrant":12,"calls_total":880,"image_count":4,"bound":0,"thread_safe":false}`

**关键决策**：**不改变**"单实例非线程安全"的既有约定（`libop.h` 顶部明文）。
本批只把"静默污染"变成"可观测事件"。串行化会把用户的错误用法伪装成能跑，更难排查。

**测试**：`tests/concurrency_batch_test.cpp` 6 条；2 处反向验证（去掉 reentrant 计数 / 去掉 peak 更新）均如愿变红。

**踩坑记录（已修）**
`OpContext.h` 引入 `<atomic>` 后，如果放在项目头之后，会让 MSVC 的
`<chrono>/<filesystem>/<__msvc_tzdb.hpp>` 解析崩（`error C2061 true_type`、`C3861 is_same_v`）。
**修法：标准库必须成组前置**（`atomic/chrono/filesystem/map/mutex/string/thread/vector` 全部放最前）。
同一坑在 `op_c_api.cpp` 也复现过一次（`OpContext.h` 必须放在 `include/libop.h` 之前）。

### 批 C · YOLO 任务维度（已提交 `fc7f915`）

**做了什么**
- 引擎抽象从「只有 `detect`」升为 `Task`：`Detect` / `Segment` / `Classify`
- 任务判定顺序：先读 ONNX metadata 的 `task` 字段 → 读不到再按输出形状推断
- 新增 5 个符号：`YoloClassify` / `YoloClassifyFromFile` / `YoloSegment` / `YoloSegmentFromFile` / `YoloGetModelInfo`
- **核心契约**：任务不符返回 **-1**，无结果返回 **0**。两者混用会掩盖"模型选错了"

**Segment 实现要点**
- 双输出（检测头 + proto）按**维数**自动分派，不依赖输出顺序
- 掩码：proto 网格上算 `coeff·proto > 0` → 8 邻域轮廓跟踪 → 抽稀 → 映射回原图坐标
- 输出 `polygon`（原图坐标）与 `mask_area`（原图尺度像素面积）

**修的两个真实缺陷（都是本轮实测踩出来的）**
1. **anchor 轴判定**：单 anchor 时 `min/max` 会把属性维当 anchor 维（实测 `nc=-5`）。
   改为：先按"输入尺寸算出的 anchor 数"对轴（真实 v5/v8/v11 都命中），
   再按 `属性维 >= 4+nm` 兜底（较小维必为属性维），都对不上才用 min/max。
2. **`SetYoloEngine` 加载失败后仍在跑旧模型**：`init` 返回失败但旧 Session 还挂着，
   对脚本是"换模型失败却继续用旧模型出结果"的静默危险行为。现在 init 失败即重建引擎（置回未加载态）。

**测试资产**：`scripts/gen_yolo_task_test_models.py` 生成
`tests/testdata/yolo_cls_test.onnx`（分类，5 类）与 `yolo_seg_test.onnx`（分割，单 anchor）。
**注意**：生成脚本要用托管 venv 的 python：
`C:/Users/lc/.workbuddy/binaries/python/envs/default/Scripts/python.exe`

**测试**：`tests/yolo_task_test.cpp` 6 条；2 处反向验证变红；`Yolo*` 全组 27/27。

**测试里踩的一个顺序坑（重要）**
YOLO 引擎是**进程级单例**。`ModelInfoReportsNoneBeforeLoad` 单跑绿、全跑红，
原因是前面的用例已经加载过模型。修法：用例自己先 `SetYoloEngine("不存在.onnx")` 制造未加载态。
—— 这条同时也暴露了上面第 2 个真缺陷。

### 批 B · DrawGui 补齐（已提交 `79c4780`）

**做了什么**
- 屏幕层：`DrawCircle`、`DrawImage`（带 alpha）
- 绑定层（对齐 OLA `DrawGui*Ex` 语义）：
  `DrawRectEx` / `DrawCircleEx` / `DrawTextEx` / `DrawClearBind` / `DrawGetCount`
  - 坐标 = **绑定窗口客户区**（与找色/鼠标同口径）
  - 画在独立透明窗口，**不写目标 DX 后台缓冲 → 不进 DX 截图**
  - 窗口移动/缩放跟随（250ms 轮询 + 每次绘制校正）
  - **未绑定窗口时显式返回 0 并记日志**（不静默画到屏幕）
- 修正既有认知：**DrawGui 最小组早已存在**（`DrawRect/Line/Text/Clear/SetVisible`，2026-10-15 P2 落地）

**已知限制（已在代码与头文件注明）**
- `DrawRectEx` 的 `mode=0`（填充）**按描边绘制**并在日志说明，不假装支持填充
- 只支持描边，无独立 `DrawSetColor`（绑定层默认白色）

**层覆盖**：C++ / C API（7 个裸名导出，354→367）/ COM（DISPID 484~490）
**坑**：`libop/com/OpAutomation.h` 是**手写**声明，不是 MIDL 产出。
改 `op.idl` 后必须同步这里，否则 `error C2509 成员函数没有在类中声明`（已在头文件加注释）。

**测试**：`tests/draw_batch_test.cpp` 5 条。
诚实说明：**不测像素级视觉正确性**（分层窗口不在本进程截图链里，判据不稳），可视化验收走人工目视。

### 批 D · 汇编（🟡 未提交，工作区有改动）

**已完成**：`AsmCall`（`libop/op/OpAsm.cpp`）
- 在目标进程执行机器码并取返回值；`hwnd=0` 表示**当前进程**（便于自测）
- `code_hex` 形如 `"48 C7 C0 2A 00 00 00 C3"`（需自带 ret），支持 `??` 占位（按 int3 填充）
- 纯 BlackBone（`RemoteExec::ExecInWorkerThread`）+ Win32，**无新依赖**
- 成功后立即释放可执行内存；上限 64KB；失败一律显式返回 + `error` 文本

**阻塞项（如实记录，不要假装完成）**：`Assemble` / `Disassemble` **未实现**
- 需要 keystone / capstone。两者在 vcpkg **有 port**，但本机装不上：
  vcpkg 引导自身工具链时用 `CreateFileW` 重定向 stdin 解压 7z，
  在沙箱里返回 `Access is denied`（`calling CreateFileW stdin failed with 5`）。
  手工把 7z 解包到 `downloads/tools/` 也无效 —— vcpkg 仍坚持走自己的解压分支。
- **已做的诚实处理**：这两个接口存在且**显式失败**（返回 nullptr、JSON 带 `error` 说明原因），
  API 面（头文件/C API/COM 位置）已预留，后续接上不用改签名。
- **恢复方式**：在有网络无沙箱的机器上
  `vcpkg install keystone:x64-windows-static capstone:x64-windows-static`
  然后按 `OpAsm.cpp` 底部 TODO 接上。

**测试**：`tests/asm_batch_test.cpp` 5 条，**全部走 hwnd=0 当前进程路径**（5/5 PASS）。
未测目标进程路径（需第三方进程 + 管理员权限，属环境依赖项）。

**未提交的改动**：`include/libop.h`、`include/op_c_api.h`、`libop/CMakeLists.txt`、
`libop/c_api/op_c_api.cpp`、`tests/CMakeLists.txt`、新增 `libop/op/OpAsm.cpp` + `tests/asm_batch_test.cpp`。

## 四、新会话必须知道的踩坑清单（省你半小时以上）

1. **构建**：只能用 `python scripts/build/_wb_build.py`（不是 `_wb_build.py` 直接当 ps1 跑），
   且**必须显式用** `D:/Program Files/Python312/python.exe`（PATH 里的 python 是 WindowsApps 桩，会报
   "系统无法访问此文件"）。脚本若报 `UnicodeEncodeError`，先设 `$env:PYTHONIOENCODING="utf-8"`。
2. **看构建错误**：控制台是 GBK 乱码。正确姿势：读 `build/nmake-x64-Release/_wb_build_out.txt`
   （UTF-8），筛 `error C|error LNK`。
3. **跑测试**：必须先
   `$env:TEMP="$pwd\workbench\tmp"; $env:TMP=$env:TEMP; $env:PATH="$pwd\build\nmake-x64-Release\libop;$env:PATH"`
   且 cwd = 仓库根 `D:/AutoPro/op-master/op`。
4. **构建与测试不能并行**（`op_test.exe` 占用 lib → LNK1104）。
5. **标准库前置**：任何新增 `#include <atomic>` 等，必须放在项目头**之前**，否则 MSVC 标准库会解析崩
   （见批 A 踩坑）。`OpContext.h` 已处理，新文件照抄它的 include 顺序。
6. **COM 手写头**：改 `libop/com/op.idl` 后，**必须同步** `libop/com/OpAutomation.h`（手写声明）。
7. **新增 C API 必须是裸名导出**：声明要写在 `include/op_c_api.h` 的 `extern "C" { ... }` 块**内部**。
   自查：`dumpbin /exports build/nmake-x64-Release/libop/op_c_api_x64.dll`。
8. **已知失败项**：`MouseKeyTest.BindWindowDxSuffix*`、`WindowStateTest.DxBindToSameIntegrity*`、
   `HookCaptureTest.*`（8 条 DX/GL）是**环境项**，干净基线同样失败，不是你的锅。
   `CaptureModeTest.DownCpu*` 是**偶发 flaky**（单跑/成组跑均 PASS，只在长跑里偶现），也不要误判为回归。
9. **正向/反向验证都要做**：本仓库约定新能力必须带端到端用例，且断言要能"故意改错 → 必须 FAIL"。
   ⚠ 本轮我在批 D 上踩过一次：写了断言却**验证不出**它有效（去掉校验用例仍绿），
   最后如实改成"代码保留 + 注释说明未证明了必要性"，而不是硬凑一个假绿的断言。
   **新会话请保持这个标准：宁可诚实记录没证明，不要写假绿断言。**
