## 二、逐批结论（只写值得记的）

### A 批：并发从"口头约定"变成"可观测事件"

**做了什么**：`OpContext` 加 4 个原子计数，C API 门面 `CallScope` 统一计入，
新增 `OpConcurrencyInfo` 诊断接口。

**最关键的决策是"不做"**：**不**把单实例改造成线程安全。348 个方法逐个加锁会显著掉性能、
有死锁风险，也和大漠/OLA 的单实例语义不一致。本批的价值在于把"静默污染"变成
"可观测 + 首次告警"——串行化会把用户的错误用法伪装成能跑，更难排查。

**留下的坑（后续各批都受影响）**：标准库头必须成组前置。`<atomic>` 放错位置会让 MSVC 的
`<chrono>/<filesystem>` 解析崩（`C2061 true_type`）。本批之后所有新文件都照 `OpContext.h` 的顺序写。

### C 批：任务维度，以及两个实测出来的真缺陷

**契约先行**：任务不符返回 **-1**、无结果返回 **0**。这两者混用会掩盖"模型选错了"，
而"模型选错了"是 YOLO 排障里最常见的根因。

**两个缺陷都是实测踩出来的，不是读代码想出来的**：

1. **anchor 轴判定错误**：单 anchor 时用 `min/max` 判轴，会把属性维当 anchor 维
   （实测算出 `nc = -5`）。改为三级判定：先按"输入尺寸算出的 anchor 数"对轴，
   再按"属性维 >= 4+nm"兜底，都对不上才回退 `min/max`。
2. **`SetYoloEngine` 加载失败后仍跑旧模型**：`init` 失败但旧 Session 还挂着，
   对脚本表现为"换模型失败却继续用旧模型出结果"——**静默的危险行为**。现在 init 失败即置回未加载态。

第 2 条是在修测试顺序问题时顺带发现的（用例单跑绿、全跑红，因为引擎是进程级单例，
前面的用例已加载过模型）。**测试顺序问题有时是产品缺陷的探针**，这条值得记住。

### B 批：两处认知修正 + 一条诚实限制

**修正 1**：规划原本说"DrawGui OP 零覆盖"，实际最小组（`DrawRect/Line/Text/Clear/SetVisible`）
**2026-10-15 P2 就已落地**。本批的真实工作量是"补三种真正天天用的图元 + 绑定窗口内绘制"。

**修正 2**：绑定层坐标口径确定为**客户区**（与找色/鼠标一致），而不是屏幕坐标。
这个选择让"找色 → 画框 → 点击"三步用同一套坐标，不需要脚本自己换算。

**诚实限制**：`DrawRectEx` 的 `mode=0`（填充请求）**按描边绘制**，并在日志里明说。
不假装支持填充——画出个空心的矩形说"填充了"比报错更害人。

**测试的诚实说明**：不测像素级视觉正确性。分层窗口不在本进程截图链里，判据不稳；
可视化验收走人工目视。这一条是"如实记录测不了"，而不是"测过了"。

### D 批：做了能做的，没做的明确挂起

`AsmCall` 用纯 BlackBone + Win32 落地，无新依赖，5/5 PASS。

`Assemble` / `Disassemble` **阻塞**在 vcpkg 装不上 keystone/capstone（vcpkg 引导工具链时用
`CreateFileW` 重定向 stdin 解压 7z，沙箱拒绝）。

**没有偷偷降级成"写个假汇编器"**：产出错码且极难排查，比没有更糟。
两个接口存在且**显式失败**（返回 0 + JSON 带 `error` 说明原因），签名已预留。

### E 批：本批的重点是"落点选对了"

规划原文说"找出各输入方法的共同落点"。读代码后发现 **op 层不是共同落点，后端原语才是**——
这条修正直接决定了录制质量：

| 钩在 op 层 | 钩在原语出口（实际做法） |
|---|---|
| `LeftClick` → 1 条事件 | `LeftClick` → `down` + `up` 两条 |
| 双击 → 1 条 | 双击 → 4 条（真实按下序列） |
| 回放不出"按了几下/按住多久" | 可逐条重放，时序完整 |

对应地，**合成方法（`LeftClick`/`DoubleClick`/`KeyPress`）一律不钩**——它们内部会走到原语。

两条刻意的"不静默"：
- **主从不阻塞**：输入是边沿事件，迟到即错位（按 200ms 前的坐标去点，点的是别处）。
  队列满（256）丢事件并计入 `async_dropped`，而不是拖慢主实例。
- **未绑定时 LOAD 返回 `bound:0`**：坐标会按屏幕语义回放，与录制时的客户区语义**不同**。
  这个差异不兜底，直接报给调用方。

## 三、这一轮踩的坑（按代价排序）

### 1. 单例跨 DLL 不唯一 —— 本批最贵的坑

**现象**：`STOP` 永远不生效，回放照走完 2s 的间隔。

**诱因**：总线写成函数内静态变量。测试进程同时载入 `op_com.dll` + `op_c_api_x64.dll`，
而 `op_test.exe` 又直接编进了 `WinMouse.cpp` / `InputEventBus.cpp` →
**进程里三份 `instance()`**：录制钩子在 exe 那份，`OpInputPlayback` 走 op_c_api.dll 那份。

**这不止是测试问题**：发布环境里 COM 入口与 C API 入口同样各录各的。

**修法**：单例的**状态**放进进程级命名共享内存（`CreateFileMapping` 名字带 PID +
`MapViewOfFile` + `InterlockedCompareExchangePointer`），各模块的 `InputEventBus` 只持有指针。

**判据**：`InputTimelineBusTest.BusIsSingleInstanceAcrossModules` 直接比较两边 `identity()`。
退回静态变量该用例必红（**已实测**：exe 侧 `...7BB0` vs op_c_api 侧 `...4350`）。

> 排查过程中我一度**误判**这个坑是主因（其实不是），但修它是正确的——它是个真 bug。
> 真因见下一条。这段弯路本身值得记：**同时存在两个问题时，先修的那个"没让测试变绿"
> 不代表它不是 bug**。

### 2. 用例自己堵住了消息泵 —— 真因，且极易误判成实现缺陷

**现象**：`PlaybackStopInterruptsLongWait` 一直红，`elapsed ≈ 1800ms`（≈ 2000 − 200）。

**误判链**：先怀疑 STOP 没置位（否定，标志确实为真）→ 怀疑多份单例（否定，identity 相同）
→ 怀疑 `impl_` 不同（否定）→ 最后定位：**回放线程卡在 `SendMessage` 上**。

**真因**：`IN_WINDOWS` 模式的 `MoveTo` 走 `SendMessageTimeout(SMTO_BLOCK, 2000ms)`，
而被调窗口的 WndProc 在**用例自己的线程**上跑。用例在主线程 `sleep`/`wait_for` 等回放线程时
没抽消息 → SendMessage 等到超时。

**修法**：等待一律走 `pump_wait()`（边等边 `PeekMessage`/`DispatchMessage`）。

**教训**：**涉及 `SendMessage` 的用例，等待必须泵消息，否则你测的是自己的死锁。**
另外，1800 这个数字（而不是 2000）本身就是线索——它说明「STOP 之后还等了 1800ms」，
而不是「整个回放 2000ms 没被打断」。

### 3. 一条假绿断言（反向验证 4 第一版）

初版断言：回调里调一次 `MoveTo`，期望重入 1 次。

**反向验证结果：去掉护栏后仍然通过** —— 因为 `reenter_handle` 被置空，递归深度只有 1 层，
护栏在不在都一样。这正是交接文档警告过的坑。

**处理**：没有保留这条断言，而是重写成「回调每次都重新装弹 + 统计嵌套深度」。
去掉护栏会打到 200 次预算 → 必红（**已实测**：`reenter_calls = 200`）。

### 4. 反向验证本身也要验证落点

第一次做「去掉 LEFTUP 钩子」的反向验证时，改的是 `IN_NORMAL` 分支，但测试用 `windows` 绑定模式
→ 走的是 `send_windows_button`，改错了地方，用例照绿。改到正确落点后立刻变红。

**教训**：反向验证要确认「改的那行代码真的在被测路径上」，否则你以为在证伪，其实在自欺。

### 5. 测试目标的链接集合

`op_test` 直接编进了 `WinMouse.cpp` / `KeyboardBackend.cpp`（`op_com` 只导出 `op.def` 的符号），
所以总线实现与 `JsonValue.cpp` 也必须编进去，否则 `LNK2019`。
这三行是踩了两次 `LNK2019` 才补全的。

## 五、没做到的（如实清单）

| 项 | 为什么没做 | 影响的严重程度 |
|---|---|---|
| `Assemble` / `Disassemble` | vcpkg 装不上 keystone/capstone（沙箱拒绝 vcpkg 的解压方式）；API 面已预留 | 中：显式失败，不误导 |
| DX 绑定模式下的事件**回放** | 回放走 WIN 语义；DX 移动需目标进程内载入器就位 | 中：录制不受影响，回放跨模式一致性未验证 |
| 回放对**目标窗口**的实际效果 | 需真实绑定窗口 + 时间竞争，判据不稳 | 低：事件计数/时序已闭环，像素级属人工验收 |
| 主从 slave 侧实际效果 | 同上 | 低：链路/丢弃/不阻塞已闭环 |
| 监听回调跨线程投递 | 与 OLA 同构（产生事件的线程上同步触发），未加"投递到指定线程"选项 | 低：语义与竞品一致且已写明 |
| DrawGui 像素级视觉正确性 | 分层窗口不在本进程截图链里，判据不稳 | 低：人工目视验收 |
| AsmCall 目标进程路径 | 需第三方进程 + 管理员权限 | 中：当前进程路径已闭环 |
| Pose / Obb / 多模型热切换 / TensorRT·NCNN | 需额外规格或整套生命周期设计 | 低：明确不在本轮范围 |

## 七、给下一个接手的人

1. **先读代码再信文档**，包括这份。规划里的接口落点（E 批的 op 层 vs 后端原语）就是错的。
2. **反向验证要确认改到了被测路径上**（第 4 条坑）。
3. **涉及 `SendMessage` 的用例，等待必须泵消息**（第 2 条坑）。
4. **跨 DLL 共享状态不能用静态变量**，用命名共享内存（第 1 条坑）。
5. **测试期间禁止构建**（`op_test.exe` 占 lib → `LNK1104`）；构建与测试必须串行。
6. **改 `.h` 后确认 obj 真重编了**（`*.obj.d` 为 0 字节 → 依赖扫描失效，
   `_wb_build.py` 有 dep-guard 兜底，绕过脚本构建时要自己查时间戳）。
7. **标准库成组前置**（A 批的坑，新文件照 `OpContext.h` 的顺序抄）。
8. **改 `op.idl` 必须同步手写的 `OpAutomation.h`**，否则 `C2509`。
9. **新增 C API 必须 `dumpbin` 自查裸名**（声明要在 `extern "C" {}` 块内部）。
