## 一、现状盘点（先确认缺口真的存在）

### 1.1 已有的（做得不错，不动）

| 类别 | 接口 | 评价 |
|---|---|---|
| 读写 | `OpReadData/OpWriteData`、`OpReadInt/Int64/Float/Double/String` 全家 | 完整 |
| 搜索 | `OpFindData/OpFindDataEx` | **实现质量高**：分块读（16MB）、跨块防漏检（多读 m-1 字节）、锚点优化、地址回绕保护、按需分配缓冲 |
| 模块 | `OpGetModuleBaseAddr/GetModuleSize/GetModuleInfoList` | 完整 |
| 内存管理 | `OpVirtualProtectEx/OpVirtualAllocEx` | 完整 |
| 图片缓存 | `OpLoadPic/OpFreePic/OpLoadMemPic/OpGetPicSize` | 有 LRU 上限（500）、shared_mutex |

### 1.2 核心缺口（实证）

检索 `include/op_c_api.h` + `include/libop.h` + `libop/com/op.idl`：

```
OpLoadImageFromMem : 0     OpLoadImage    : 0
OpFreeImage        : 0     OpGetImageData : 0
OpCropImage        : 0     FromMem/FromPtr: 0     ImageHandle: 0
```

**图像句柄注册表完全不存在。**

后果：所有识别入口（OCR / 找图 / 找色 / YOLO）要么吃"屏幕区域"，要么吃"文件路径"，
调用方**无法把自己手上已有的图像数据直接喂进来**。

对 Python/易语言用户的现实痛点：从游戏内存/其他采集工具拿到了像素，
必须先落盘成 bmp，再让 op 读盘 —— 多一次磁盘往返（实测 50~200ms 量级）。

## 二、本期范围（有意收窄）

规划 §7.3 分三期，全做是 8~10 天。**本期只做一期地基**，理由是：
- 地基不做，二期所有 `*FromMem` 都没有落脚点
- 地基可以独立验证、独立交付，风险可控

### 2.1 本期做

| 接口 | 说明 |
|---|---|
| `OpLoadImageMem(data, w, h, stride, fmt)` → 句柄字符串 | 从原始像素内存注册图像 |
| `OpLoadImageBmp(data, size)` → 句柄 | 从 BMP 字节流注册（自动解析头） |
| `OpFreeImage(handle)` | 释放单个 |
| `OpFreeAllImages()` | 释放全部 |
| `OpGetImageSize(handle)` → `{"width":W,"height":H,"channels":C}` | 尺寸查询 |
| `OpGetImageData(handle, fmt)` → 原始字节 | 读回像素（fmt: `raw`/`bmp`） |
| `OpCropImage(handle, x, y, w, h)` → 新句柄 | 裁剪（深拷贝） |
| `OpFindStrMem(handle, targets, ...)` | **首个消费者验证**：在图像句柄上跑 FindStrBatch |

### 2.2 本期不做（明确）

- 二期全家桶（`OpOcrFromMem` / `OpFindPicInMem` / `OpGetColorFromMem` / YOLO FromMem 等）
- 三期截屏缓存（`OpSetSnapCacheTime` / `OpLockDisplay`）
- HBITMAP 入口（需要额外跨进程/DC 处理，单独排期）

## 三、设计

### 3.1 句柄形态：字符串 `img:<编号>`

与仓库既有的 `pic:<路径>` 显示输入风格一致。用字符串而非整数，好处：
- 现有接口全是 `const wchar_t*`，无需新类型
- 易语言/COM 层零改动（BSTR 直接传）
- 便于日志排查（一眼看出是图像句柄不是文件）

### 3.2 存储

复用仓库已有的 `Image`（BGRA 32bpp，见 `libop/image/Image.h`），
新增一个进程级注册表：

```cpp
// ImageSearchService.cpp（与 g_pic_cache 并列）
std::map<std::wstring, std::shared_ptr<Image>> g_image_registry;
std::shared_mutex g_image_registry_mutex;
std::atomic<long> g_image_registry_seq{0};
std::atomic<long> g_image_registry_max{256};  // 上限，防泄漏
```

**为什么用 shared_ptr**：`OpGetImageData` 读的同时别的线程可能在 Free，
shared_ptr 快照保证不悬垂（与 `g_pic_cache` 一致的做法）。

**上限策略**：达上限时**拒绝新增并返回空串**（而不是像 pic 缓存那样整体清空）——
图像句柄是调用方显式创建的，静默清空会让调用方手里的句柄突然失效，
是更糟的失败模式。

### 3.3 输入格式

| fmt | 含义 |
|---|---|
| `bgra` / `4` | 32bpp BGRA（默认） |
| `bgr` / `3` | 24bpp BGR |
| `gray` / `1` | 8bpp 灰度（会复制到三通道） |

`stride <= 0` 时按 `width * bpp` 处理（紧凑排列）。
`stride > width*bpp` 视为带行填充，逐行复制。

### 3.4 边界与安全

| 场景 | 行为 |
|---|---|
| `data == nullptr` / `w<=0` / `h<=0` | 返回空串 |
| 像素总量 > 64MB | 返回空串（与 OCR 引擎的限制对齐，防误传巨大尺寸） |
| 句柄不存在 / 已释放 | 返回空串（**不崩溃**） |
| 裁剪区域越界 | 自动 clamp 到图像内；结果为空则返回空串 |
| 注册表满 | 返回空串（不静默淘汰） |

### 3.5 契约：句柄稳定但像素不可变

**设计决策**：注册后图像内容**不可修改**（本期不做 `OpSetImagePixel`）。
理由：句柄可能被多线程并发读；允许就地修改会引入数据竞争。
需要变体就新建句柄（`OpCropImage` 已经是这样）。

## 四、`OpFindStrMem` 的设计（首个消费者）

不新增匹配逻辑，**复用 P1 的 `find_str_batch` 内核**，只是把"取图"换成"从注册表取图"：

```
OpFindStrMem(handle, json_targets, sim)
  → 从注册表取 Image
  → 临时把 ImageSearchService 的 _src 指向这份像素
  → 调 find_str_batch 的匹配部分（跳过截图/颜色二值化）
  → 还原 _src
```

坐标从图像自身左上角算起（无窗口偏移）。

## 六、反向验证计划

1. 把 `OpGetImageData` 的行复制步长写错（用 `width*bpp` 而非 `stride`）→ **M4 必须 FAIL**
2. 把 `OpCropImage` 的源偏移漏掉 `y * stride + x * bpp` → **M5 必须 FAIL**
3. 把注册表上限判据改成"清空重存" → **M7 必须 FAIL**
4. 把 `OpFindStrMem` 的图像来源指向空 → **M8 必须 FAIL**

## 七、给二期的接口预留

一期把内部函数做成：

```cpp
// 能力层通用入口：拿"屏幕区域"或"图像句柄"的像素，供二期所有 *FromMem 复用
long with_image_source(const std::wstring &source_spec, /* 回调 */);
```

`source_spec` 形如 `img:1` 或 `screen:x1,y1,x2,y2`。二期新增 `OpOcrFromMem` 等
只需把 `source_spec` 交给这个入口，不用再碰截图/注册表逻辑。

### 8.4 过程中踩的坑（值得记住）

**1）C API 字符串返回值是复用缓冲区，下一次调用就失效**

`OpLoadImageMem` 返回的 `const wchar_t*` 指向 `handle->string_result`，
**任何后续 C API 调用都会清空并重写它**（`call_string` 的既有设计）。
测试里若这样写就会踩雷：

```cpp
const wchar_t *h = OpLoadImageMem(...);
OpGetImageSize(api.handle, h, ...);   // ← 这一步已经把 h 的内容清空了
OpFindStrMem(api.handle, h, ...);     // ← h 现在指向空串
```

表现出来是 `handle_len=0`，非常像"句柄传递丢了"的实现 bug，实际是测试写法问题。
**正确做法：拿到句柄后立刻复制成 `std::wstring`。**

> 这条不是本轮引入的，是仓库既有契约。已写进测试注释，建议其他新接口的测试也照此办理。

**2）行号编辑脚本两次差点毁文件**

- 第一次：`$lines` 为空导致整个 `ImageSearchService.cpp` 被覆盖成 274 行（`git checkout` 救回）
- 第二次：PowerShell 引号转义把脚本自身解析坏了

**改用 Python 脚本插入**（`scripts/probes/insert_image_registry.py` 与
`insert_image_registry_api.py`），内置三道保护：
读入后校验行数与关键字 → 写入前备份 → 写入后复检，不符自动回滚。
**建议后续所有跨大文件的结构性插入都走这种方式。**

### 8.5 与规划原案的偏差（如实记录）

规划 §7.3 三期全量约 8~10 天。本轮**只做一期地基**，理由：
- 地基不做，二期所有 `*FromMem` 没有落脚点
- 地基可独立验证、独立交付，风险可控
- 用户要求"每个模块做到无可继续优化空间"，但**二期全家桶属于"新增功能"而非"优化"**，
  规模远超单模块优化，且会牵动 OCR/YOLO/找图全部路径

`OpOcrFromMem` / `OpFindPicInMem` / `OpGetColorFromMem` / `OpYoloDetectFromMem`
—— 实现上只需复用本期的 `acquire_image` + 现有屏幕版实现，把"截屏"换成"取句柄"。
