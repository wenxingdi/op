# 函数命名审计与整理（2026-11-26）

任务来源：核验 op 插件全部函数命名，对需要更改的函数名进行整理（可改、可删），
原则：**简洁 + 精确**。HTTP 对接 OCR 的代码全部移除（v6 内置引擎已完善，不需要外置）。

## 一、审计范围与方法

| 层 | 文件 | 数量 | 处置权 |
|---|---|---|---|
| C API 导出（对外契约） | `include/op_c_api.h` | 433 个导出 | **冻结，不改名** |
| C++ 契约层 | `include/libop.h` | ~430 方法（非导出） | 可整理 |
| SWIG 绑定 | `swig/op_wrap.cxx` / `python/pyop/_binding.py` | 生成物 | 跟随契约层重新生成 |
| ctypes 绑定 | `bindings/python/op/api.py` | 432 个公开方法 | **本次整理主战场** |
| C#（OPTool） | `OpSoft.Gen.cs` | 生成物（从 op_c_api.h 生成） | 跟随 C 名 |

**核心结论：C 导出函数名是对外 ABI 契约**——易语言 / Python / Go / C# 脚本直接按名
`GetProcAddress`，任何一个改名都会让所有存量脚本静默失效。因此整理策略是：

1. **C 导出名一律不动**，在头文件注释中标记 canonical / legacy；
2. **规范化落在 python 绑定层**（唯一手写、可安全演进的一层）：
   归一入口定为正名，冗余旧名保留转发但加 `DeprecationWarning`；
3. C++ 契约层内部类名可安全改名（非导出），随本次 HTTP OCR 移除一并改。

## 二、发现的问题与处置

### 2.1 OCR 双前缀混乱（最主要问题，已整理）

同一族免字库 OCR 存在两代命名：

```
旧层 OpOcr*   : OpOcrAuto / OpOcrAutoColor / OpOcrAutoColorLine / OpOcrAutoColorEx
                / OpOcrAutoColorEx2 / OpOcrAutoColorFromFile / OpOcrAutoFromFile
                / OpOcrFromFile / OpOcrAutoColorFromMemEx2 / OpOcrEx2 ...
归一层 OpAutoOcr*: OpAutoOcr / OpAutoOcrLine / OpAutoOcrEx / OpAutoOcrFromFile
```

根因：`OpAutoOcr*` 是后加的"空颜色→原图直识、非空→按颜色二值化"归一门面，
但旧 `OpOcr*` 入口全部保留，导致一个语义四个入口、新用户无法判断该用哪个。

**处置（python 层，C 名不动）：**

| 处置 | python 名 | 说明 |
|---|---|---|
| ✅ 正名（推荐入口） | `autoocr` / `auto_ocr_from_file` | 对应 OpAutoOcr / OpAutoOcrFromFile，color 可空 |
| ✅ 正名（显式族保留） | `ocr_auto_color` / `ocr_auto_color_line` / `ocr_auto_color_ex` / `ocr_auto_color_ex2` | 显式颜色二值化家族，语义各自独立，保留 |
| ✅ 正名（字库族保留） | `ocr` / `ocr_ex` / `ocr_from_file` | 字库点阵家族，与免字库语义不同，保留 |
| ⚠️ 废弃别名（本次加 DeprecationWarning） | `autoocr_line` → `ocr_auto_color_line` | 2026-10-15 已标文档废弃，本次补运行时告警 |
| ⚠️ 废弃别名 | `autoocr_ex` → `ocr_auto_color_ex` | 同上 |
| ⚠️ 废弃别名 | `ocr_auto` → `autoocr(color="")` | 与归一入口空色分支完全等价 |
| ⚠️ 废弃别名 | `ocr_auto_from_file` → `auto_ocr_from_file(color_format="")` | 同上 |
| ⚠️ 废弃别名 | `ocr_auto_color_from_file` → `auto_ocr_from_file(color_format=非空)` | 同上 |

废弃别名**保留转发、不删方法**——`scripts/check_swig_sync.py` 要求契约层每个方法
在 ctypes 层有包装，删包装会造成漂移拦截失败；告警只对 `__main__` 脚本可见，
GMAJ 等库调用方日志不受影响。

### 2.2 拼音命名 OpGaiLu（已整理）

全 API 唯一拼音导出名（"概率"）。C 名 `OpGaiLu` 冻结；
python 层新增正名 `prob(p)`（以 1/p 概率返回 True），`gai_lu` 转为废弃别名带告警。

### 2.3 非导出内部类改名（随 HTTP OCR 移除一并完成）

- `HttpOcrEngine` 类：**删除**（HTTP OCR 后端整体移除，见 §三）
- `HttpOcrService` → `OcrService`（OCR 引擎管理器，内部类非导出，安全改名）

### 2.4 记录但不改（向后兼容优先）

| 项 | 说明 | 不改的原因 |
|---|---|---|
| `OpGetDPI` vs `OpGetFPS`/`OpGetID` 大小写风格不一 | 历史导出 | 改名破坏 ABI，风格问题不值得 |
| `OpFindPicExS` / `OpFindColorBlockExS` / `OpFindLineExS` 的 `ExS` 后缀 | S=聚类/去噪增强版，注释已说明 | 同上；命名虽欠精确但文档可补 |
| `OpHex2RGB` 等数字连写 | 已登记 `_PY_SNAKE_SPECIAL`，文档化 | 改 python 名要动 200+ 调用点，收益为负 |
| `OpWinExec` / `OpBeep` / `OpDownCpu` | 大漠兼容风格的直白名 | 语义其实清楚，保留 |
| `OpRequestCaptureForTest` 测试导出进了公共头 | 测试专用 | 已注释标明；从公共头移走要动导出表，收益低 |

## 三、HTTP 对接 OCR 移除（任务 2）

背景：`OP_ENABLE_HTTP_OCR_BACKEND` 宏**从未在任何构建中定义过**——HTTP OCR 后端
从合入起就是死代码，运行时 init 传 `http/tesseract/paddle` 也只会被拒绝。
内置 ONNX v6 引擎已是唯一且完善的路径，外置 HTTP 对接没有意义。

**已删除：**

- `libop/ocr/OcrService.h`：`HttpOcrEngine` 类声明整块删除；管理器改名 `OcrService`。
- `libop/ocr/OcrService.cpp`：条件 include、`HttpOcrEngine` 全部实现（约 142 行）、
  endpoint 解析块、`init_unlocked` 的 #ifdef 分支。拒绝日志改为
  `remote OCR backend removed (built-in ONNX v6 only)`。
- 引用方同步改名：`libop/image/ImageSearchService.cpp`（4 处）、`libop/op/OpOcr.cpp`（2 处）。
- `libop/CMakeLists.txt` 注释块更新为"已移除"说明。

**核对无残留**：全库 grep `OP_ENABLE_HTTP_OCR_BACKEND` / `HttpOcrService` /
`HttpOcrEngine` 零命中；COM 层（op.idl）只保留通用 HTTP 小族（HttpGet/HttpPost/
HttpDownloadFile，对接大模型 API 用，与 OCR 无关，**保留**）。

### 新发现并补文档的 3 处名实/语义问题（均已修，仅文档，无行为变更）

1. **`extract_word_rects` 的 `min_word_h` 参数实为"最小字宽"**（`get_rois` 比对的是
   `width()`，C 头早有 ⚠ 但 python 无文档）→ python docstring 补 ⚠，指引
   `extract_word_rects_ex` 做宽高双过滤。
2. **`capture_pre`**：历史名，"Pre" 无实际语义 = 不传区域参数的**全屏截图** → C 头 + python 补文档。
3. **`sleep` vs `delay` 语义双关且无文档**：`sleep`=硬阻塞不处理消息队列；
   `delay`=消息泵等待（UI/热键不卡）→ C 头 + python 补语义对照，指引脚本延时用 delay。

记录不改：`GetWordsNoDict`/`FetchWords*` 字库辅助族为 legacy 大漠风格命名但内部自洽；
`GetScreenData` 裸指针返回有风险但 C 注释已标注、python 有安全封装。
