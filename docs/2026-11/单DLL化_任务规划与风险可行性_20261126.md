# 单 DLL 化：任务规划、风险与可行性分析（2026-11-26）

> 目标：把 ONNX Runtime 吸收进 op DLL，做到像 ola 插件那样的**单文件交付**。
> 约束：op-master 项目不受任何影响；所有输出、cmake、依赖构建放后期新建的独立文件夹。
> 本文档只做规划与记录，不改动任何构建行为。

---

## 0. 现状账（2026-11-26 实测）

### 0.1 当前交付物（`op/build/nmake-x64-Release/libop/` 与 `ninja-x86-Release/libop/` 实测）

| 文件 | x64 | x86 | 说明 |
|---|---|---|---|
| `op_x64.dll` / `op_x86.dll` | 53,248,512 B | 49,108,992 B | 主体（OCR 模型已内嵌资源段，OpenCV 静态，CRT 静态） |
| `op_c_api_x64.dll` / `op_c_api_x86.dll` | 53,219,328 B | 49,147,392 B | C API 门面，同上 |
| `onnxruntime.dll` | 11,234,848 B | 9,989,664 B | **sidecar #1**（delay-load） |
| `onnxruntime_providers_shared.dll` | 22,048 B | 20,408 B | **sidecar #2**（ORT 运行时自行加载，不在导入表） |

即当前一个架构的完整交付 = **3 个文件**：x64 ≈ 64.5MB、x86 ≈ 59.2MB。除此之外没有其他 sidecar（OpenCV 已静态、minhook 经 vcpkg 静态链接、BlackBone/静态 CRT 已在库内）。

### 0.2 关键代码事实（勘察结论，后续阶段的依据）

1. **`libop/CMakeLists.txt` L633–697 已有完整的静态链接分支**：只要 `${ONNXRUNTIME_DIR}/lib/onnxruntime_static.lib` 存在，即自动走静态链接（"0 新增 DLL"），配套系统库清单（advapi32/userenv/ole32/shell32/user32/gdi32/crypt32/rpcrt4/ncrypt/ws2_32/mmdevapi）都已写好。**op 侧代码改动预计为零**，任务重心不在 op 而在"造出这个静态库"。
2. **delay-load 的历史动机**（L664–678 注释）：op DLL 会被注入目标进程（DX 输入通道 hook），静态导入 onnxruntime.dll 会使目标进程能否解析它成为注入成功的前置条件——BlueStacks 5 实测 0xC0000135 翻车。**静态链接天然解决此问题**（导入表彻底没有 ORT），比 delay-load 更优。
3. **全链 /MT 静态 CRT**（`op/CMakeLists.txt` L190–197 + 3rd_party 约定）：ORT 静态库也必须按静态运行库构建，否则链接报 LNK2038 运行库冲突。
4. 模型走 `ocr_models.rc` 模板生成 + 资源段注入，换模型后需删 `.dir/ocr_models.rc.res`（既有老坑，见 FP16 规划）。
5. op 是 git 仓库，工作区干净，基线 commit `25b9bcc`——支持 worktree 隔离方案。

## 1. 方案选型

| 方案 | 内容 | 单 DLL | 注入安全 | 难度 | 结论 |
|---|---|---|---|---|---|
| **A（推荐）** | ORT 1.19.2 源码静态构建出 `onnxruntime_static.lib`（x64+x86，/MT），放入预期路径，走 CMake 现成分支 | 真·单文件 | **优于现状**（导入表无 ORT） | 中（难点全在 ORT 构建） | **采用** |
| B | onnxruntime.dll 编入资源段 + 运行时释放到磁盘再加载 | 单交付文件，但运行时落盘 | 差：注入目标进程上下文里释放/加载路径不可靠 | 中 | 否决（注入场景几乎不可行 + AV 误报风险） |
| C | 维持现状（3 文件，delay-load） | 否 | 现状已安全 | 零 | 兜底/默认 |

方案 A 与 FP16 模型压缩（32.2→16.2MB）**正交可叠加**，互不阻塞。

**体积预估**（ORT 代码段并入约 +10~12MB，与模型 FP16 无关）：

| 架构 | 现状 3 文件总和 | 单 DLL（FP32 模型） | 单 DLL（FP16 模型） |
|---|---|---|---|
| x64 | ≈64.5MB | ≈64~66MB | ≈48~50MB |
| x86 | ≈59.2MB | ≈59~61MB | ≈43~45MB |

文件数 3→1，总字节数基本持平；FP16 落地后单文件比现状**总和还小**。

## 3. 可行性结论

**可行，且比直觉容易。** 依据：

1. op 侧改动≈零——CMake 静态分支、系统库清单、资源注入全部现成（L644–655）；
2. 全链 /MT 一致，无 CRT 冲突源；
3. ORT 从源码产出静态库有广泛社区先例，1.19.2 无已知阻断性问题；
4. 最大不确定点（R1）可用半天 spike 闭环，失败代价为零（停在现状）。

**难度评级：总体中等。** 工作量集中在"ORT 静态构建脚本化 + 双架构验证"，是一次性工程，做完即固化。

## 4. op-master 隔离硬规则（本线全程生效）

1. **op-master 工作区只读**。唯一允许写入的位置：`op/docs/`（文档白名单）。任何构建、转换、输出不得落盘到 op-master。
2. **git worktree 隔离**：新文件夹（建议 `D:\AutoPro\op-onedll\`）内以 `git worktree add` 挂出 op 源码（基线 `25b9bcc`），不用整份复制，节省空间且 lineage 清晰；worktree 里改动走独立分支，**默认不合回 op-master**，除非显式要求。
3. **不运行 `D:\AutoPro\OPTool\sync_op_dll.py`**，不触发任何发布件同步；op-onedll 有自己的 out/ 与校验清单。
4. **阶段前后 git status 快照对比**，结果写进对应阶段验证报告；出现白名单外变更立即停工排查。
5. FP16 模型转换（P1）的转换脚本、FP16 模型、A/B 报告同样全部落在 op-onedll，**op-master 的 `build/_deps/ocr_models/` 原模型不动**。

## 5. 任务规划（阶段 / 产出 / 验收）

> 顺序说明：P1（FP16）与 P2（ORT spike）互相独立；建议 P1 先行（半小时级、立即见效、零结构风险），P2 随后。

### P0 基线固化（今日，随本文档完成）
- 记录基线 commit `25b9bcc`、当前 4 个 DLL + 2 个 sidecar 的大小与 sha1；
- 产出：本文档 + INDEX 登记。✅

### P1 FP16 模型转换（先行，预计 ≤0.5 天）
- 内容：`onnxconverter_common.float16.convert_float_to_float16(keep_io_types=True)` 转 det/rec/cls 三模型；`ocr_ab_bench.py` 跑 Dict_test + line_test 双基线对比；
- 产出：FP16 模型 + A/B 报告（字错率 diff、耗时 diff、优化图 Cast 折叠确认）；
- 验收：字错率 diff <0.5%（落在 0.2%~0.5% 区间则扩样本复测）、耗时无回退；不通过则按模型粒度回退；
- 全部产物在 op-onedll。

### P1.5 v4 降级评估（2026-11-26 模型级预审，已出结论）

问题：单 DLL 是否用回 PP-OCRv4 mobile（FP16 后更小）？**结论：否决，单 DLL 模型内容拍板 v6 small + FP16 存储。**

- 模型级 4 变体对比（v6/v4 × FP32/FP16，同一 Python 流水线）：v6-FP16 与 v6-FP32 输出 7/8 图完全一致——**FP16 对 v6 无损**，P1 预审通过；
- v4-FP32 字准低 6~20 个百分点（合成行测试）/ 大图编辑距离 64~82 字符（Dict 3/4/7/8），与 11-20 引擎级 A/B 互相印证，代际差决定性；
- v4 det 是 opset 12 老导出，FP16 转换后概率图噪声底翻倍、det 框爆炸（1~21 → 36~498），工具坑不值得排雷；
- 单行/多行 det 行为两代一致（B/C/D/F 均正确分 2 框）——该痛点与模型代际无关，方向仍是引擎后处理参数；
- 踩坑留档：Paddle 导出模型 CTC blank=索引 0（非末位）；多语言字典按 `\n` 切分不能用 splitlines；v6 det 输入须 32 倍数。
- 详细报告：`workbench/v4_eval/v4_fp16_评估报告.md`（含完整数据表）。

### P2 ORT 静态构建 spike（x64 only，预计 0.5~1 天）
- 内容：拉 ORT 1.19.2 源码（与现用预编译包**严格同版本**，避免行为漂移）；CPU-only、静态运行时、Release，脚本化构建；
- 验证点：产物名与组织（R1）、/MT 一致（R2）、在 worktree 临时副本走通 CMake 静态分支编出单 DLL、OCR 冒烟、导出优化图确认行为一致；
- 产出：spike 记录（构建脚本 + 产物 sha1 + 踩坑）；
- 验收/止损：编不出或冒烟不过→停在方案 C，损失仅半天。

### P3 双链重编 + 全量回归（预计 1 天）
- 内容：x64/x86 静态链接双链重编（注意 R5 资源缓存坑）；全量回归（**TEMP 指到工作区**后跑 `run_tests.ps1`，TimeoutSec ≥2400，遵守"测试期间不构建"约定）；BlueStacks 注入绑定真机复测（R4）；OCR A/B 基准无回退；记录加载耗时（R7）；
- 产出：双架构单 DLL + 回归记录 + 注入复测记录；
- 验收：回归基线不低于 op-master 当前基线（注册 690，除已知恒定 FAILED 与偶发项）；DX 三通道绑定通过。

### P4 交付固化（0.5 天）
- 产出：out/ 交付件 + sha1 清单 + 最终报告（INDEX 登记）；
- 决策点：**默认不改动 OPTool 现有分发形态**（sync 脚本与三处 Dll 不动），单 DLL 作为独立交付线存在；是否切换分发形态由用户单独拍板。

### 执行期新增踩坑（2026-11-26 晚，已解决）

1. MSVC 14.44 编译 ORT 1.19.2 需给 `include/onnxruntime/core/platform/ort_mutex.h` 补 `#include <chrono>`；
2. ORT 默认 /MD，op 全家 /MT → 必须用 build.py `--enable_msvc_static_runtime` 全量重编（否则 30 个 `__imp_*` 链接错）；
3. `--skip_tests` 时 re2 不编（无消费者）→ 在 `_deps/re2-build` 单独 `--target re2` 后重新合并；
4. 代理按路径拦 `microsoft/onnx*` 且 git 协议被 reset → gitcode.com 镜像；cmake 内建下载经代理不稳 → curl 预置 zip（SHA1 校验）到 `<dep>-populate-prefix/src/`；
5. x64 非 wheel 构建在**新 CMake 缓存**上必须显式 `-DOPENCV_ROOT/-DOPENCV_LIB_SUFFIX=500`（op-master 靠缓存残留值，worktree 会踩空）。
