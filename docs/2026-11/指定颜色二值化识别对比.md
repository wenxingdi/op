> 测试日期：2026-11-20
> 颜色参数：`e01111-000000|33ee33-000000`
> 素材：`D:\GMPLUG\DmTools\Dict\` 下 8 张小图（文件名即真值）

## 一、最重要的发现：颜色格式是 **RGB 顺序**，不是 BGR

这是本次测试最关键的一条。

你给的 `1111e0-000000|33ee33-000000` **直接传进去全部返回 0 行**。排查后确认颜色必须按 **RGB 顺序**写：

| 传入值 | 实际含义 | 结果 |
|---|---|---|
| `1111e0-000000` | 按 RGB 解 → R=0x11,G=0x11,B=0xE0（蓝紫） | **0 行**（失败） |
| `e01111-000000` | 按 RGB 解 → R=0xE0,G=0x11,B=0x11（红色） | **完全正确** ✅ |
| `33ee33-000000` | 对称色（RGB/BGR 同值）→ 绿色 | 有效 |

### 代码依据（已核实，非推测）

`libop/image/Color.h` 的 `try_str2color`：

```cpp
unsigned int rv = 0, gv = 0, bv = 0;
if (!hex6 || swscanf(t.c_str(), L"%02X%02X%02X", &rv, &gv, &bv) != 3) { ... }
b = static_cast<uchar>(bv);
g = static_cast<uchar>(gv);
r = static_cast<uchar>(rv);
```

**前两位解析进 `rv`（红），中两位 `gv`（绿），后两位 `bv`（蓝）** → 对外就是 RGB 顺序。

> ⚠ **与旧文档记载冲突**：CLAUDE.md 写"对外 RGB hex `RRGGBB`"（本文实测吻合），
> 但交接记录的 B10 注释写"BGR hex（RGB 黄 #ffff00 应写 00ffff）"——**该说法有误**，
> 与代码实现和本次实测都不符。建议后续修正交接记录，避免继续误导调用方。

**正确写法**：

```
e01111-000000|33ee33-000000
```

## 一.5 智能选路已内置（2026-11-20 实现）

原设计需要调用方自己判断"该不该传色"。现已把判断做进引擎，**调用方不用改**：

```
OpOcrAutoColorEx2(..., color, ...)
  → 扫描图里命中目标色（逐通道容差）的像素数
    ├─ 占比 >= 1/1000  → 走颜色二值化（有该色，抠字有效）
    └─ 占比 <  1/1000  → 自动回退原图直识（图里没这个色，二值化会全空）
```

实现：`ImageSearchService::count_color_hits()`，复用 `str2colordfs` 解析颜色（与既有颜色路径同口径）。
特殊写法（如 `@000000` 反白格式）无法逐色比对时返回 -1，保守沿用颜色路径。

**实测效果（8 张小图 × 2 档位）**：

| 档位 | 原图路径 | 颜色路径（选路前） | **智能选路后** |
|---|---|---|---|
| v6 完全正确 | 3/8 | 5/8 | **8/8** |
| v4 完全正确 | 3/8 | 0/8 | **3/8** |

v6 达到 **8/8 全对**——原本失效的三张白字图自动回退到原图路径。

## 四、根因分析：颜色路径为什么能救回坐标类图

统计 8 张图的颜色分布：

| 图片 | 红色像素 | 绿色像素 | 说明 |
|---|---|---|---|
| 月龙村 | 0 | 288 | 绿字 |
| 断臂崖 | 357 | 0 | 红字 |
| 邪神殿 | 334 | 0 | 红字 |
| 割喉台 | 336 | 0 | 红字 |
| 青螺山死门 | 393 | 0 | 红字 |
| 青螺山割喉者 / 幻魔者 / 魔化雪怪 | 0 | 0 | **白字，无目标色** |

**规律非常清晰**：

- **坐标类文本（`[-1219,-1864]`）用的是红色字**（RGB(224,17,17)）
- **纯汉字名（`青螺山割喉者`）用的是白色字**
- 颜色二值化把红色字单独抠出来 → 去掉背景噪声和描边干扰 → 小字变得清晰 → 识别率从 23% 跳到 100%

这也解释了为什么原图路径在小图上表现差：**红色字 + 复杂背景 + 12~14px 小字**，
抗锯齿和描边让 det 框和 rec 都难处理；纯白字反而容易。

## 五、智能选路方案（已实测验证）

既然两种路径各有适用场景，按图选路能达到最优：

```
探测图中是否存在目标色像素（红 RGB(224,17,17) 或 绿 RGB(51,238,51)）
  ├─ 有（≥30 像素）→ 走颜色路径
  └─ 无            → 走原图路径
```

## 六、v4 档的颜色路径问题

v4 在颜色路径下**没有一张完全正确**（0/8），且错误模式高度一致：

```
真值:  断臂崖[-1219,-1864]
v4:    断臂崖［-1219,-1864]      ← 左方括号 [ 变成全角 ［
```

8 张里 6 张都是这个「`[` → `［`」的全角/半角错误。这是 v4 字典（6623 字）里全角括号优先级更高导致的。

**建议：颜色路径只用 v6，不用 v4。**

## 七、可执行结论

### 立刻可用的写法

```
颜色参数: e01111-000000|33ee33-000000
```

（如果你原来的 `1111e0-000000` 确实是想表达"红色"，那是颜色顺序写反了）

### 使用策略

| 场景 | 推荐做法 |
|---|---|
| 知道文字是特定颜色（如游戏里的红字坐标） | **传色**，准确率 100% |
| 文字是白色/浅色 | **不传色**，传色会返回空 |
| 不确定颜色 | 先探测，或**两条路都跑取高 conf** |
| 坐标类文本 | 优先传色（能修掉逗号丢失问题） |

### 关键收益：颜色路径修掉了「逗号丢失」

上一轮发现的系统性问题——`[-1219,-1864]` 丢逗号变成 `[-1219-1864]`——
**在颜色路径下全部修复**。这是本项目坐标识别最重要的改进。
