## 三、修掉的 6 个真缺陷

### 3.1 `check_swig_sync.py` 把 typedef 当成方法名，导致 78 条假缺口

**现象**：`scripts/run_tests.ps1` 的前置门禁直接退出 4，**测试根本跑不起来**：

```
[DRIFT] libop.h 有、pyop.py 无 (79): ARGB2Hex AesDecrypt ... YoloUseModel void
结论： 存在漂移，需重新生成
```

**根因**：`libop_methods()` 的正则 `^\s+(?:std::)?[\w:<>, \s\*&]+?\b(\w+)\s*\(` 会把

```cpp
    typedef void (*InputMonitorCallback)(const op_input_event_view *event, void *user);
```

里的 **`void`** 当成方法名。这个假的 `void` 永远不在 pyop.py 里，于是恒列一条缺口。

**危害**：假缺口和真缺口混在同一张清单里。实际真因只是**批 56~61 新增的 78 个 API 没重新生成 SWIG 包装**，
但报告读起来像"整个绑定层崩了"，会把排查方向引到完全错误的地方。

**修法**（`scripts/check_swig_sync.py`）：
- 提取阶段跳过 `typedef` / `using` 开头的行，并排除 C++ 关键字；
- 不把 `void` 塞进噪声表 —— 那样将来真出现畸形声明 `void void(` 也会被静默放过。

修完后报告变成精确的 **78 条真缺口**，重新生成即清零。

### 3.2 SWIG 包装与 libop.h 落后 78 个方法（据此重新生成）

用本机 SWIG 4.4.1 重新生成，`pyop.py` 368 → 446 个 def，`_wrap_` 362 → 440：

```bash
cd swig && swig -c++ -python -o op_wrap.cxx op.i
copy /Y pyop.py ..\python\pyop\_binding.py
```

修复后 `check_swig_sync.py` 退出码 0。**Python 用户此前无法调用** Draw 全家桶 / UIA / Asm /
热键 / 注册表 / 加密 / 时间轴等 78 个接口。

### 3.3 ctypes 绑定整段漏绑 7 个接口（输入时间轴 + 并发自省）

`op_c_api.h` 与 DLL 导出里都在（`dumpbin` 可见），但 `bindings/python/op` 的 `_ffi.py`
没有签名、`api.py` 没有包装 —— **Python 侧完全调不到**：

| 接口 | 用途 |
|---|---|
| `OpConcurrencyInfo` | 同实例并发自省（peak / reentrant） |
| `OpInputSyncEnable` / `OpInputSyncLink` / `OpInputSyncStatus` | 输入采集开关 + 主从同步 |
| `OpInputRecord` / `OpInputRecordGetPath` / `OpInputPlayback` | 录制 / 回放 |

**修法**：`_ffi.py` 补 7 条签名；`api.py` 补 7 个方法 + `_InputEventView` 结构与
`_INPUT_MONITOR_CALLBACK` 回调类型（布局与 `op_c_api.h` 的 `op_input_event_view` 逐字段一致，
并在注释里标注"改这里必须同步头文件与 libop.h"）。

**端到端实测**（非只跑 import）：

```
concurrency_info      -> {"id":0,"in_flight":1,"peak":1,"reentrant":0,...}
input_sync_status     -> {"ok":1,"enabled":0,"master":0,"slave":-1,...}
record start          -> ('workbench/tmp/_rec_smoke.jsonl', 1)
record stop           -> ('workbench/tmp/_rec_smoke.jsonl', 0)
playback LOAD         -> ('{"ok":1,"events":0,"bound":0,"path":"..."}', 0)
playback FREE         -> ('{"ok":1,"freed":0}', 1)
```

### 3.4 颜色换算族的命名口径自相矛盾（两个脚本各说各话）

`gen_api_reference.py` 与 `check_swig_sync.py` 各自维护一份 `_PY_SNAKE_SPECIAL`，
但都没登记颜色换算族。于是 `ARGB2Hex` 按通用规则算出 `argb2_hex`，
而 `api.py` 里实际是 `argb2hex` —— 两份都"发现缺口"，但改 `api.py` 等于改 200 多处调用点。

**修法**：把既有拼写登记进两张表的同一组条目（`hex2rgb` / `hex2argb` / `argb2hex` /
`rgb2hsv` / `hex2hsv`），并在两处注释里写明"必须同步"。

### 3.5 `run_tests.ps1` 硬编码 180 秒超时，全量必然被腰斩

**现象**：全量跑到 `ConcurrencyBatchTest.SameInstanceReentryIsObservable` 时进程消失，
**没有 gtest 汇总行**。第一反应是"这条用例挂死"，实测单独跑只要 **8ms** 且 PASS。

**根因**：`$p.WaitForExit(180000)` —— 全量实际要 **10~12 分钟**（676 条，含 hook/dx 载体的等待），
180s 必然在跑到一半时 `Kill()`。表现是"最后一条用例没有结果 + 汇总缺失"，
**极容易被误诊为用例挂起**。

**修法**：加 `-TimeoutSec`（默认 1800），超时报错文案里点明"全量请留足"。

### 3.6 测试隔离：一次熔断污染同进程的整组用例

这是本轮**最有价值**的一处，因为原来的红灯读数完全误导。

**WGC 组**：本机（Win10 18363）第 1 条用例跑过后，第 2 条起 `WgcCapture::Init` 抛
`0xC0000005`，`win10InitSehGuard` 兜住不崩进程但**置进程级熔断**，后续 WGC 请求快速失败。
实测**每条单独首跑都是 PASS**（10/10），合起来却是 6 FAIL —— 纯隔离问题。

**DX 组**：`MouseKeyTest` 里 16 条 dx 用例本来就写好了 `if (ret != 1) GTEST_SKIP()`
的统一判据，但 `BindWindowDxSuffixDoesNotPolluteSessionAttr` 用了 `ASSERT_EQ(ret, 1)`，
**独独它没有**；`WindowStateTest.DxBindToSameIntegrityWindowStillSucceeds` 也是硬断言。

**修法**：

- `tests/wgc_test.cpp`：基类加 `BindWgc()` 统一入口。绑定成功记 `g_wgc_ever_bound`；
  失败且此前成功过 → 置熔断标记 → 后续用例 `SetUp` 显式 `GTEST_SKIP` 并写明原因。
  **关键保护**：首条就绑不上时 `g_wgc_ever_bound` 仍为 false，**不会**误判熔断，
  用例照常判红 —— 保证"环境真不支持"不会被静默成 SKIP。
- `tests/mouse_keyboard_test.cpp`：与该文件其余 16 条 dx 用例对齐，绑不上就跳过。
- `tests/window_state_test.cpp`：先探一次纯 dx 绑定，不可用则跳过并注明
  "integrity precheck not implicated"，**避免把环境故障记到完整性预检头上**。
- `tests/hook_capture_test.cpp`：绑不上时按模块表区分
  "注入被拦（两侧都没加载）" vs "按需加载只完成一侧（真缺陷）"，
  后者用 `ADD_FAILURE` 带出 `d3d9= / dinput8= / bind_ret=` 三个值。

**反向验证（重要）**：把探测临时改成"永远成功"（`probe = 1`），
该用例立刻 **FAILED** 而不是 SKIP —— 证明守卫**没有让断言失去判别力**，随后已恢复。

### 3.7 `run_tests.ps1` 是 UTF-8 无 BOM，PowerShell 5.1 按 GBK 解析

**踩到的过程**：给 §3.5 加完超时参数后，脚本突然报

```
Missing closing ')' in expression.
At run_tests.ps1:84 ... if (-not $p.WaitForExit($TimeoutSec * 1000)) {
```

但**文件内容明明是完好的**（逐行打印、`git diff` 都正常）。根因是：

- 文件是 **UTF-8 无 BOM**，而 `powershell.exe`（5.1）对无 BOM 文件按**系统 ANSI 代码页（本机 GBK）**解读；
- 中文字符的多字节序列会吃掉引号配对 —— 只要**行数/位置**改变，原本"侥幸能解析"的文件就崩；
- 所以这是个**潜伏缺陷**：任何人改这个脚本都可能触发，与改动本身无关。

**修法**：给文件补 UTF-8 BOM。PowerShell 5.1 见到 BOM 即按 UTF-8 解析；
`pwsh` 7 本来就默认 UTF-8，加了 BOM 也兼容。

> 同类风险：`scripts/` 下任何含中文的 `.ps1` / `.bat` 都建议统一加 BOM。
> 本轮只修了 `run_tests.ps1`（唯一被改动的那个），其余未动以免扩大改动面。

## 四、代码与注释审计：为什么删得很少

### 4.1 结论：注释密度高，但九成是"判据"，不是"废话"

全仓 `libop/` 181 个文件、**208 万字节**源码。抽查注释后判断：这些不是冗余描述，
而是**踩坑后固化的判据**。典型样本：

```cpp
// 必须在窗口自身的 DPI 上下文里量：截帧（窗口 DC 位图）就是这个口径。
// 目标进程 DPI 不感知时，DPI-aware 宿主量到的是物理像素（150% 下大 1.5 倍），
// 与帧尺寸不符 → 区域越界判定失效、越界部分静默读垃圾。
```

删掉这类注释 → 下一个人会把 `dpi_context_scope` 当"无用装饰"再删一次，缺陷复现。
**所以本轮不做注释瘦身。** 真正做的是**排除**（列证据，不是凭感觉）：

| 检查项 | 结果 |
|---|---|
| `TODO` / `FIXME` / `HACK` 遗留 | `libop/` 下 **0 条** |
| 文档内部链接 | 全 `docs/**/*.md` 扫描：**0 条断链** |
| `op_c_api.h` 声明 vs DLL 实际导出 | **433 声明 = 433 导出，双向差集为空** |
| 头文件里前一轮遗留的死代码 | 无（`HttpClient`/`HttpYoloEngine` 是宏保护的**有意保留**，非死代码，见 §七.3） |

### 4.2 唯一清理掉的"代码类"东西：手工源码副本

`op/backup_capture_f/`（10 个文件）与 `op/backup_yolo_f/`（2 个文件）是手改前的手工副本，
不在构建里、不在 `.gitignore` 的显式白名单。**删前逐个校验**：

```
for f in <12 files>: git hash-object f → git log --all --find-object=<blob>
结果：12/12 全部存在于 git 历史
```

确认零信息损失后才删。同类处理：

| 位置 | 判定 | 处置 |
|---|---|---|
| `backup_capture_f/` `backup_yolo_f/` | 12 个 blob 全在 git 历史 | **删除** |
| 根 `_backup_L0_20260804/`（12 个） | 全在 git 历史 | 合并进 `workbench/_legacy_hand_backups_20260827/` |
| 根 `_backup_docs_20260827/`（3 个） | **不在** git 历史 | **保留**（合并进同上目录） |

## 七、诚实的边界：本轮没做到的

### 7.1 WGC 全组在同进程内仍然只有前 1~2 条能真跑

熔断是 `WgcCapture` 的**有意设计**（Windows 10 WGC 背靠背建会话会派发访问违例，
SEH 兜住以免进程崩溃）。本轮做的是**把它的后果如实标注**（显式 SKIP + 原因），
没有、也不建议在测试侧绕过它。

要真正逐条验证 WGC，请**每条单独起进程**：

```powershell
.\build\nmake-x64-Release\tests\op_test.exe --gtest_filter="WgcTest.NormalAutoUsesWgcForKnownBrowserClasses"
```

本轮已实测 **10/10 单进程全部 PASS**。

> **注意全量总数会随熔断时机抖动**：熔断发生在第 N 条用例之后，则前 N 条真跑、其余 SKIP。
> 实测两轮分别是 `649 PASS / 26 SKIP`（2 条 WGC 真跑）与 `647 PASS / 28 SKIP`（4 条真跑），
> **总数恒为 676、FAILED 恒为 1**。这不是 flaky 缺陷，是熔断时机的正常差异；
> 判断回归时请盯 **FAILED 数**，不要盯 PASS/SKIP 的分配。

### 7.2 `HookCaptureTest.BindLoadsMissingGraphicsAndInputModulesOnDemand` 仍是 FAILED

这**不是本轮引入的**（`CHANGELOG` 第四十一批起就记为 `baseline FAIL`）。本轮把它的诊断信息加强了：

```
按需加载只完成了一侧：d3d9=true dinput8=true bind_ret=0
```

**这句话很关键**：两个模块**都加载成功了**，说明"按需加载"功能本身没坏，
失败发生在后续的**钩子活性回环**（`BindingSession.cpp` 的 `PingHook`，原因码 `0x2009`）。
同一台机器上真实 D3D9/D3D11 载体的 `dx.d3d9` / `dx.d3d11` 绑定**都 PASS**，
所以这是**素载体（无渲染循环）特有的回环问题**，不是注入通路坏了。
