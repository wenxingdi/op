## 二、新增对外接口（验收时可直接调用）

### P1：FindStr 增强

| 层 | 符号 | DISPID |
|---|---|---|
| C API | `OpFindStrBatch(handle, x1,y1,x2,y2, json_targets, color, sim)` | — |
| C API | `OpFindStrEx2(handle, x1,y1,x2,y2, pattern, color, sim, flags)` | — |
| C++ | `op::Op::FindStrBatch` / `op::Op::FindStrEx2` | — |
| COM | `FindStrBatch` / `FindStrEx2` | **442 / 443** |

**解决了旧接口的什么**：

| 旧接口行为 | 新接口 |
|---|---|
| `FindStr("909")` 在 `1909`/`9090` 上误命中 | `match=exact` 只认整行相等 |
| 只返回整行左上角 | 返回 `cx1/cx2` **字符级**水平范围 |
| 只有子串包含 | + `exact` / `prefix` / `suffix` / `regex` |
| 形近字直接失败 | + `fuzzy`（编辑距离 ≤1/2/3） |
| 只能告诉你"哪几个串命中" | 返回**每个目标的全部命中**，可独立配置 |

**实测效果**（COM 后期绑定，`scripts/probes/verify_com_call.py`）：

```
图片 "击倒机关兽909米"，找 "909"
→ found=1, hits=1
→ 行框 x=0..388，而 cx1=247, cx2=344   ← 精确落在 909 上，不是整行
→ begin=5, end=8, line_text="击倒机关兽909米"   ← 下标与文本完全对应
→ exact 模式下（909 只是子串）found=False        ← 子串误命中已消除
```

## 四、两个额外发现（都写进了文档和 CLAUDE.md）

### 4.1 构建缺陷：改头文件不触发重新编译 ⚠ 影响所有人

**根因已完全定位**：`cl /showIncludes` 输出 **UTF-8**，而 CMake 写进 `build.make` 的
`--filter-prefix` 是 **GBK**（`注意:  包含文件:  `）。字节不匹配 → 依赖扫描一行都过滤不到
→ `*.obj.d` 恒为 0 字节 → 头文件不在依赖图里。

实测：233 个 `.obj.d` 里 **86 个是 0 字节**。

**这件事差点让我给出错误结论**：第一次跑反向验证时，5 个场景有 3 个"改错后测试仍全绿"，
第一反应是"断言恒真"。真实原因是**补丁打在头文件上，测试 obj 根本没重编**。
如果不是坚持追查，本轮的"反向验证通过"会是假的。

**已修复**：`scripts/build/_wb_build.py` 加 dep-guard，构建前自动清理 0 字节依赖的 obj。
实测生效：`dep-guard: forced rebuild of 86 obj with empty .obj.d`。

详见 `docs/2026-11/构建缺陷_改头文件不触发重编译_20261121.md`。

### 4.2 环境问题：DSH 沙箱下原生进程写不了 `%TEMP%`

新会话第一次跑 `OcrEx2Test` 时 **8/9 失败**，全是 `path.empty()`。
不是代码问题：DSH 拦截了原生子进程对 `%TEMP%` 的写入（`err=5 拒绝访问`），
测试画不出临时 BMP。`$env:TEMP` 指到工作区即全部通过。

详见 `docs/2026-11/环境诊断_原生进程TEMP写入失败_20261120.md`。

> 你自己直接在终端跑（不经 DSH）不受影响。这一条只影响 DSH 会话。
