# 构建缺陷：改头文件不触发重新编译 —— 根因已定位（2026-11-21）

> **严重程度：高。** 会让人误判"修复无效"或"断言恒真"，是调试期最浪费时间的一类问题。
> 交接文档 §1.2 记录了「Copy-Item 恢复后必须 touch 时间戳」，但**本条与之无关**：
> 即使 touch 了头文件，也不会重建。**根因已在本轮完全定位，并给出修复方案。**

---

## 一、现象（可复现，已实测）

```powershell
$obj = "D:\AutoPro\op-master\op\build\nmake-x64-Release\tests\CMakeFiles\op_test.dir\find_str_batch_test.cpp.obj"
(Get-Item $obj).LastWriteTime        # 2026/11/20 23:49:02
(Get-Item "D:\AutoPro\op-master\op\libop\algorithm\StrMatch.h").LastWriteTime = Get-Date
cd D:\AutoPro\op-master\op
& "D:\Program Files\Python312\python.exe" scripts/build/_wb_build.py
(Get-Item $obj).LastWriteTime        # 仍是 2026/11/20 23:49:02  ← 没有重编
```

构建日志显示 `[100%] Built target op_test`，看着"已最新"，实际代码早已过期。

## 二、根因：**cl 的输出编码（UTF-8）与 CMake 记录的过滤前缀（GBK）不一致**

依赖扫描的调用形态（来自 `build.make`）：

```
cmake -E cmake_cl_compile_depends
      --dep-file=...obj.d
      --working-dir=...
      --filter-prefix="注意:  包含文件:  "
      -- cl.exe @C:\...\nmXXXX.tmp
```

`cmake_cl_compile_depends` 的工作是：把 `cl /showIncludes` 的输出行里**以 `--filter-prefix`
开头**的行过滤出来，把剩下的路径写进 `.obj.d`。前缀对不上 → 一行都不匹配 → **写出的 .d 是空文件**。

实测的编码不一致（本轮取证）：

| 项目 | 内容 | 字节 |
|---|---|---|
| `build.make` 里记录的 `--filter-prefix` | `注意:  包含文件:  ` | **GBK**：`D7 A2 D2 E2 3A 20 B0 FC BA AC CE C4 BC FE 3A 20 20` |
| `cl /showIncludes` 实际写到文件的输出 | `注意:  包含文件:  ...` | **UTF-8**：`E6 B3 A8 E6 84 8F 3A 20 E5 8C 85 E5 90 AB E6 96 87 E4 BB B6 3A 20 ...` |

取证方法：

```powershell
# 1) build.make 里的前缀字节
$b = [System.IO.File]::ReadAllBytes("build\nmake-x64-Release\libop\CMakeFiles\op_x64.dir\build.make")
# 找到 --filter-prefix= 后的 "..." 内容，按字节看：D7 A2 D2 E2 ... = GBK 的“注意”

# 2) cl 实际输出字节（重定向到文件）
cmd /c "`"<vcvars64> `" >nul 2>&1 && cl /nologo /showIncludes /c /Fo_ p.obj dep_probe_src.cpp > showinc.txt 2>&1"
$b = [System.IO.File]::ReadAllBytes("showinc.txt")
# 第一个 include 行以 E6 B3 A8 ... 开头 = UTF-8 的“注意”
```

> 为什么 cl 输出 UTF-8 而 CMake 记 GBK：`cl` 的本地化消息走 MSVC 的 `1033`/`2052` 语言包资源，
> 在 UTF-8 终端/重定向环境下以 UTF-8 落盘；而 CMake 在**配置阶段**把前缀字符串按当前
> ANSI 代码页（936/GBK）写进 `build.make`。两侧编码不同，字节级比较必然失败。
> （`VSLANG=1033` 无效：中文版 VS 装了中文语言包，cl 无论如何都输出中文消息。）

## 四、危害实证（为什么必须重视）

本轮做 P1/P3 的反向验证时，第一次跑完 5 个场景，**3 个场景"改错后测试仍全绿"**，
第一反应是"断言恒真"。实际原因是：**saboteur 补丁打在头文件 `StrMatch.h` 上，
测试 obj 根本没重编**，测试跑的是旧二进制。

补上"强制删 obj 再构建 + 校验 obj 时间戳确实更新"之后，5/5 全部如愿变红。

> 如果没有这一步，本轮的"反向验证通过"会是**假的**。

## 五、当前规避办法（已验证有效）

**改动任何被多个 TU 包含的头文件后，删掉受影响的 .obj 再构建：**

```powershell
$repo = "D:\AutoPro\op-master\op"
Remove-Item "$repo\build\nmake-x64-Release\tests\CMakeFiles\op_test.dir\*.obj" -Force
Remove-Item "$repo\build\nmake-x64-Release\libop\CMakeFiles\op_x64.dir\*.obj" -Force
Remove-Item "$repo\build\nmake-x64-Release\libop\CMakeFiles\libop.dir\*.obj" -Force
& "D:\Program Files\Python312\python.exe" scripts/build/_wb_build.py
```

`workbench\reverse_verify.ps1` 已内置该逻辑（`Force-Rebuild`），并在构建后
**校验 obj 时间戳确实更新**，否则把场景判为 `INVALID-STALE-OBJ` 而不是"通过"。

**哪些改动是安全的（无需清理）**：
- 只改 `.cpp`（`.cpp` 是 `build.make` 的显式依赖，会正常触发重编）
- 新增 `.cpp` / 新增头文件（新文件没有旧 obj）

**哪些改动必须清理**：
- 改动任何既有 `.h`，尤其 `OcrService.h`（`ocr_char_t`/`ocr_line_ext_t`/本轮新增的 `ocr_profile_t`）、
  `Types.h`、`libop.h`、`op_c_api.h`、`StrMatch.h`

## 六、建议的长期修法（未实施，需单独排期）

按可靠性排序：

1. **改用 Ninja 生成器**（最彻底）。Ninja 用 `deps = msvc` 自己解析 `/showIncludes`，
   不经过 `cmake_cl_compile_depends` 的 `--filter-prefix` 字符串比较，天然免疫本问题。
   代价：需要重新配置构建目录，`_wb_build.py` 要改（`nmake` → `ninja`）。**推荐**。
2. **删除并重建 CMake 缓存**，同时把配置阶段的代码页设成 65001（UTF-8），
   让 `build.make` 里记录的前缀与 cl 输出同为 UTF-8。做法：
   `chcp 65001` + `set CMAKE_...`，再 `cmake -S . -B build/...` 重新配置。
   风险：CMake 对非 ASCII 路径/参数的 UTF-8 处理在 Windows 上历来不稳，需实测。
3. 在 `_wb_build.py` 里加保护：构建前扫描所有 `*.obj.d`，发现 0 字节的就把对应
   `.obj` 删掉（强制重编）。**成本最低、立刻可用**，建议至少先加这一条。
4. 配置一个英文 UA 版的 cl（仅装英文语言包）——改动面太大，不推荐。

## 七、给后续会话的提醒

> 跑反向验证、"修复后没生效"、"测试结果反直觉"这三种情况，
> **第一件事先确认 obj 真的重编了**：
> `(Get-Item <对应>.obj).LastWriteTime` 必须晚于你改文件的时间。
> 这一条比任何调试技巧都省时间。
