```

```

## 二、技术路线（沿用规划定稿，不自创）

**WASAPI 会话级音量**：

```
MMDeviceEnumerator
  -> GetDefaultAudioEndpoint(eRender, eConsole)
  -> IAudioSessionManager2
  -> 按 PID 匹配 IAudioSessionControl2
  -> ISimpleAudioVolume   （滑块音量 / 静音，可写）
  -> IAudioMeterInformation（GetPeakValue 实时响度，只读）
```

**为什么是会话级而不是全局**：用户要的是"**某个游戏**有没有声音"。
全局音量在系统混音层面，分不清是哪个进程；会话级能按 PID 定位。

### 2.1 规划里记录过的 4 个真机坑（Python 版踩过，C++ 版要避开）

| # | 坑 | 对策 |
|---|---|---|
| 1 | COM 初始化重复/未配对释放 | RAII + 接受 `RPC_E_CHANGED_MODE`，只释放自己成功那次 |
| 2 | 缓存会话指针，游戏重启后 PID 变化指向野指针 | **每次调用重新枚举**，不缓存任何 COM 指针 |
| 3 | vtable 下标手误（Python ctypes 特有） | C++ 用官方头 + `__uuidof` + `CComPtr`，天然没有 |
| 4 | 峰值保持/衰减需要状态 | **DLL 无状态**，峰值保持留在调用方 |

### 2.2 关键语义（必须写清楚，否则误用）

| 字段 | 语义 |
|---|---|
| `found` | 该 PID 是否有音频会话。**没有会话 ≠ 没声音**（可能在播放系统音，或进程刚启动还没建会话） |
| `muted` | 该会话是否被静音 |
| `playing` | 该会话是否处于 Active 状态（`IAudioSessionControl::GetState == AudioSessionStateActive`） |
| `volume` | 滑块值 0.0~1.0（**与出声大小无直接关系**：滑块 1.0 也可能当前无声音） |
| `peak` | 实时峰值 0.0~1.0（`GetPeakValue`）。**"现在有没有声音"看这个** |
| `error` | 失败原因（成功为空串） |

> ⚠ 最常见的误用：用 `volume` 判断"游戏有没有声音"。正确做法是 `peak > 阈值`。
> 规划 §8.3 的真机验收标准也是这么定的："**滑块值不随出声变化**"。

## 三、接口设计

### 3.1 C ABI（对齐规划命名）

| 接口 | 说明 |
|---|---|
| `OpAudioQueryWindow(hwnd)` | 按窗口句柄：取其 PID，再查该 PID 的会话；返回 JSON |
| `OpAudioQueryPid(pid)` | 按 PID 直接查（窗口取不到 PID 时的兜底） |
| `OpAudioGetPidFromHwnd(hwnd)` | 纯取 PID（不碰 COM，轻量） |
| `OpAudioSetVolume(pid, volume)` | 设置滑块（0.0~1.0） |
| `OpAudioSetMute(pid, muted)` | 设置静音 |

**为什么返回 JSON 而不是 POD 结构体**：规划原设想 POD `{found,muted,playing,volume,peak,error[256]}`。
但 op 全系列已经是 JSON 风格（OCR/FindStr/YOLO/OpenCV），且 COM 层返回结构体需要额外封送。
**改用 JSON**，与既有接口一致，易语言侧也统一。

```json
{"ok":1,"code":0,"found":true,"pid":12345,
 "muted":false,"playing":true,
 "volume":0.75,"peak":0.3421,"error":""}
```

- `ok`: 1=查询链路成功（**不代表有声音**）；0=失败（看 `error`）
- `found=false` 时 `muted/playing/volume/peak` 全为 0/false，`ok` 仍可能为 1
  （"顺利查完，但这个 PID 没有会话"是有效结果，不是错误）

### 3.2 失败分级（code）

| code | 含义 |
|---|---|
| 0 | 成功 |
| -1 | 无默认音频渲染设备（`GetDefaultAudioEndpoint` 失败） |
| -2 | 创建 `IAudioSessionManager2` 失败 |
| -3 | 枚举会话失败 |
| -4 | 传入 PID/HWND 非法 |
| -5 | 设置音量/静音失败 |

## 四、实现要点

### 4.1 COM 初始化 RAII

```cpp
struct ComGuard {
    bool owned = false;
    ComGuard() {
        HRESULT hr = CoInitializeEx(nullptr, COINIT_MULTITHREADED);
        // RPC_E_CHANGED_MODE：别的线程已用 STA 初始化，可直接用，但不归我们释放
        owned = SUCCEEDED(hr);
    }
    ~ComGuard() { if (owned) CoUninitialize(); }
};
```

**必须接受 `RPC_E_CHANGED_MODE`**：op 是插件，宿主可能已在 STA 里初始化过 COM。
此时不能再 `CoUninitialize`（不是我们初始化的），否则会破坏宿主状态。

### 4.2 每次重新枚举

不缓存 `IAudioSessionManager2` 或会话指针。理由：游戏重启 PID 变了，
缓存指针会指向已失效对象。枚举成本很低（单次 <2ms）。

### 4.3 构建接线

- 新增 `libop/audio/AudioService.cpp/.h` → 必须同步 `libop/CMakeLists.txt`
- 链接 `ole32.lib`（已链接）+ `mmdevapi.lib`（**需确认已链接**）
- 新增测试 `tests/audio_test.cpp` → 同步 `tests/CMakeLists.txt`
- `#include <mmdeviceapi.h>` `<audiopolicy.h>` `<endpointvolume.h>`

### 5.1 A8 的现实困难（必须说明）

要验证"设置音量→读回一致"，需要一个**有音频会话的进程**。
测试进程自己默认没有音频会话（除非它播放音频）。

两条路：
1. **生成一个带音频的测试进程**：用 `PlaySound` 播放一段静音 wav，
   Windows 会为其创建音频会话。可行但依赖机器有音频设备。
2. **跳过并写明原因**：没有音频设备时 `found=false`，如实跳过。

**决策：两条都做** —— 有设备就跑真实验证，没设备就 `GTEST_SKIP` 并写明。
不假装验证过。

## 六、反向验证计划

1. `ComGuard` 无条件 `CoUninitialize`（无视 `owned`）→ 宿主 STA 场景破坏 COM，
   用"先 CoInitializeEx(STA) 再调接口再验证 COM 仍可用"的用例抓。
2. `found` 判据恒真（不比对 PID）→ A2 必须 FAIL。
3. `peak` 与 `volume` 字段写颠倒 → A6 必须 FAIL。
4. 非法 PID 不校验 → A3 必须 FAIL。

## 七、不做

- 全局系统音量（`IAudioEndpointVolume`）：需求是"某游戏有没有声"，全局分不清进程。
  但**顺手可加**——见 §8。
- 峰值保持 / 平滑 / 阈值判定：属调用方逻辑（规划明确"DLL 无状态"）。

## 八、可选增项（时间允许就做）

规划原文档只要求会话级。但"**查系统总音量 / 设置系统静音**"是同类高频需求，
且只需 `IAudioEndpointVolume`（同一套 enumerator 上多取一个接口）：

| 接口 | 说明 |
|---|---|
| `OpAudioGetSystemVolume()` | 系统主音量 0~1 + 是否静音 |
| `OpAudioSetSystemVolume(volume)` / `OpAudioSetSystemMute(muted)` | 设置系统音量/静音 |

成本很低（复用同一 enumerator），价值明确。**计划做**。

### 9.2 真机验证结果（本机有音频设备，全部闭环）

**用子进程播放 440Hz 循环音频创建真实会话，实测：**

```
query #1: {"ok":1,"code":0,"found":true,"pid":33596,"muted":false,"playing":true,
           "volume":1,"peak":0.194206073880196,"error":""}
query #2: {"ok":1,...,"volume":1,"peak":0.194206103682518,...}   ← peak 两次略有差异（实时特性）
SetSessionVolume(0.42) -> 0
after set: volume=0.420   ← 写入读回一致
```

> **这组数据同时印证了本模块最重要的语义**：
> `volume=1`（滑块满格）而 `peak=0.194` —— **滑块值与出声大小确实无关**，
> 判断"现在有没有声音"必须看 `peak`。

**其他路径实测**：

| 场景 | 结果 |
|---|---|
| 系统音量 | `{"ok":1,"code":0,"muted":false,"volume":1}` ✅ |
| 自身进程（无会话） | `found=false, ok=1` ✅ 正确语义 |
| PID=0 | `ok=0, code=-4, error="invalid pid"` ✅ |
| PID=999999（不存在） | `found=false, ok=1` ✅ |

### 9.4 反向验证（`scripts/probes/reverse_verify_audio.ps1`）

| 场景 | 改错内容 | 结果 |
|---|---|---|
| RV-A1 | `found` 判据恒真（不比 PID） | **RED** ✓ |
| RV-A2 | 非法 PID 不校验 | **RED** ✓ |
| RV-A3 | `volume` 与 `peak` 写颠倒 | **RED** ✓ |
| RV-A4 | `ComGuard` 把 `RPC_E_CHANGED_MODE` 也算作自己初始化 | **RED**（落在 STA 用例上）✓ |

**RV-A4 值得单独说**：COM 初始化语义在 MTA 主线程**测不出来**
（`owned=true` 时无条件/有条件释放表现相同）。为此专门加了
`StaHostKeepsComUsableAfterCalls`：先让当前线程以 STA 初始化（模拟宿主），
连续调接口，最后再自己 `CoCreateInstance` 一个 COM 对象确认仍可用。
**这个用例让 RV-A4 从"抓不到"变成"能抓到"**。

### 9.5 过程中自己制造并修掉的一个测试缺陷（如实记录）

`StaHostKeepsComUsableAfterCalls` 第一版在开头无条件调 `::CoUninitialize()`
想"确保 COM 干净"，结果把后续用例依赖的 COM 引用计数扣掉了 ——
表现为 `RealSessionReadWriteRoundTrip` 在本用例之后**偶发失败**（单独跑则通过）。

**这是测试自身制造的污染，不是产品缺陷。**
修正：改用探针 `CoInitializeEx` 判断当前线程 COM 状态，
只在"原本未初始化 / 本用例 +1"时才释放（`owns_com` 标记），
真正处于"宿主已初始化"场景时直接复用。之后 11/11 稳定全绿。

### 9.6 与规划原案的偏差

| 项 | 规划 | 实际 | 理由 |
|---|---|---|---|
| 返回形态 | POD 结构体 `{found,muted,playing,volume,peak,error[256]}` | **JSON** | op 全系列已统一 JSON（OCR/FindStr/YOLO/OpenCV）；COM 层返回结构体需额外封送 |
| 系统音量 | 未要求 | **加了 4 个接口** | 同一套 enumerator 上多取 `IAudioEndpointVolume`，成本极低、需求高频 |
| 独立 DLL | 建议并入 op | **并入 op** | 沿用规划建议，分发链路零新增成本 |

### 9.7 未做（明确）

- 峰值保持/衰减/阈值判定：按规划「DLL 无状态」，全部留给调用方
- 音频采集/回放（`IAudioClient` 环回）：超出"查音量"范围，属独立能力
- 麦克风（eCapture）设备：本期只做渲染（eRender）侧

## 十、后续修正：4 个 setter 的返回值契约（2026-11-21 18:30）

### 10.1 发现的缺陷（`scripts/return_contract_survey.py` 报出来的）

4 个 setter 原实现把 `op::audio::Set*` 的返回值**原样透传**：

| 接口 | 原返回 | 契约要求 |
|---|---|---|
| `AudioSetSessionVolume` | 成功 `0` / 失败 `-2/-4/-5` | 成功 `1` / 失败 `0` |
| `AudioSetSessionMute` | 同上 | 同上 |
| `AudioSetSystemVolume` | 同上 | 同上 |
| `AudioSetSystemMute` | 同上 | 同上 |

**这是语义整体反转，不是"错误码风格不同"**：

- 库内对外契约是「`0` = 失败，非 `0` = 成功」（`OpSetPath` 返 1、宿主普遍 `if (ret)` 判定）；
- 于是**成功返回 0 → 调用方判失败；失败返回 -5 → 被当成成功**（负数在布尔语境里是真）；
- 相邻的 `AudioGetPidFromHwnd` 又是「失败返回 0」，两个紧挨着的接口 0 语义相反。

### 10.2 修法

`OpAudio.cpp` 加 `setter_result()` 归一：成功 `1`、失败 `0`，
具体错误码写 `__op.log`（`setlog`）；要结构化错误码的调用方走
`AudioQueryPid` 的 `code` 字段（`-1` 无设备 / `-2` COM / `-3` 枚举 / `-5` 设置失败）。

> 注意：**JSON 里的 `code` 字段仍是 0=成功**（它是显式字段，不是布尔返回值），
> 两套口径并存是有意的，文档分别标注。

### 10.3 反向验证

把 `setter_result` 改回"原样透传"，3 条用例**全部变红**：

```
FAILED  AudioTest.SetSessionRejectsInvalidPid        (期望 0，实际 -4)
FAILED  AudioTest.SetVolumeClampsOutOfRange          (期望 0，实际 -5)
FAILED  AudioTest.RealSessionReadWriteRoundTrip      (期望 1，实际 0)
```

恢复后 `AudioTest.*` **11/11 PASS**。
